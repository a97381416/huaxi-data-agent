# “可打断 → 恢复”功能迁移方案（从 0 到 1 移植指南）

> 目标读者：要把本项目的“可打断→恢复、停止后发消息（可空/也可以不空）”能力移植到**另一个 Agent** 的开发者。
> 参考实现：`backend/mini-agentx-core`（内核）+ `backend/data-agent-server` 的 `DodoAgent`/`AgentController`（接入层）。
> 阅读前提：目标 Agent 是 Java 后端、执行过程产出流式事件、有工具调用循环（ReAct 或类似）。
> 姊妹篇：《刷新不丢功能迁移方案.md》解决“连接断执行不停”；本文解决“**用户主动停 → 现场存下来 → 以后接着跑**”。

---

## 1. 问题与思路（一分钟版）

**现象**：Agent 跑一个复杂任务要几十秒、十几轮工具调用。用户中途点“停止”，半截工作直接报废——要么重头再跑一遍（浪费 token 和工具副作用），要么永远丢掉。

**根因**：执行循环把“用户不想看了”等同于“任务该死”。停止信号直接 dispose 掉整个执行，消息链、执行到第几轮、哪些工具调了还没回灌——全部随订阅一起消失。

**思路**：把“停止”拆成两种语义，并在停止瞬间给执行现场拍一张快照：

| 动作 | 语义 | 现场处理 | 后续 |
| --- | --- | --- | --- |
| **interrupt（可恢复暂停）** | “先停下，我待会儿回来” | 刷入半截输出 → 补占位响应 → **快照落库** → 发 `PAUSED` 事件 | 同会话下次发消息时**自动走恢复通道**续跑 |
| **stopTask（强制停止）** | “这个任务不要了” | dispose 订阅 → 直接 complete | 不产生快照，不可恢复 |

**“停止后发消息（可空/也可以不空）”= 恢复通道的三分支语义**（本方案的灵魂）：

| 用户停止后回来发的内容 | resumeQuery | 恢复行为 |
| --- | --- | --- |
| 什么都不发，直接点“继续” | **空** | **本地真实重放**被打断的 pending 工具调用（不重调 LLM），然后继续循环 |
| 发“继续”“接着来”这类指令 | 非空 | 工具**不重放**（注入“已跳过”占位），原始任务 + 用户消息用**澄清语包装**后追加，由模型基于快照上下文自决策续跑 |
| 发新的澄清/补充/方向调整 | 非空 | 同上——模型自己判断用户是想细化原任务、还是提了新问题、还是只是让继续 |

设计哲学：**空消息 = 确定性续跑（代码说了算）；非空消息 = 语义续跑（模型说了算）**。代码不为非空消息猜意图，只负责把现场和用户的话原样摆到模型面前。

## 2. 总体架构与五条不变式

```
 前端                Controller               AgentTaskManager            AgentLoopExecutor（执行循环）
  │  GET /agent/stop     │  interrupt(convId,msg)    │                        │
  │ ───────────────────► │ ─────────────────────────►│ tasks.remove(convId)   │
  │                      │                           │ disposable.dispose() ──► LLM 流被切断
  │                      │                           │ handler.accept(msg) ───► onInterrupt():
  │                      │                           │                          ① 刷半截输出入链
  │                      │                           │                          ② 未回灌工具补占位
  │                      │                           │                          ③ buildSnapshot()
  │  ◄─ SSE: PAUSED ──── │ ◄── sink.tryEmitNext ─────┤                          ④ stateStore.save()
  │                      │                           │                          ⑤ persistTerminal("interrupted")
  │                      │                           │                          ⑥ 发 PAUSED → complete
  │  （用户回来，发消息或直接继续）                      │                        │
  │  POST /agent/stream  │  hasInterruptedState()?   │                        │
  │ ───────────────────► │ ──── yes ──► resumeStream(convId, query /* 可空 */) ─────►│
  │                      │                           │                        │ initMessagesFromResume():
  │  ◄─ TEXT/TOOL/... ── │                           │                        │  反序列化 → 剥占位 → 重放/跳过
  │  ◄─ SSE: COMPLETE ── │                           │                        │  → 追加澄清语 → 继续循环
```

迁移时**不可走样**的五条不变式：

1. **执行与连接解耦是前提**。打断的对象是“注册在案的**任务**”（TaskManager 按 conversationId 登记），不是某条 HTTP 连接。如果目标 Agent 的执行还绑在 HTTP 订阅上（前端断开执行就死），先迁移《刷新不丢》方案，否则 interrupt 连打断谁都找不到。
2. **中断只能发生在安全点，且快照必须能表达“当时正在干什么”**。安全点只有两个：`LLM_STREAMING`（在收 LLM 流，副作用只是耗 token）和 `TOOL_EXECUTION`（工具已发出、结果未回灌）。快照记录 safePoint + pendingToolCalls，恢复时才知道该重放什么。
3. **消息链协议配对**。OpenAI 兼容协议要求每个 `assistant.tool_calls` 后面必须跟着对应 `tool_call_id` 的工具响应，孤立 tool_call 会让下一轮 LLM 调用直接 400。中断现场一律用**占位响应**补配对，恢复时再按占位标记剥离替换。
4. **终态单次（CAS）**。每条流必以 PAUSED 或 COMPLETE 收尾、且只发一次；落库只落一次。中断收尾和正常收尾可能并发赛跑，全靠 `AtomicBoolean.compareAndSet` 裁决。
5. **快照生命周期单向**：`Paused 时 save → 恢复时消费 / 非 Paused 终态（complete、error）及 takeOver 时 delete`。终态不删快照 = 僵尸恢复：任务明明完成了，用户下次发消息却从旧断点复活。

## 3. 第 0 步：迁移前置检查

动手前确认目标 Agent 满足以下四点，缺什么补什么：

| # | 检查项 | 不满足时的补救 |
| --- | --- | --- |
| A | 执行循环是**独立于 HTTP 连接的后台任务**，可通过 conversationId 定位并 dispose（Reactor `Disposable` 或等价物） | 先做执行/连接解耦（见《刷新不丢方案》）；或退化为“停止即放弃，不支持恢复” |
| B | 执行过程能产出**事件流**，且事件模型里有终态语义（能表达 PAUSED） | 参照 Step 1 扩展事件枚举 |
| C | 消息链（system/user/assistant+tool_calls/tool）可**序列化/反序列化**，且 tool_call id 在链中可配对 | 参照 Step 4 的 OpenAI 风格 role JSON 行格式，为目标框架写一对转换器 |
| D | 每轮问答有稳定的 **conversationId**，同会话新请求能被路由到同一个入口 | 前端生成 UUID 随请求携带即可 |

## 4. Step 1：统一事件契约（PAUSED 是一种终态）

事件模型只需在既有 6 种事件上加一种 `PAUSED`。核心约束写进约定：**每个流必以 PAUSED 或 COMPLETE 收尾**，前端据此判断“是暂停了还是真结束了”。

```java
/** 流式事件模型（可按目标 Agent 裁剪，PAUSED 为本方案必需） */
public class AgentStreamEvent {
    public enum Type {
        THINKING, TEXT, TOOL_START, TOOL_END,
        PAUSED,    // 暂停（用户中断），发完立即 complete 流
        ERROR,     // LLM 异常（重试中每次都发）
        COMPLETE   // 终态（成功/失败都发）
    }

    private final Type type;
    private final String content;      // THINKING/TEXT 增量
    private final String toolName, toolCallId, arguments, result;
    private final String code, message, detail;   // ERROR 三件套
    private final String pauseReason;  // PAUSED 专用：USER_INTERRUPT / HITL_TOOL_REQUEST
    private final String sessionId;    // PAUSED/COMPLETE 携带：本逻辑轮次的落库 ID

    public static AgentStreamEvent paused(String reason, String sessionId) { ... }
}
```

要点：
- `pauseReason` 让前端区分暂停原因，渲染“已暂停，可继续”的 UI。
- `sessionId` 必须带：暂停也是一次落库（产生一个逻辑轮次），前端把这一轮的附件/trace 关联到这个 ID，恢复后归属不变。

**验收标准**：前端收到 `PAUSED` 后知道流已结束但任务可恢复；收到 `COMPLETE` 后知道任务终结。

## 5. Step 2：安全点状态机（InterruptContext）

回答“中断时我在哪、有什么在飞”。这是快照能正确表达现场的基础，也是整个方案里最容易被忽略的组件——没有它，快照只是一串消息，恢复时不知道哪些工具调用还没回灌。

```java
/**
 * SafePoint 安全点状态机 + 打断上下文。
 * 状态单向初始化后在 LLM_STREAMING ⇄ TOOL_EXECUTION 间切换。
 */
public class InterruptContext {

    private volatile SafePoint safePoint = SafePoint.INIT;      // INIT → LLM_STREAMING ⇄ TOOL_EXECUTION
    private volatile boolean interrupted = false;
    private volatile List<PendingToolCall> pendingToolCalls = List.of();
    private final CopyOnWriteArrayList<Runnable> interruptCallbacks = new CopyOnWriteArrayList<>();

    /** 调 LLM 前切：副作用仅耗 token，中断时半截输出刷成 assistant 消息即可 */
    public void enterLlmStreaming() {
        this.safePoint = SafePoint.LLM_STREAMING;
        this.pendingToolCalls = List.of();
    }

    /** 调工具前切：缓存待执行工具清单（快照靠它表达"待执行"状态） */
    public void enterToolExecution(List<PendingToolCall> calls) {
        this.safePoint = SafePoint.TOOL_EXECUTION;
        this.pendingToolCalls = List.copyOf(calls);
    }

    public void markInterrupted() { this.interrupted = true; }
    public boolean isInterrupted() { return interrupted; }
    public SafePoint getSafePoint() { return safePoint; }
    public List<PendingToolCall> getPendingToolCalls() { return pendingToolCalls; }

    /** 注册中断回调（interrupt 时在打断线程上执行） */
    public void onInterrupt(Runnable callback) { interruptCallbacks.add(callback); }

    /** 触发中断回调（仅一次；由 AgentTaskManager 保证） */
    public void fireInterrupt() {
        markInterrupted();
        for (Runnable cb : interruptCallbacks) {
            try { cb.run(); } catch (Exception ignored) { /* 不阻断后续回调 */ }
        }
    }
}
```

接入方式（两处，都在执行循环里）：

```java
// ① 每轮调 LLM 前（scheduleRound）：
interruptCtx.enterLlmStreaming();

// ② 每轮并发执行工具前（finishRound）：
List<PendingToolCall> pending = merged.stream()
        .map(tc -> new PendingToolCall(tc.id(), tc.name(), tc.arguments()))
        .toList();
interruptCtx.enterToolExecution(pending);   // 快照可表达待执行状态

// ③ 所有可能的续跑入口检查打断标志，置位后不再续轮：
if (interruptCtx.isInterrupted() || terminalEmitted.get()) return;
```

关键语义：**interrupt 标志置位后，工具完成回调据此不再续轮**（`if (interruptCtx.isInterrupted()) return;`），收尾权让给中断处理器——否则工具执行完了照样 scheduleRound，打断白打。

## 6. Step 3：任务登记与两种停止（AgentTaskManager）

回答“停止按钮按下去，谁来定位并切断执行”。单例共享（可跨 Agent 实例），按 conversationId 登记：

```java
public class AgentTaskManager {

    /** 执行器注册的中断回调：入参 interruptMessage（停止时附言，可空） */
    public interface InterruptHandler extends Consumer<String> {}

    private static final class TaskInfo {
        final Sinks.Many<?> sink;              // 该任务的事件流出口
        volatile Disposable disposable;        // 当前轮 LLM 流/重试延时的订阅
        final InterruptHandler interruptHandler;
    }

    private final Map<String, TaskInfo> tasks = new ConcurrentHashMap<>();

    /** 登记任务；putIfAbsent —— 同会话互斥（一个会话同时只能有一个运行任务） */
    public void registerTask(String conversationId, Sinks.Many<?> sink, InterruptHandler handler) {
        TaskInfo existing = tasks.putIfAbsent(conversationId, new TaskInfo(sink, handler));
        if (existing != null) throw new IllegalStateException("会话已有进行中的执行: " + conversationId);
    }

    /** 每轮 LLM 订阅建立后绑定，interrupt 时据此 dispose */
    public void bindDisposable(String conversationId, Disposable disposable) { ... }

    /** 执行器结束时注销（complete/error/paused 之后） */
    public void unregisterTask(String conversationId) { tasks.remove(conversationId); }

    /**
     * 可恢复中断：dispose 订阅（停流）→ 执行器回调（flush 输出 → 快照 → PAUSED）。
     * @return true=找到任务并触发；false=无运行任务
     */
    public boolean interrupt(String conversationId, String message) {
        TaskInfo info = tasks.remove(conversationId);
        if (info == null) return false;
        if (info.disposable != null && !info.disposable.isDisposed()) {
            info.disposable.dispose();
        }
        if (info.interruptHandler != null) {
            info.interruptHandler.accept(message);
        }
        return true;
    }

    /** 强制停止（丢弃状态，不产生 PAUSED 事件、不落快照） */
    public boolean stopTask(String conversationId) {
        TaskInfo info = tasks.remove(conversationId);
        if (info == null) return false;
        if (info.disposable != null && !info.disposable.isDisposed()) {
            info.disposable.dispose();
        }
        info.sink.tryEmitComplete();
        return true;
    }
}
```

三个不可走样的细节：

1. **`interrupt()` 先 dispose 再回调**：dispose 切断 LLM 流（chunk 不再进来），但收尾逻辑跑在**打断线程**上（调用 `/stop` 的 HTTP 线程），不在原订阅线程。执行循环里的收尾代码（`onInterrupt`）必须按“任意线程可能调用”来写——所有共享状态走 `synchronized`/volatile。
2. **`interrupt()` 里 `tasks.remove` 是移除而非 get**：天然保证回调只触发一次，并发 interrupt 第二次直接返回 false。
3. **dispose 引发的流取消不算错误**：LLM 流被切断后 Reactor 会走 cancel/doFinally，执行循环里要区分“用户打断引发的取消”和“真错误”——`handleLlmError` 开头一句 `if (interruptCtx.isInterrupted()) return;`。

## 7. Step 4：快照模型与存储（PauseState / PauseStateStore）

### 7.1 快照模型

回答“恢复需要哪些现场信息”。逐字段问一遍“恢复时要不要”，少一个字段恢复就变形：

```java
public class PauseState {
    public enum Reason { USER_INTERRUPT, HITL_TOOL_REQUEST /* 占位 */ }
    public enum SafePoint { INIT, LLM_STREAMING, TOOL_EXECUTION }

    private final String conversationId;   // 快照键
    private final String sessionId;        // 逻辑轮次 ID：恢复沿用，落库/trace 归属一致
    private final String query;            // 原始任务（澄清语包装时要用）
    private final RunnableParams params;   // userId/customParams/toolParams：恢复时重建执行参数
    private final List<String> messagesJson;       // 完整消息链逐条 JSON 行（含半截输出与占位响应）
    private final int currentRound;                // 中断时已完成轮次：恢复沿用
    private final List<PendingToolCall> pendingToolCalls; // 未回灌的工具调用（恢复时重放/跳过）
    private final long totalPromptTokens, totalCompletionTokens; // 恢复沿用，统计不断档
    private final Reason reason;
    private final SafePoint safePoint;
    private final String interruptMessage;         // 打断附言（"用户请求中断"/"新消息顶掉旧回答"）
    private final long interruptedAt;

    /** 待执行/未回灌的工具调用。重放要求工具幂等——工具可能已部分执行副作用 */
    public record PendingToolCall(String id, String name, String arguments) {}
}
```

### 7.2 消息链序列化

快照的灵魂是 `messagesJson`：**逐条消息一行 JSON，用 OpenAI 风格 role 格式作为交换格式**（任何框架都能映射）：

```
{"role":"system","content":"..."}
{"role":"user","content":"..."}
{"role":"assistant","content":"...","tool_calls":[{"id","name","arguments"}],"reasoning_content":"..."}
{"role":"tool","tool_call_id":"..","name":"..","content":"result"}
```

实现要点（参考 `MessageJsonSerializer`，约 170 行，可直接移植后改消息类型）：
- ToolResponseMessage 序列化时**展开为多行** `role:"tool"`，反序列化时**连续 tool 行合并**回一条消息（对齐 OpenAI 协议的一对多关系）。
- 思考内容放 `reasoning_content` 字段随链保存，恢复后前端还能回放“思考过程”。
- 序列化失败不抛异常（退化为 user 行兜底）、反序列化失败行跳过——快照损坏不能让恢复通道整个挂死。

### 7.3 存储接口与两级实现

```java
public interface PauseStateStore {
    void save(PauseState state);
    PauseState get(String conversationId);
    boolean delete(String conversationId);   // true=删除成功（可作并发恢复 CAS）
    boolean has(String conversationId);
}
```

- **第一级：InMemoryPauseStateStore**（`ConcurrentHashMap` + 7 天 TTL，进程重启丢）——先跑通全流程。
- **第二级：JdbcPauseStateStore**（表 `agentx_pause_state`，UPSERT by conversation_id，TTL 7 天）——生产形态，跨重启可恢复。表结构：

```sql
CREATE TABLE IF NOT EXISTS `agentx_pause_state` (
  `id` bigint NOT NULL AUTO_INCREMENT,
  `conversation_id` varchar(100) NOT NULL COMMENT '会话ID',
  `reason` varchar(50) NOT NULL COMMENT '暂停原因',
  `safe_point` varchar(50) DEFAULT NULL COMMENT '中断安全点',
  `current_round` int NOT NULL COMMENT '中断时已完成轮次',
  `interrupted_at` timestamp NOT NULL COMMENT '中断时间',
  `expires_at` timestamp NULL DEFAULT NULL COMMENT '过期时间',
  `snapshot_json` longtext NOT NULL COMMENT '完整 PauseState JSON',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_conversation_id` (`conversation_id`),
  INDEX `idx_pause_state_expires` (`expires_at`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

序列化注意：**手工转 Map 存 JSON，不要让 Jackson 反射序列化整个 PauseState**——params 里可能挂框架类型，反射序列化既脆又可能把不该存的带进去。过期清理偷懒做法：每次 `save` 时顺手 `DELETE ... WHERE expires_at < NOW()` 一次（恢复频率低，不值得定时任务）。

## 8. Step 5：执行循环接入中断（打断收尾 = onInterrupt）

这是本方案**代码量最大、正确性要求最高**的一步。中断处理器把“任意时刻被砍”的执行整理成“协议合法、可恢复”的现场。

### 8.1 打断收尾主流程

```java
/** 中断回调：在打断线程上执行（AgentTaskManager.interrupt 触发） */
private void onInterrupt(String interruptMessage) {
    interruptCtx.markInterrupted();
    PauseState snapshot;
    synchronized (this) {
        RoundState rs = current;
        current = null;
        if (rs != null) {
            // 现场A：LLM 流式被打断 —— 半截输出刷成 AssistantMessage 入链（不丢已生成的字）
            flushParser(rs);                       // ThinkTag 未闭合的补齐刷出
            List<ToolCall> merged = buildToolCalls(rs);   // 聚合流式分片的 tool_call
            messages.add(AssistantMessage.builder()
                    .content(rs.textBuffer.toString())
                    .properties(reasoningProps(rs.reasoningBuffer.toString()))
                    .toolCalls(merged)
                    .build());
            if (!merged.isEmpty()) {
                // 已解析出 toolCall 但尚未执行：登记为 pending + 补占位响应（协议配对）
                interruptCtx.enterToolExecution(merged.stream()
                        .map(tc -> new PendingToolCall(tc.id(), tc.name(), tc.arguments()))
                        .toList());
                appendToolResponses(placeholderResponses(merged));
            }
            accumulateTokens(rs);
        } else {
            // 现场B：工具执行期被打断 —— 给链尾未回灌的 toolCall 补占位响应
            closeDanglingToolCalls();
        }
        snapshot = buildSnapshot(interruptMessage);
    }
    if (stateStore != null) stateStore.save(snapshot);          // ④ 快照落库
    if (!terminalEmitted.compareAndSet(false, true)) return;    // ⑤ 终态 CAS（与正常收尾赛跑）
    persistTerminal("interrupted");                             // ⑥ 消息链落库（暂停也是一个轮次）
    emit(AgentStreamEvent.paused("USER_INTERRUPT", sessionId)); // ⑦ PAUSED 事件
    resultRef.set(AgentResult.paused(snapshot));
    finishSink();                                               // ⑧ complete + 注销任务
}
```

### 8.2 两个“补配对”工具方法

```java
/** 占位响应：保证【工具调用—工具结果】成对出现，带标记供恢复时识别剥离 */
private List<ToolResponse> placeholderResponses(List<ToolCall> calls) {
    return calls.stream()
        .map(tc -> new ToolResponse(tc.id(), tc.name(),
                "[占位] 本轮工具调用未产生真实结果（轮次上限/中断），请基于已有信息作答。"))
        .toList();
}

/** 工具执行期被打断（现场B）：找链尾最近的带 toolCalls 的 assistant，未回灌的补占位 */
private void closeDanglingToolCalls() {
    List<ToolCall> dangling = new ArrayList<>();
    for (int i = messages.size() - 1; i >= 0; i--) {
        Message m = messages.get(i);
        if (m instanceof ToolResponseMessage) continue;   // 已回灌的跳过
        if (m instanceof AssistantMessage am && am.hasToolCalls()) {
            for (ToolCall tc : am.getToolCalls()) {
                if (!respondedToolCallIds.contains(tc.id())) dangling.add(tc);
            }
            break;   // 只看链尾最近一个 assistant
        }
        break;
    }
    if (!dangling.isEmpty()) appendToolResponses(placeholderResponses(dangling));
}
```

注意执行循环里要有 `respondedToolCallIds`（LinkedHashSet）随手记账：每次 `appendToolResponses` 时把 id 塞进去。`closeDanglingToolCalls` 靠它区分“真回灌过”和“还没回灌”。

### 8.3 正常路径的配合改动

| 位置 | 改动 | 目的 |
| --- | --- | --- |
| `scheduleRound` 开头 | `if (interruptCtx.isInterrupted() || terminalEmitted.get()) return;` | 打断后不再开新轮 |
| `scheduleRound` 调 LLM 前 | `interruptCtx.enterLlmStreaming()` | 切安全点 |
| `finishRound` 工具轮 | `interruptCtx.enterToolExecution(pending)` | 切安全点 + 缓存待执行清单 |
| 工具完成回调开头 | `if (interruptCtx.isInterrupted() || terminalEmitted.get()) return;` | 打断后工具结果不回灌、不续轮，收尾权让给 onInterrupt |
| `handleLlmError` 开头 | `if (interruptCtx.isInterrupted()) return;` | dispose 引发的取消不算错误 |
| `completeTerminal` / `errorTerminal` | `discardSnapshot()` | 非 Paused 终态删快照（不变式 5） |
| 流 `doFinally` | `fallbackPersist()`：CAS 失败即“未落库”，一律按 interrupted 补落 | 不信任 Reactor signal 的兜底（vmkill、cancel 等极端路径） |

## 9. Step 6：恢复通道（resumeQuery 三分支语义）

### 9.1 恢复初始化总览

恢复 = 一个新的执行器实例，从快照重建消息链后**照常进循环**（循环代码零改动）：

```java
/**
 * 从 PauseState 快照重建消息链并续跑：
 * 反序列化快照链 → 剥离链尾中断占位响应 → 按 resume 语义回灌工具结果
 * （空 query=本地重放 / 带 query=跳过占位）→ 追加澄清语 → 继续循环。
 */
private void initMessagesFromResume() {
    for (String row : resumeState.getMessagesJson()) {
        messages.addAll(serializer.fromJsonArray(row));
    }
    // 同一逻辑轮次：沿用快照的轮次号与 sessionId（落库/trace 归属一致）
    round = Math.max(resumeState.getCurrentRound(), 0);
    if (resumeState.getSessionId() != null && !resumeState.getSessionId().isBlank()) {
        this.sessionId = resumeState.getSessionId();
    }
    if (resumeState.getTotalPromptTokens() > 0) totalPromptTokens = resumeState.getTotalPromptTokens();
    if (resumeState.getTotalCompletionTokens() > 0) totalCompletionTokens = resumeState.getTotalCompletionTokens();

    stripTrailingPlaceholderResponses();                      // ① 剥离链尾占位
    appendResumeToolResponses(resumeState.getPendingToolCalls()); // ② 重放/跳过回灌

    if (resumeQuery != null && !resumeQuery.isBlank()) {      // ③ 非空消息 → 澄清语包装
        String original = resumeState.getQuery() == null ? "无" : resumeState.getQuery();
        messages.add(new UserMessage(RESUME_INTERRUPT_USER_PROMPT.formatted(original, resumeQuery)));
    }
    // 已被中断轮落库的部分（user/assistant 到剥离点为止）不再重复追加
    historySize = (int) messages.stream().filter(m -> !(m instanceof SystemMessage)).count();
}
```

### 9.2 剥离占位（防“同一 tool_call 被回答两次”）

中断现场入链的占位响应必须剥掉，替换为真实重放/跳过结果——OpenAI 协议下同一 `tool_call_id` 回答两次会 400。**识别规则必须保守：整批响应全部属于 pending 且全部带 `[占位]` 标记才剥离，单条不匹配立即停手**（真实工具结果永不误伤）：

```java
private void stripTrailingPlaceholderResponses() {
    Set<String> pendingIds = pendingToolCallIds(resumeState);
    if (pendingIds.isEmpty()) return;
    while (!messages.isEmpty()) {
        Message last = messages.get(messages.size() - 1);
        if (last instanceof ToolResponseMessage trm && isPlaceholderBatch(trm, pendingIds)) {
            messages.remove(messages.size() - 1);
            for (ToolResponse r : trm.getResponses()) {
                respondedToolCallIds.remove(r.id());   // 回滚记账
            }
        } else {
            break;
        }
    }
}

/** 仅当整批响应都属于 pending 的占位行时才可剥离（真实结果永不匹配） */
private static boolean isPlaceholderBatch(ToolResponseMessage trm, Set<String> pendingIds) {
    for (ToolResponse r : trm.getResponses()) {
        if (!pendingIds.contains(r.id())) return false;
        String data = r.responseData();
        if (data == null || !data.contains("[占位]")) return false;
    }
    return true;
}
```

### 9.3 三分支回灌（本方案的核心语义）

```java
/** 按恢复语义回灌 pending 工具调用：空 query=本地真实重放；带 query=跳过占位 */
private void appendResumeToolResponses(List<PendingToolCall> pending) {
    if (pending == null || pending.isEmpty()) return;
    boolean replay = resumeQuery == null || resumeQuery.isBlank();   // ★ 分歧点只在这一行
    List<ToolResponse> responses = new ArrayList<>();
    for (PendingToolCall ptc : pending) {
        if (replay) {
            // 分支1：本地真实重放 —— 重新执行工具，不重调 LLM，执行完继续循环
            ToolExecutionOutcome o = toolExecutor.executeSync(
                    new MergedToolCall(ptc.id(), ptc.name(), ptc.arguments()),
                    toolMap, params, conversationId(), sink, emitLock);
            if (o.success()) emit(AgentStreamEvent.toolEnd(o.name(), o.id(), o.result()));
            responses.add(new ToolResponse(ptc.id(), ptc.name(), o.result()));
        } else {
            // 分支2/3：不重放 —— 注入"已跳过"占位，把决策权交给模型
            responses.add(new ToolResponse(ptc.id(), ptc.name(),
                    TOOL_SKIPPED_PLACEHOLDER.formatted(ptc.name(),
                            ptc.arguments() == null ? "" : ptc.arguments())));
        }
    }
    appendToolResponses(responses);
}
```

两段提示词模板（恢复语义的“合同条款”，务必原样保留结构）：

```java
/** 带新消息恢复时的澄清语包装 */
static final String RESUME_INTERRUPT_USER_PROMPT = """
        [用户中断后返回]

        你之前的执行已被用户中断，以下是用户返回后发送的消息。
        请根据原始任务和用户消息之间的关系，判断用户意图并继续执行：
        - 如果用户是对原任务的细化或方向调整，请据此修正后续输出
        - 如果用户是提出新问题，请将其作为新任务处理
        - 如果用户只是让你继续，请无缝恢复执行

        原始任务：
        %s

        用户消息：
        %s
        """;

/** 带新消息恢复时，被跳过工具的占位响应（不重放，让模型按新指示自决策） */
static final String TOOL_SKIPPED_PLACEHOLDER = """
        工具执行被用户中断，用户返回后给出了新的指示。
        请根据用户补充的消息判断是否需要继续执行该工具，或调整方案。
        原工具调用：%s(%s)
        """;
```

为什么带消息时不重放工具？——用户既然说了新话，说明旧计划可能已经不对了；此时花真金白银重放工具（可能带副作用）是赌博。注入“已跳过”占位让模型知道“这个工具没跑成”，由它结合用户新消息决定重试、放弃还是换路。

## 10. Step 7：门面 API 与 HTTP 接入

### 10.1 Agent 门面（对称 API）

```java
public class ReactAgent {   // 目标 Agent 的门面类，方法一一对应
    /** 全新执行 */
    public Flux<AgentStreamEvent> stream(String query, RunnableParams params);

    /** 从中断快照恢复；resumeQuery 可空。无快照时返回 Flux.error */
    public Flux<AgentStreamEvent> resumeStream(String conversationId, String resumeQuery) {
        PauseState state = stateStore.get(conversationId);
        if (state == null) {
            return Flux.error(new IllegalStateException("没有可恢复的中断快照: " + conversationId));
        }
        // 恢复通道：复用快照里的 query/params，沿快照 sessionId/轮次续跑
        return newResumeExecutor(state, resumeQuery).run();
    }

    /** 可恢复中断（→ PAUSED + 快照） */
    public boolean interrupt(String conversationId, String message) {
        return taskManager.interrupt(conversationId, message);
    }
    /** 强制停止（丢状态，不产生 PAUSED） */
    public boolean stopStream(String conversationId) {
        return taskManager.stopTask(conversationId);
    }

    public boolean hasInterruptedState(String conversationId) { return stateStore.has(conversationId); }
    public boolean discardInterruptedState(String conversationId) { return stateStore.delete(conversationId); }
}
```

接入层注意（多租户/每请求重建 Agent 的架构）：
- **AgentTaskManager / PauseStateStore / SessionStore 必须是共享单例**（Spring `@Bean` 注入），Agent 实例可以每请求重建——否则 interrupt 找不到运行中任务、快照存进实例字段随实例消失。
- 恢复执行用**快照里的 params**（userId/toolParams），不要用本次请求新传的——快照轮次的工具参数必须与中断前一致。

### 10.2 HTTP 层：停止接口 + stream 自动恢复路由

```java
/** 中断（持久化快照，支持后续恢复） */
@GetMapping("/stop")
public R<Map<String, Object>> stop(@RequestParam String conversationId) {
    boolean interrupted = agent.interrupt(conversationId, "用户请求中断");
    boolean hasState = agent.hasInterruptedState(conversationId);
    return R.ok(Map.of("stopped", interrupted, "hasInterruptState", hasState));
}

/** 流式入口：④条路径，其中③是自动恢复路由 */
@PostMapping(value = "/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public Flux<ServerSentEvent<String>> stream(@RequestBody ChatRequest request) {
    // ...①recovery 断线续传 / ②takeOver 判定（见下）...

    // ③ 存在中断快照 → 恢复执行（本次 query 作为 resumeQuery，空 = 纯恢复）
    if (agent.hasInterruptedState(conversationId)) {
        source = agent.resumeStream(conversationId, userId, request.query(), ...);
    } else {
        // ④ 全新执行（query 必填）
        source = agent.stream(request.query(), conversationId, userId, ...);
    }
    // 注册进重放缓存、后台驱动（刷新不丢方案）
    return liveStreams.register(conversationId, userId, source).map(this::toSse);
}
```

**“恢复”对前端是透明的**：前端不需要知道“这是恢复还是新问”——同会话发消息时，后端发现有快照就自动走恢复通道，query 有内容就是带消息恢复，没内容就是纯恢复。

### 10.3 takeOver：新消息顶掉旧回答（可选，但强烈建议一起迁）

会话执行中用户又发了新消息——打断旧回答，但**丢弃断点**（旧回答已被新意图取代，半截内容保留在历史时间线里即可）：

```java
private void takeOverActiveStream(String convId) {
    boolean interrupted = agent.interrupt(convId, "新消息顶掉旧回答");   // 会产生快照
    // 等旧流真正停止（快照落库、注册表摘除），最多 3 秒
    for (int i = 0; i < 30 && liveStreams.isActive(convId); i++) {
        try { Thread.sleep(100); } catch (InterruptedException e) { break; }
    }
    if (liveStreams.isActive(convId)) {
        throw new ResponseStatusException(HttpStatus.CONFLICT, "当前会话回答尚未停止，请稍后重试");
    }
    agent.discardInterruptedState(convId);   // ★ 顶掉断点：防僵尸恢复（不变式5）
}
```

### 单元测试（参考本项目 `AgentLoopTest`，用 ScriptedChatModel 注入脚本化 LLM 响应）

| 用例 | 断言要点 |
| --- | --- |

| **非空 resumeQuery 恢复** | 工具**未被重放**（注入跳过占位）；链尾追加了澄清语包装的 user 消息（含原始任务+用户新消息）；模型自决策续跑 |

| 占位剥离保守性 | 链尾 ToolResponse 有一条 id 不在 pending / 不含 `[占位]` → 整批不剥离 |
| 并发 interrupt | 第二次 interrupt 返回 false；PAUSED 只发一次 |
| 快照 JSON 往返 | `toMap/fromMap` 往返后字段无损（不连库，直接测序列化） |

### 手工验收场景（按用户故事走一遍）

1. **停 → 空手回来**：长任务中途点停止 → 前端显示“已暂停” → 直接点继续 → 回答无缝接上，工具结果与不停止时一致。
2. **停 → 带澄清回来**：停止后发“改用柱状图” → 模型按新方向续跑，不重放旧工具。
3. **停 → 发全新问题**：走 takeOver/恢复通道，模型把新问题当新任务处理。
4. **停止后进程重启 → 恢复**：JDBC 快照生效（InMemory 版此场景必挂，属预期）。
5. **正常完成后发消息**：不得触发恢复（快照已在终态删除）。
6. **执行中直接发新消息**：takeOver 顶掉旧回答，旧断点被丢弃，新回答全新开始。

## 12. 常见坑与适配点

### 12.1 踩坑清单（每条都是本项目真实考虑过的点）

| # | 坑 | 对策 |
| --- | --- | --- |
| 1 | **收尾跑在打断线程**：dispose 后回调在 HTTP 线程执行，不是原订阅线程 | 共享状态全部 `synchronized(this)`/volatile；收尾代码不得依赖 ThreadLocal |
| 2 | **dispose 引发的 cancel 被当成 LLM 错误**，走重试逻辑 | `handleLlmError` 开头查 `interruptCtx.isInterrupted()` |
| 3 | **工具重放不幂等**：写库/发消息类工具重放 = 副作用翻倍 | 快照里明确记录“重放要求幂等”约束；对副作用工具优先建议用户带消息恢复（跳过占位分支） |
| 4 | **占位标记误伤**：真实工具结果恰好含 `[占位]` 字样 | 识别条件必须是“整批 id ∈ pending **且** 全部含标记”，单条不匹配即停（见 9.2） |
| 5 | **协议配对缺失**：下一轮 LLM 调用 400（孤立 tool_call / 同 id 回答两次） | 中断现场必补占位（8.2）；恢复时必先剥占位再回灌（9.2/9.3）——顺序不能反 |
| 6 | **恢复轮断档**：sessionId/round/tokens 没沿用快照，落库和 trace 变成新轮次 | `initMessagesFromResume` 开头三段沿用代码（9.1），不要“优化”掉 |
| 7 | **恢复轮重复落库**：中断轮已把 user/assistant 落库，恢复轮再全量追加 → 历史重复 | `historySize` 按恢复后的消息链重算（剥离点之后），落库时按它截断 original 视图 |
| 8 | **僵尸恢复**：任务 complete/error 后快照还在，下次发消息从旧断点复活 | 非 Paused 终态一律 `discardSnapshot()`；takeOver 等流停后显式丢弃 |
| 9 | **终态双发**：中断收尾与正常收尾并发赛跑，PAUSED/COMPLETE 各发一次 | `terminalEmitted`/`persisted` 两个 AtomicBoolean CAS 裁决（不变式4） |
| 10 | **极端路径不落库**：vmkill/cancel 等不走任何终态方法 | `doFinally(fallbackPersist)`：CAS 成功即说明没落过库，按 interrupted 补落 |
| 11 | **同会话并行执行**：恢复请求打断期间进来，两个执行器同写一个会话 | `registerTask` putIfAbsent 互斥，冲突抛异常上层转 409 |
| 12 | **Jackson 反射序列化 PauseState**：挂框架类型、升级即崩 | 手工转 Map（见 7.3） |

### 12.2 框架适配点（目标 Agent ≠ Spring AI 时）

| 本项目依赖 | 适配方向 |
| --- | --- |
| Reactor `Flux/Sinks/Disposable` | 换成目标框架的流式机制（如 SSE Emitter + 阻塞队列）。唯一硬要求：**能按 conversationId 定位任务并取消**，没有等价物就自己包一层（执行线程 + volatile cancel 标志） |
| Spring AI `Message/AssistantMessage/ToolResponseMessage` | 换目标框架消息类型；**序列化交换格式保持 OpenAI role JSON 不变**（Step 7.2），转换器一对即可 |
| `ChatModel.stream(Prompt)` | 任意 LLM 客户端的流式调用；只需保证 chunk 里能取到增量文本与 tool_call 分片 |
| `ToolCallback` / `ToolCallingChatOptions` | 目标框架的工具注册机制；关键是 tool_call 有稳定 id、执行器支持同步执行（恢复重放用 `executeSync`） |
| MySQl 方言的 JDBC DDL | 换目标库方言（PostgreSQL 把 `ON DUPLICATE KEY UPDATE` 换成 `ON CONFLICT ... DO UPDATE`） |

### 12.3 与“刷新不丢”方案的边界（谁负责什么）

| 场景 | 归属方案 | 快照是否产生 |
| --- | --- | --- |
| 用户刷新页面/断网 | 刷新不丢（重放缓存 + recovery 续传） | 否——执行根本没停 |
| 用户点停止 → 回来继续 | **本文**（interrupt → resume） | 是 |
| 执行中发新消息顶掉旧回答 | 本文 takeOver + 刷新不丢的注册表摘除 | 产生后**立即丢弃** |
| LLM 错误重试耗尽 | 本文（errorTerminal + 删快照） | 产生于 doFinally 兜底，属异常路径 |

两套方案的公共地基是**执行与连接解耦 + 事件流**（前置检查 A）；在它之上，“刷新不丢”管**连接的生死**，“打断恢复”管**任务的生死**。
