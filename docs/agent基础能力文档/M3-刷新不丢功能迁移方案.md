# “刷新不丢”功能迁移方案（从 0 到 1 移植指南）

> 目标读者：要把本项目的“刷新不丢”（流式断点续传 + 执行/连接解耦）能力移植到**另一个 Agent 项目**的开发者。
> 参考实现：本项目 M3 里程碑，核心讲解见《如何实现流式断点续传？.md》。
> 阅读前提：目标 Agent 是 Spring Boot 后端 + 浏览器前端；Agent 执行过程产出流式事件。

---

## 1. 问题与思路（一分钟版）

**现象**：Agent 回答一个复杂问题要跑几十秒，期间用户刷新页面 / 断网 / 切走再回来，答到一半的内容直接丢掉。

**根因**：Controller 把 Agent 的 `Flux` 直接交给 HTTP。数据从上游（Agent）流向下游（前端），而前端一断开，cancel 控制信号**逆流而上**传回执行循环，Agent 被取消——执行和连接绑死，连接的生死决定了执行的生死。

**思路**：在前端和 Agent 框架之间加一层“直播服务器”式转发：

| 比方 | 实现 |
| --- | --- |
| 主播只管产出，不关心有没有人看 | Agent 流注册后立即**后台驱动**（`connect()`），与 HTTP 订阅无关 |
| 直播服务器缓存 + 分发 | 每个事件**编上序号**存进 `replay` 缓存，随时向晚来的订阅者重放 |
| 观众中途退场直播不停 | 前端断开只是取消它自己的订阅，执行照常跑、事件照常进缓存 |
| 回来看回放补进度再接直播 | 重连带 `startSeq`：先瞬时补发缺失事件，再续实时尾流 |

**“刷新不丢”= 三层保障叠加**：

1. 刷新期间执行不停 → 事件进缓存（后端解耦）；
2. 刷新回来 → 探测 + 从第 1 号事件**全量重放**（重放缓存，不是重新生成，瞬间完成）；
3. 流已结束才刷新 → 从**落库历史**渲染。

---

## 2. 总体架构与四条不变式

```
前端浏览器                Controller                LiveStreamRegistry              Agent
   │  POST /agent/stream      │  register(convId, source)     │                        │
   │ ───────────────────────► │ ─────────────────────────────►│  index().replay()      │
   │                          │ ◄───── 可重放SSE流 ◄───────────│  .connect() 立即后台驱动 │
   │ ◄──── SSE(id=序号) ────── │        （订阅同一流）           │───────────────────────►│
   │                          │                               │                        │
   │  × 刷新/断网（连接断）      │        HTTP 订阅被取消          │   执行照常，事件照常入缓存 │
   │                          │                               │                        │
   │  POST recovery+startSeq  │  attach(convId, startSeq)     │                        │
   │ ───────────────────────► │ ─────► skipUntil 检票补发 ────►│                        │
```

迁移时**不可走样**的四条不变式：

1. **执行与连接解耦**：Agent 流必须是“注册即后台驱动”的冷流——`register()` 内 `connect()`，有没有 HTTP 订阅都在跑。这是全部方案的基础。
2. **事件编号从 1 起自增**，写进 SSE 的 `id:` 字段（SSE 标准的 Last-Event-ID 惯例）。序号是断点位置的**唯一依据**。
3. **一个会话同一时间只有一条进行中的流**（注册表按 conversationId 存一条），流终止按 **key+value 匹配**摘除，防止同会话紧接着开下一轮时误删新流。
4. **当前轮终态才落库**：进行中的轮次不在历史里，只能靠重放缓存恢复；流结束后刷新走历史接口。

## 3. 第 0 步：迁移前置检查

动手前确认目标 Agent 满足以下三点，缺什么补什么：

| # | 检查项 | 不满足时的补救 |
| --- | --- | --- |
| A | Agent 执行过程能表达为**事件流**（冷 `Flux<Event>`，订阅才执行），事件至少覆盖：思考增量 / 正文增量 / 工具开始 / 工具结束 / 错误 / 终态 | 若现在是阻塞式返回，先改造执行循环为 Sinks/Flux 产出；若框架不可改，退而求其次只保“历史不丢”，放弃“刷新期间不中断” |
| B | 每轮问答有稳定的 **conversationId**（会话窗口 ID，跨刷新不变），且流式接口的请求体里能带上 | 前端生成 UUID（如 `conv_<uuid>`）随请求携带即可 |
| C | 技术栈：后端 Spring Boot 且能返回 `Flux<ServerSentEvent>`（WebFlux 或 MVC + Reactor），前端能用 `fetch` 消费 SSE | MVC 同样可用（返回 `SseEmitter` 时重放缓存逻辑同构，需自行缓存事件列表） |

## 5. Step 2：后端核心——LiveStreamRegistry（重放转发层）

这是整个方案的心脏，一个会话一条记录，先定义接口再给内存实现。

### 5.1 接口

```java
public interface LiveStreamRegistry {

    /** 注册并立即后台驱动：返回可重放的 SSE 流（事件已带序号） */
    Flux<ServerSentEvent<AgentStreamEvent>> register(String conversationId, Long ownerUserId,
                                                     Flux<AgentStreamEvent> source);

    /** 接回进行中的流：先补发序号 >= startSeq 的缓存事件，再续实时尾流；无流返回 null */
    Flux<ServerSentEvent<AgentStreamEvent>> attach(String conversationId, long startSeq);

    boolean isActive(String conversationId);

    /** 全部进行中流的会话 ID（列表接口批量标记 streaming 用） */
    Set<String> activeConversationIds();

    /** 进行中流的属主用户（无流时为 null，恢复请求校验权限用） */
    Long ownerOf(String conversationId);
}
```

### 5.2 内存实现（单机版，完整代码）

```java
@Component
public class InMemoryLiveStreamRegistry implements LiveStreamRegistry {

    /** 一条进行中的流：可重放 SSE 流 + 属主用户 */
    private record LiveStream(ConnectableFlux<ServerSentEvent<AgentStreamEvent>> replay,
                              Long ownerUserId) {}

    private final Map<String, LiveStream> live = new ConcurrentHashMap<>();

    @Override
    public Flux<ServerSentEvent<AgentStreamEvent>> register(String conversationId, Long ownerUserId,
                                                            Flux<AgentStreamEvent> source) {
        AtomicReference<LiveStream> self = new AtomicReference<>();
        ConnectableFlux<ServerSentEvent<AgentStreamEvent>> replay = source
                // ① 编号：事件序号写进 SSE id 字段，从 1 起。前端按 id 记游标，重连带 startSeq
                .index((i, evt) -> ServerSentEvent.builder(evt).id(String.valueOf(i + 1)).build())
                .doFinally(signal -> {
                    LiveStream entry = self.get();
                    if (entry != null) {
                        // ③ 按 key+value 摘除：同会话紧接着开下一轮时不会误删新注册的流
                        live.remove(conversationId, entry);
                    }
                })
                // ② 重放缓存：晚来的订阅者先收到全部历史缓存，再续实时尾流
                .replay();
        LiveStream entry = new LiveStream(replay, ownerUserId);
        self.set(entry);
        live.put(conversationId, entry);
        // ④ 开播：注册完立即驱动，与有没有 HTTP 订阅无关——执行与连接解耦的基础
        replay.connect();
        return replay;
    }

    @Override
    public Flux<ServerSentEvent<AgentStreamEvent>> attach(String conversationId, long startSeq) {
        LiveStream entry = live.get(conversationId);
        if (entry == null) {
            return null;
        }
        long from = Math.max(startSeq, 1);
        // 检票：startSeq 之前的一律拦住，从 startSeq 号开始放行。
        // startSeq=1 即全量补发（刷新恢复），= lastSeq+1 即增量续传（断线重连），一个方法通吃。
        return entry.replay().skipUntil(sse -> sse.id() != null && Long.parseLong(sse.id()) >= from);
    }

    @Override
    public boolean isActive(String conversationId) { return live.containsKey(conversationId); }

    @Override
    public Set<String> activeConversationIds() { return Set.copyOf(live.keySet()); }

    @Override
    public Long ownerOf(String conversationId) {
        LiveStream entry = live.get(conversationId);
        return entry == null ? null : entry.ownerUserId();
    }
}
```

**逐行讲解（迁移时最容易做错的四个点）**：

- `index((i, evt) -> ... id(String.valueOf(i + 1)))`：`i` 从 0 起，SSE id 从 1 起。前端游标、`startSeq`、`skipUntil` 全围绕这个序号。
- `replay()` 在 `index()` **之后**：缓存的是“已编号”的事件，重放时序号原样带给前端，保证重放流和实时流的游标同一套。
- `doFinally` 摘除必须在 `replay()` **之前**挂在源流上（流终止即触发，含 cancel/error）；`live.remove(key, value)` 双参重载是幂等防线。
- `connect()` 是“开播”动作，没有它整个流不会跑（冷流直到被订阅才执行）。register 返回的 `replay` 和前端订阅的是**同一个**可重放流。

### 6.2 Controller 主干（recovery + 全新执行两条路径）

```java
@PostMapping(value = "/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public Flux<ServerSentEvent<String>> stream(@RequestBody ChatRequest request) {
    String conversationId = StringUtils.hasText(request.conversationId())
            ? request.conversationId() : "conv_" + UUID.randomUUID();
    Long userId = authService.getCurrentUserIdOrNull();   // 按你的鉴权体系取当前用户
    if (userId == null) throw new ResponseStatusException(HttpStatus.UNAUTHORIZED, "请重新登录");

    // ① 恢复请求：不新起执行，接回进行中的流（断线/刷新续传的唯一入口）
    if (Boolean.TRUE.equals(request.recovery())) {
        requireActiveOwned(conversationId, userId);       // 无流 404 / 非属主 403
        long startSeq = request.startSeq() == null ? 0 : request.startSeq();
        Flux<ServerSentEvent<AgentStreamEvent>> attached = liveStreams.attach(conversationId, startSeq);
        if (attached == null) {
            throw new ResponseStatusException(HttpStatus.NOT_FOUND, "当前会话没有进行中的回答");
        }
        return attached.map(this::toSse);
    }

    // ② 全新执行：query 必填 → 拿到 Agent 冷流 → 流级兜底 → 注册后台驱动
    if (!StringUtils.hasText(request.query())) {
        throw new ResponseStatusException(HttpStatus.BAD_REQUEST, "query 不能为空");
    }
    Flux<AgentStreamEvent> source = agent.stream(request.query(), conversationId, userId);
    final String convId = conversationId;
    source = source.onErrorResume(e -> Flux.just(            // 内核异常也转成事件，保证流正常收尾
            AgentStreamEvent.error("STREAM_ERROR", safeMessage(e), null),
            AgentStreamEvent.complete(0, 0, convId, "")));

    Flux<ServerSentEvent<AgentStreamEvent>> registered = liveStreams.register(conversationId, userId, source);
    return registered.map(this::toSse);
}

/** 恢复请求前置校验：流存在且当前用户是属主 */
private void requireActiveOwned(String convId, Long userId) {
    if (!liveStreams.isActive(convId)) {
        throw new ResponseStatusException(HttpStatus.NOT_FOUND, "当前会话没有进行中的回答");
    }
    Long owner = liveStreams.ownerOf(convId);
    if (owner != null && !owner.equals(userId)) {
        throw new ResponseStatusException(HttpStatus.FORBIDDEN, "无权访问该会话的流");
    }
}

/** 转成字符串 SSE：id（序号）必须透传，event = 事件类型小写，data = 事件 JSON */
private ServerSentEvent<String> toSse(ServerSentEvent<AgentStreamEvent> sse) {
    try {
        ServerSentEvent.Builder<String> b = ServerSentEvent
                .builder(objectMapper.writeValueAsString(sse.data()))
                .event(sse.data().getType().name().toLowerCase());
        if (sse.id() != null) b.id(sse.id());
        return b.build();
    } catch (Exception e) {
        return ServerSentEvent.builder("{\"type\":\"ERROR\",\"message\":\"事件序列化失败\"}")
                .event("error").build();
    }
}
```

## 7. Step 4：终态落库与历史查询（“流结束后刷新”场景的保障）

刷新时如果流**已经跑完**，注册表里没有流了，内容必须从库里来。需要两个落库时机 + 一组查询接口。

### 7.1 两张最小表

### 7.2 两个落库时机（对齐本项目内核 AgentLoopExecutor 的做法）

```java
// 时机一：执行启动时先落一行 conversation（status=running）
sessionStore.initConversation(id, conversationId, sessionId, userId, query);

// 时机二：流终止时落终态（completed / interrupted / error 三种都算终态）
```

## 8. Step 5：全局异常两处必改（否则前端状态机会错乱）

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    /** 坑一：SSE 端点上 Controller 同步抛的 ResponseStatusException 会被兜底 Exception
     *  处理器吞成 HTTP 200 + code:500，前端按状态码分支（404=流已结束拉历史）就失效了。
     *  必须单独处理、透出真实状态码。 */
    @ExceptionHandler(org.springframework.web.server.ResponseStatusException.class)
    public ResponseEntity<R<Void>> handleResponseStatus(
            org.springframework.web.server.ResponseStatusException e) {
        return ResponseEntity.status(e.getStatusCode()).body(R.fail(e.getStatusCode().value(), e.getReason()));
    }

    /** 坑二：前端断开（刷新/关页）后服务端往死连接写事件抛 IOException，属预期现象，
     *  识别出客户端断开后降为 warn，不刷 ERROR 堆栈。 */
    @ExceptionHandler({AsyncRequestNotUsableException.class, IOException.class})
    public ResponseEntity<R<Void>> handleClientAbort(Exception e) {
        if (isClientAbort(e)) {
            log.warn("客户端已断开，SSE 连接中止（回答仍在后台执行，重连可续传）");
            return null;
        }
        return ResponseEntity.status(500).body(R.fail("IO 异常：" + e.getMessage()));
    }
    // isClientAbort：沿异常链找 ClientAbortException / AsyncRequestNotUsableException，
    // 以及消息含 reset / broken pipe / aborted / 远程主机强迫关闭 的 IOException（Windows 常见裸 IOException）
}
```

## 9. Step 6：前端 API 层（fetch 消费 SSE + 同步 abort 句柄）

```js
/** 发起一条 SSE 流（首发 / recovery 续传共用）。同步返回 abort 句柄。 */
export function openAgentStream(body, onEvent, handlers = {}) {
  const ctrl = new AbortController()
  ;(async () => {
    try {
      const resp = await fetch('/agent/stream', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json', /* 你的鉴权头 */ },
        body: JSON.stringify(body),
        signal: ctrl.signal
      })
      if (!resp.ok) {
        const err = new Error(await readErrorMessage(resp))
        err.status = resp.status                    // 状态码要带上：前端 404/403/409 分支靠它
        handlers.onError?.(err); handlers.onClose?.(); return
      }
      const reader = resp.body.getReader()
      const decoder = new TextDecoder('utf-8')
      let buffer = ''
      while (true) {
        const { done, value } = await reader.read()
        if (done) break
        buffer += decoder.decode(value, { stream: true })
        buffer = buffer.replace(/\r\n/g, '\n')      // 统一换行符再按空行切事件
        let idx
        while ((idx = buffer.indexOf('\n\n')) >= 0) {
          const evt = parseSseEvent(buffer.slice(0, idx))
          buffer = buffer.slice(idx + 2)
          if (evt) onEvent(evt)
        }
      }
      handlers.onClose?.()
    } catch (err) { handlers.onError?.(err); handlers.onClose?.() }
  })()
  return { abort: () => ctrl.abort() }
}

/** 解析单个 SSE 块：id 就是断点游标，必须读出来传给 onEvent */
function parseSseEvent(raw) {
  let event = 'message', id = ''
  const dataLines = []
  for (const line of raw.split('\n')) {
    if (line.startsWith('event:')) event = line.slice(6).trim()
    else if (line.startsWith('id:')) id = line.slice(3).trim()
    else if (line.startsWith('data:')) dataLines.push(line.slice(5).trimStart())
  }
  if (!dataLines.length) return null
  let payload
  try { payload = JSON.parse(dataLines.join('\n')) }
  catch { payload = { type: 'TEXT', content: dataLines.join('\n') } }
  return { event, data: payload, id }
}

export const getAgentStreamStatus = (cid) => request.get('/agent/stream/status', { params: { conversationId: cid } })
export const listSessions = (page = 0, size = 10) => request.get('/session/list', { params: { page, size } })
export const getSessionDetail = (cid) => request.get(`/session/${encodeURIComponent(cid)}`)
```

> 用 `fetch` 而不是 `EventSource`：`EventSource` 不支持 POST 请求体，而流式问答的 query/recovery/startSeq 都在 POST body 里。

## 10. Step 7：前端全局流表 + 游标去重（“页内切换不丢”）

核心思想：**流不绑在页面上**。所有进行中的流放进一张模块级全局表，切会话/新建会话只是视图切换，流继续跑、继续往消息对象上追加。

```js
// cid -> { cid, aiMsg, question, controller, lastSeq, retries, paused }
const liveStreams = new Map()

/** 打开一条流（首发/恢复共用）：注册进 liveStreams 并发起请求 */
function openStream(cid, aiMsg, body, question = '') {
  const entry = { cid, aiMsg, question, controller: null, lastSeq: 0, retries: 0, paused: false }
  liveStreams.set(cid, entry)
  entry.controller = openAgentStream(body, onStreamEvent(cid, entry), streamHandlers(cid, entry))
  return entry
}

/** SSE 事件消费：第一件事是游标防重 */
function onStreamEvent(cid, entry) {
  return ({ data, id }) => {
    if (id) {
      const seq = Number(id)
      if (!Number.isNaN(seq)) {
        if (seq <= entry.lastSeq) return      // ★ 补发与实时尾流有一瞬间交叠，序号 <= 已记录的直接丢弃
        entry.lastSeq = seq                   // ★ 游标推进：重连时 startSeq = lastSeq + 1
      }
    }
    const timeline = entry.aiMsg.timeline
    switch (data.type) {
      case 'THINKING': /* 追加/新建 thinking 项 */ break
      case 'TEXT':     /* 追加/新建 text 项     */ break
      case 'TOOL_START': /* toolCallId 建 running 工具卡片 */ break
      case 'TOOL_END':   /* 按 toolCallId 回填 result+completed */ break
      case 'ERROR':    timeline.push({ type: 'error', message: data.message }); break
      case 'COMPLETE': entry.aiMsg.streaming = false; break
    }
  }
}

/** 流结束：identity 守卫清理（防止误清新一轮的流），恢复界面状态 */
function finishStream(cid, entry) {
  if (liveStreams.get(cid) === entry) liveStreams.delete(cid)
  entry.aiMsg.streaming = false
}
```

## 11. Step 8：断线自动重连（增量）与进页恢复（全量）

### 11.1 自动重连：带游标的增量续传

```js
function streamHandlers(cid, entry) {
  return {
    onError(err) {
      // 分支 1：服务端已无进行中的流（断开期间跑完了）→ 按已结束处理，拉最终历史
      if (err.status === 404) {
        finishStream(cid, entry); loadConversation(cid); refreshConversationList(); return
      }
      // 分支 2：403/409/400 等被明确拒绝 → 展示错误，收尾
      if ([400, 401, 403, 409].includes(err.status)) { /* 展示 err.message，finishStream */ return }
      // 分支 3：收到过事件才自动重连（增量续传），退避 1s/2s/3s 最多 3 次
      if (entry.lastSeq > 0 && entry.retries < 3) {
        entry.retries++
        setTimeout(() => {
          if (liveStreams.get(cid) !== entry) return            // 已被新一轮替换，放弃
          openAgentStream(
            { conversationId: cid, recovery: true, startSeq: entry.lastSeq + 1 },  // ★ 从下一个事件续
            onStreamEvent(cid, entry), streamHandlers(cid, entry)
          )
        }, 1000 * entry.retries)
        return
      }
      // 分支 4：本地主动 abort 不算错误；其余彻底断开，展示“连接中断”
    },
    onClose() { /* 兜底收尾 + 刷新侧栏 */ }
  }
}
```

### 11.2 进页面恢复：探测 + 从 1 号全量补发（“刷新不丢”的主场景）

页面刷新后本地渲染状态全没，但**游标也不用记**——直接从第 1 个事件全量重放，`replay` 缓存是现成的，瞬间补到当前进度再接实时流：

```js
async function tryResumeOnLoad(cid) {
  if (liveStreams.has(cid)) return
  let active = false
  try { active = !!(await getAgentStreamStatus(cid))?.active } catch { return }
  if (!active) return                       // 没有进行中的流 → 走正常历史加载
  const s = sessions[cid]
  const aiMsg = { role: 'ai', timeline: [], streaming: true }   // 挂一个实时气泡
  s.messages.push(aiMsg); s.streaming = true
  openStream(cid, aiMsg, { conversationId: cid, recovery: true, startSeq: 1 })  // ★ 全量补发
}

// 调用点：进入页面 onMounted 时；点开历史会话 loadConversation 末尾（无本地流时）；
// 首个事件未到时历史接口可能还没有该轮记录（终态才落库），直接追加实时气泡即可
```

三个入口统一走它：**刷新/关页重开**（onMounted → 按 URL 里的 conversationId 打开会话）、**页内点历史会话**（openConversation）、**切走再切回**（本地有流则直接复用 `liveStreams` 里的消息对象，根本不发请求）。

## 12. Step 9：侧栏“生成中”标记

- 会话列表 VO 带 `streaming` 字段（Step 4.3 的批量探测）；
- **发送瞬间就本地置 streaming=true 并刷新侧栏**（不等服务端落库），用户切走后立刻能在侧栏看到“生成中”并点回来；
- 流结束（COMPLETE/onClose）后再次刷新侧栏归位。

## 13. 验收清单（迁移完成的判定标准）

| # | 场景 | 预期 |
| --- | --- | --- |
| 1 | 回答进行中刷新页面 | 内容不丢：进页探测到 active → 从 1 号事件瞬时全量重放到当前进度，再续实时 |
| 2 | 回答进行中断网数秒后恢复 | 自动重连 ≤3 次，`startSeq=lastSeq+1` 增量续传，文本无重复无缺口 |
| 3 | 回答进行中切到别的会话再切回 | 不发请求，直接渲染 `liveStreams` 里的实时消息，输出从未中断 |
| 4 | 回答进行中关页，数分钟后重开 | 若仍在跑 → 场景 1；若已跑完 → 404 分支拉落库历史，完整渲染 |
| 5 | 回答进行中点开侧栏历史会话 | 同样探测 + 恢复（或复用本地流） |
| 6 | 同一会话连发两次 | 第二条顶掉第一条，不出现两条并行流（有 takeOver 需求见 §15） |
| 7 | 用户 A 恢复用户 B 的会话流 | 403 拒绝（ownerOf 校验） |
| 8 | 流结束后刷新 | 历史接口渲染，timeline 完整（thinking/tool/text 都在） |
| 9 | 服务端重启 | 内存注册表清空：刷新后 status.active=false，走历史；进行中那轮只有半截问题行（单机内存版的已知边界，可接受） |
| 10 | 全程观察后端日志 | 客户端断开只有一行 warn，无 ERROR 堆栈刷屏 |

## 14. 已知边界与升级路线

- **单机内存边界**：`InMemoryLiveStreamRegistry` 的进行中流只活在收到首发请求的那个 JVM 里。多实例部署时恢复请求打到别的实例会 404、探测查不到、可能同题跑两遍。升级路线是把注册表换成 Redis Stream / Redis Pub-Sub 的分布式版（事件缓存与订阅搬进 Redis），接口签名不变，业务层无感。
- **重放缓存的生命周期 = 流的生命周期**：流结束后缓存即被 GC，所以“流结束后刷新”完全依赖 Step 4 的落库。**两边都不能省**。
- **游标存内存即可**：本项目刷新场景直接用 `startSeq=1` 全量重放（重放是瞬间的，不必省），所以 lastSeq 不需要写 localStorage；若会话很长导致全量重放体积大，再把游标持久化到 localStorage 并在进页恢复时改为 `startSeq=lastSeq+1`。

## 15. 可选扩展（本项目的 M3 增强项，迁移时可后置）

- **takeOver（新消息顶掉旧回答）**：会话执行中来了新消息 → 打断旧执行 → 轮询 ≤3s 等流停 → 丢弃旧断点 → 全新执行；停不下来返回 409。挂进 Controller 的“② 全新执行”分支之前即可。
- **pause/resume（中断断点续跑）**：`/agent/stop` 打断时把执行现场（消息链快照）持久化；下次发消息（可为空 query）从快照续跑而不是从头再来。依赖 Agent 内核能导出/恢复执行现场，改动在 Agent 层，不影响本方案的转发层。
- 两者与“刷新不丢”共享同一张注册表和同一套状态码语义（404=无流、403=非属主、409=顶掉超时），建议在同一期落地。

## 16. 常见坑速查表

| 症状 | 根因 | 解法 |
| --- | --- | --- |
| 刷新后内容丢一半 | 忘了 `connect()` 后台驱动，或 recovery 重新生成了回答 | register 内 connect；recovery 分支**绝不**新起执行 |
| 重连后文本重复拼接 | 补发与实时尾流交叠，没去重 | `seq <= entry.lastSeq` 直接丢弃（Step 7 ★） |
| 前端收不到 404，重连死循环 | SSE 端点异常被兜底处理器吞成 200+500 | ResponseStatusException 单独透传（Step 8 坑一） |
| 断开后日志刷 ERROR 堆栈 | 死连接写事件抛 IOException 未降噪 | isClientAbort 识别后降 warn（Step 8 坑二） |
| 同会话下一轮流被误摘 | doFinally 用 `remove(key)` 单参 | 改 `remove(key, value)` 双参幂等摘除 |
| 重放流序号丢失 | `replay()` 放在了 `index()` 之前 | 先 `index()` 后 `replay()` |
| startSeq=0 或负数炸掉 | skipUntil 永远不满足 | `Math.max(startSeq, 1)` 兜底 |
| 双击连发开了两条流 | 首事件未到时无保护 | 前端 `lastSeq===0` 时禁止连发；后端同会话 isActive 时拒绝/顶掉 |
| 历史里当前轮是空气泡 | 进行中轮次被提前落库 | 终态才落库；前端对空 timeline 轮跳过渲染，交给 recovery |
