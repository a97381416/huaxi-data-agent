## 一、核心概念题（必考级）

### Q1. 什么是上下文工程（Context Engineering）？为什么 Agent 需要它？

**一句话**：管理"每次 LLM 调用时模型能看到什么"的工程。上下文窗口是稀缺资源，Agent 多轮对话 + 工具调用会把历史撑得越来越长，导致三个问题：**贵（token 按量计费）、慢（长 prompt 推理慢）、差（超窗口报错或中间信息被稀释）**。

展开：上下文工程的本质不是"删历史"，而是**"压缩不丢信息"**——把不值那么多 token 的历史段移出工作链、归档保存、留个取回凭证，模型需要时再取。

### Q2. Agent 的记忆一般分几层？

**一句话**：至少两层——模型读的（working）和用户看的（original）不能混。

- **working 链**：真正发给 LLM 的消息列表，会被压缩污染（含 uuid 占位符）
- **original 链**：只增不减的"真相链"，落库后是用户翻历史看到的完整对话
- 往外还有 **OffloadStore 归档层**：被压掉的原文按 uuid 存 DB，构成第三份

**追问点：为什么不直接一份？** 拿压缩后的链当原始对话落库，用户翻历史会看到 `[已压缩 offload，uuid=xxx]` 占位符，体验崩坏；反过来拿原始链每次全量发给模型，压缩就白做了。

### Q3. 长对话 Agent 的记忆方案有哪几种？各自优缺点？

| 方案 | 做法 | 缺点 |
|---|---|---|
| 全量历史 | 每轮把所有历史塞给模型 | token 线性膨胀，很快爆窗口 |
| 滑动窗口 | 只保留最近 N 条 | **信息真丢了**，模型答不出"之前那个数字" |
| 摘要记忆 | 定期把老历史 LLM 摘要成一段 | 有损压缩，细节（精确数字）会丢 |
| **offload 压缩+取回** | 换成小抄+归档，模型按需取回 | 实现复杂，要多一次存储和工具 |

**答出层次感的说法**：前三种都是"一次性决策"——删了就删了。第四种把压缩变成**可逆操作**，小抄保留预览（工具名+参数前100字+结果前200字），归档保留全文，等于在"上下文预算"和"信息完整性"之间加了个惰性加载层。

### Q4. 什么时候触发压缩？阈值怎么定？

**一句话**：每轮 LLM 调用前检查，**消息数 ≥100 或估算 token ≥90K，任一满足即触发**（OR 关系）。

- 90K ≈ 128K 窗口 × 0.7，留 30% 余量给本轮工具结果和回复
- token 用估算不用精确 tokenizer：中文 1.5 字符/token、其他 4 字符/token，误差 ±20% 无妨——因为它只服务"到没到阈值"这个粗粒度决策
- **加分点**：为什么要双阈值？消息数防"条数多但每条短"（协议开销），token 数防"条数少但单条巨大"（大结果集）。单看任何一个都会漏掉另一种膨胀模式

### Q5. 为什么最近 50 条是"禁区"，任何策略都不碰？

**一句话**：近期上下文是模型当前推理的直接依据，压它等于边干活边抽走脚手架。

展开：压缩永远只动历史区（链头到 `size-50` 之间）。而且禁区边界处理很讲究：一个工具段如果**骑在边界上**（一半在历史区一半在禁区），必须**整段放弃而不是切一半**——切一半会让禁区里的 tool 响应失去配对的 assistant，协议直接 400。

## 二、方案深挖题（区分度题）

### Q6. 讲讲三个压缩策略（L1/L2/L4）各适合什么场景？

**一句话**：按"信息密度"分层打包——L1 收工具流水、L2 收单条巨型消息、L4 收纯聊天旧轮次。

- **L1 工具段整段 offload**：连续工具响应 ≥6 条且 ≥5000 token → 整段归档，换成"工具名+参数前100字+结果前200字"的小抄。9800→约100 token，压 ~99%
- **L2 大消息原地换预览**：单条 >2000 token → 换成前 200 字预览+uuid 标记。实测单条压掉 8517 token
- **L4 LLM 摘要**：完整历史轮次 ≥5000 token → 调 LLM 写摘要（用户原话保留），一次最多 3 轮

**追问：为什么顺序是 L1→L2→L4？** 成本递增。L1/L2 是纯规则零成本，L4 要花 LLM 调用。先试便宜的。

### Q7. 为什么"先触发者赢"，一次只压一层？

**一句话**：一次只压一层，压完下轮重新评估，避免一次压太狠、也方便定位问题。

展开：如果一次把 L1+L2+L4 全跑完，可能出现"过度压缩"——把还需要的信息也压掉了；而且每层独立可测（10 个单测全绿的基础），出问题能快速定位是哪层。这本质是个**保守迭代**的设计：每轮压一点，token 曲线逐步回落而不是断崖。

### Q8. 为什么 assistant(toolCalls) 和 tool 响应必须成对？破坏了会怎样？

**一句话**：OpenAI 协议规定 tool 响应必须通过 tool_call_id 关联到发起调用的 assistant 消息，孤儿 tool 响应 = **400 报错**，对话直接中断。

所以三条铁律：

- L1 整段移除时**把前导 assistant 一起带走**（配对整体消失，合法）
- L2 遇到带 toolCalls 的 assistant **直接跳过**（哪怕它 5000 token）
- L4 只摘"完整收尾的轮次"

**面试亮点说法**：这叫"协议配对安全高于压缩收益"——宁可少压一条大消息，不冒协议崩溃的风险。这是所有"看起来能多压一点"的优化都不敢越的红线。

### Q9. 压缩后模型怎么找回原文？为什么用 uuid 标记而不是把全文放检索？

**一句话**：替换文本里嵌 `uuid=xxx` 标记 + 一句话指引，模型看到标记后自己决定要不要调 `context_reload` 工具取回（最长 32000 字符截断）。

设计细节（都是考点）：

- **小抄自带预览兜底**：多数情况模型看前 200 字就够了，不取回也不影响干活——取回是惰性的
- **防幻觉文案**：取不到时返回"未找到，**请勿编造原文**"——实测显著降低模型瞎编率
- **每请求新建工具实例**绑定 conversationId，不能做单例——串对话就串归档
- 相比 RAG 检索方案：uuid 是**精确寻址**不需要向量库，代价是依赖模型"主动意识到要看原文"

### Q10. 压缩过程中出错怎么办？

**一句话**：压缩是增益功能不是关键路径，**任何异常只 warn 不阻断**。

分层容错：

- LLM 摘要失败 → 跳过该轮，用原链继续
- 归档写库失败 → warn，小抄里的预览还在，只是事后取不回
- 整个 compact 抛异常 → catch 住，本轮对话照常走

**加分点**：还有个开关兜底 `enableCompaction=false`，关掉后行为和迁移前完全一致——**可逆性**是这类"侵入主循环"功能的设计底线。

### Q11. 怎么让压缩收益跨请求复利？

**先澄清术语**：这里的"跨请求"指**同一个对话（conversationId）的多次请求**，不是"新对话继承旧对话"。三个名词先对齐：

| 名词 | 含义 |
|---|---|
| 对话（conversationId） | 用户点开的那个聊天窗口，可以跨很多天、发很多条消息，始终是同一个对话 |
| 请求（一次执行） | 用户发一条消息触发的完整过程：加载历史 → ReAct 循环 → 落库退出 |
| 复利的"跨请求" | **同一对话**的第 N+1 次请求，继承第 N 次请求压缩后的链 |

**一句话**：落库存两个视图，下次加载时**优先加载 working（压缩后）链**，全删全插；original 只做增量追加。

效果举例（同一个对话，连续三天用）：第 1 天干到 130 条 / 95K，压缩到 40 条 / 30K 并落库；第 2 天开局只背 30K，加本轮新增 50K 共 80K——**没到阈值（100 条 / 90K），这个请求一次压缩都不用触发**，第 1 天省下的 65K 在第 2 天的每次 LLM 调用里都省着。反例：若只存/只加载原始链，第 2 天开局就要背 95K、把压过的内容重压一遍，第 3 天直接爆 128K 窗口——这就是"单次收益"和"复利"的差别。

**边界（易误解点）**：另开新对话 = 新 conversationId = **空白开局**，只有 system prompt + 本条消息。旧对话的消息和 offload 归档都不继承——归档按 conversationId 隔离存储，新对话里传旧对话的 uuid 调 context_reload 会得到"未找到"。这是故意设计：对话间内容隔离，防泄漏也防上下文污染。

**面试区分点**：对话内记忆（压缩/摘要/offload 取回，M7 讲的）≠ 跨对话记忆（用户偏好、历史结论带进新对话——需要用户级记忆表或会话级 RAG，是另一个独立子系统）。面试时主动区分这两者很加分。

如果只想单请求内生效，working 用完即弃、只落 original 一份即可——方案文档给了两种选法。

### Q12. token 估算为什么不引 tokenizer？

**一句话**：估算只做两个决策（触发判断+段大小比较），±20% 误差不改变决策结果；换来零依赖、零词典维护、纳秒级速度。

对比：tokenizer 精确但要带模型词典（几十 MB）、版本绑定、慢两个数量级。**判断依据是"用途决定精度要求"**——同样的估算值不能拿去计费或审计。

## 三、场景设计题（大厂高频）

### Q13. 【设计题】让你从 0 设计一个长对话 Agent 的上下文管理，说说思路？

答题骨架（STAR 式）：

1. **先问三个问题**：工作链在哪个对象、每轮 LLM 调用在哪发起、工具清单怎么注入——答案齐了，方案就是"拷内核包 + 插三行 + 实现一个存取接口"
2. **触发**：每轮 LLM 调用前内联检查，双阈值 OR（条数/token），没超就直通零开销
3. **策略**：分层（规则 offload → 单条替换 → LLM 摘要），先触发者赢，只动历史区、保护区从链尾倒数
4. **安全**：协议配对铁律（assistant+tool 成对进退）、压缩异常只 warn
5. **闭环**：原文归档+uuid 标记+context_reload 工具，压缩不丢信息
6. **持久化**：original/working 双视图，working 跨请求复利
7. **验收**：调小阈值联调（msg-threshold: 6）、token 曲线对比、问"当时那个数字"验证取回、伪造 uuid 验证不编造

### Q14. 【设计题】压缩后用户问"之前查出来的精确数字"，怎么保证答对？

三层保障：

1. **预览层**：小抄保留结果前 200 字，简单问题直接看预览回答
2. **取回层**：uuid 标记+context_reload 工具，模型自己判断需要就取全文（32K 截断）
3. **提示层**：L4 摘要 prompt 硬性要求"数字、表名、字段名原样保留"；reload 失败返回"请勿编造原文"

验收方法：压缩后专门问"当时查询结果里的具体数字"，观察模型调 context_reload 取回并正确作答——这是闭环验收的必测项。

### Q15. 【设计题】怎么验证你的压缩没把对话压坏？

M7 的验收清单（可以直接背）：

- 日志出现 `[compaction] L1/L2/L4 生效`
- 压缩前后 LLM 实际 prompt token 对比（L2 单次实测压 8517）
- 压缩轮之后对话继续正常——**无 400、无 tool_call_id 配对报错**（协议没坏）
- 问压缩前的细节 → context_reload 取回成功
- 伪造 uuid → "未找到"且不编造
- 关开关重启 → 行为与迁移前一致（可逆）
- 落库检查 original 视图无压缩标记污染、working 为压缩后链

## 四、关联高频考点（文档带出来的通用知识）

### Q16. ReAct 循环是什么？压缩点为什么插在它里面？

ReAct = Reason + Act 交替：模型思考→调工具→看结果→再思考→…→出最终答案。每轮循环 = 一次 LLM 调用 + 工具回灌。

压缩点必须在**"上轮工具已回灌、本轮 LLM 未调用"之间**——这是唯一时序确定的检查点，太早会漏掉刚回灌的结果，太晚本轮已经把膨胀的上下文发出去了。这也是 M7"压缩内联进循环、不做 Hook 体系"的理由：**单检查点加抽象只添复杂度**。

### Q17. Function Calling 的完整协议流程？

1. 开发者随请求注入工具清单（name/description/参数 schema）
2. 模型决定调工具 → 返回 assistant 消息携带 `tool_calls`（id+name+arguments）
3. 客户端执行工具，把结果作为 **role=tool、tool_call_id=id** 的消息回灌
4. 模型看到结果继续推理，可多轮，直到出最终文本

**Q8 的配对问题就出在第 3 步**——每个 tool 消息必须能通过 tool_call_id 找到发起者。上下文压缩一旦只删一半，协议非法。

### Q18. "Lost in the Middle" 是什么？和上下文压缩有什么关系？

LLM 对长上下文首尾信息的利用好于中段（U 型注意力）。所以：重要的放头尾（system 在头、保护区保尾）、低值的中间历史正是压缩优先动刀的区域——**压缩不只是省钱，也在提升模型对剩余信息的有效利用率**。

### Q19. 上下文压缩 vs RAG，什么场景选哪个？

- **RAG**：知识在**对话之外**（文档库、知识库），靠检索按需注入，天然开放域
- **offload 压缩**：知识在**对话之内**（自己产生的历史），靠 uuid 精确寻址，不需要向量化
- 混合用：历史压缩用 offload，外部知识用 RAG。M7 方案的取舍是**精确性**——uuid 直取不用猜相关性，代价是依赖模型主动取回

### Q20. Agent 场景下抑制幻觉有哪些手段？（结合本档）

- **不丢信息**：压缩可逆（归档+取回），从源头减少"模型忘了只能编"
- **防编造提示**："请勿编造原文"写进工具返回——失败路径的提示词和成功路径一样重要
- **硬信息保真**：摘要 prompt 强制保留数字/表名/字段名原样
- **预览兜底**：归档失败时小抄里仍有前 200 字，降级优雅（graceful degradation）
