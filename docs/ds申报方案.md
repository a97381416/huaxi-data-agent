在 Agent 侧**不建议重新做一个完整表单来“镜像” OA 的字段**。更合理的做法是：**让 Agent 成为一个“填单助手”，在对话中按 OA 表单的结构逐步引导用户提供信息，最终生成一份符合 OA 接口要求的结构化数据**。如果确实需要一个可视化界面给用户确认或修改，再提供一个**精简的确认表单**，而不是把 OA 的全部参数原样搬过来。

### 为什么不直接复刻 OA 表单

OA 系统里的参数、下拉选项、文件上传控件是**面向“人工在网页上操作”设计的**。直接搬到 Agent 侧会带来几个问题：

- 下拉选项的枚举值可能很多，且依赖 OA 侧的业务规则（如部门、项目类型、审批流分支），Agent 侧硬编码这些选项容易与 OA 不同步。
- 文件上传在 Agent 对话中本身就不自然——用户无法在聊天框里“选一个本地文件上传到 OA”。
- 如果 Agent 侧做一个和 OA 一模一样的表单，那用户为什么还要用 Agent？直接去 OA 填就好了。Agent 的价值在于**降低填报负担**，而不是把表单换个地方再填一遍。

### 推荐的设计：对话式引导 + 结构化提交

把填报过程拆成三个阶段，Agent 在不同阶段承担不同角色：

**阶段一：信息收集（对话为主）**

Agent 根据从 OA 获取的表单字段定义（字段名、类型、是否必填、枚举范围），在对话中逐项或分组向用户提问。对于下拉选择类字段，Agent 不需要把全部选项丢给用户，而是先理解用户意图，再匹配到 OA 的合法值。例如用户说“我是研发部的”，Agent 自动映射到 OA 下拉选项里的“研发中心/技术部”对应值。对于文件上传，Agent 可以引导用户提供文件，然后在提交环节通过 OA 的上传接口或预签名 URL 完成传输，而不是在对话里直接“传文件”。

**阶段二：预填与校验**

很多申报信息其实可以从用户身份或历史数据中自动获取。参考智能填报系统的做法，Agent 可以对接校内或企业内的主数据，按字段映射关系自动填充可获取的内容。同时，Agent 在收集过程中就做校验：必填项是否齐全、格式是否正确、跨字段逻辑是否冲突。发现缺失或冲突时，当场提示用户补充或确认。

**阶段三：确认与提交**

所有信息收齐后，Agent 生成一份**只读的填报摘要**（或一个极简的确认表单，只展示将要提交的关键字段和值），让用户过目确认。确认后，Agent 通过 OA 的 API 或 RPA 将结构化数据写入 OA 系统。如果 OA 没有 API，才考虑用 RPA 模拟网页操作，但那是执行层的事，Agent 侧仍然只负责“把数据准备好”。

### 如果一定要有可视化表单

那就做一个**动态生成的确认表单**，字段来自 OA 的表单 schema，但只用于**展示和微调**，不作为主要输入方式。技术上可以用 JSON Schema 描述字段，前端根据 schema 渲染控件：字符串用文本框，枚举用下拉框，文件用上传组件。Agent 先把收集到的值填入，用户只需要检查、改几个错，然后提交。这样既保留了表单的直观性，又没有让用户从头填一遍。

### 文件上传的处理要点

文件在 Agent 侧不应该作为“表单字段”来设计。正确的做法是：Agent 在对话中确认用户要上传哪个文件，然后通过 OA 提供的文件上传接口（或对象存储预签名 URL）把文件传到 OA 侧，拿到文件 ID 或 URL 后，再作为申报数据的一个字段值提交。如果 OA 没有文件上传 API，才退回到让用户在 OA 网页上手动上传，Agent 只负责提醒和记录。

**一句话总结**：Agent 侧的“表单”应该是**对话流程 + 结构化数据**，而不是 OA 网页表单的复制品。用户通过对话提供信息，Agent 负责映射、校验、预填，最后生成符合 OA 接口规范的数据提交。可视化表单只在确认环节作为辅助出现。

关键认知：**不要把“填报”当成一次性的表单提交，而是当成一个多轮、可增量、可回退的会话过程。** 下面按交互设计给出具体方案。

## 1. 先建立“填报任务”这个会话状态对象

Agent 侧需要一个显式的任务状态，而不是靠对话历史隐式记忆。建议结构如下：

text

```
task = {
  task_id,
  oa_form_schema,          // 从 OA 拉取的字段定义（名称/类型/必填/枚举/分组）
  fields: {
     field_key: { value, status: empty|filled|inferred|invalid, source: user|inferred|default }
  },
  files: {
     file_key: { uploaded: bool, file_id, local_ref, status }
  },
  current_group,           // 当前正在填的分组
  pending_questions: []
}
```



有了这个状态，Agent 每一轮都能知道“还差什么、下一步问什么、哪些可以自动推断”，也支持用户随时说“我改一下第三个字段”或“先跳过这个”。

## 2. 字段按“分组 + 优先级”分批推进，不要一次抛全部

OA 表单往往有几十个字段，一次性列出来用户直接放弃。做法是：

- **按 OA 表单的语义分组**（如基本信息、项目内容、预算、附件），一次只推进一个分组。
- 组内再分优先级：**必填且无法推断的**先问；**可从上下文推断的**（如申报人、部门、日期）自动填好让用户确认；**选填的**最后问或折叠。
- 每完成一组，给一个简短小结：“基本信息已填好：项目名 X、负责人 Y、周期 Z。接下来填预算部分。”

这样用户每一轮只面对 2–4 个问题，认知负担可控。

## 3. 多字段的提问策略：能推断就不问，能批量就批量

- **可推断字段自动填**：申报人、部门、当前日期、项目编号规则等，直接从用户身份或上下文取，填入后标注“已自动填写，可修改”。
- **关联字段合并问**：比如“项目起止时间”一次问，“预算总额和分项”一起问，减少轮次。
- **枚举字段不让用户背选项**：用户自然语言说“我们是做图像识别的”，Agent 匹配到 OA 枚举里的合法值再确认，而不是让用户从 20 个下拉项里挑。
- **长文本字段给模板/示例**：项目简介这类，给一个结构提示（背景/目标/成果），用户口述，Agent 整理成文再让用户确认。

## 4. 多文件上传：单独设计一个“附件清单”流程，和字段填报解耦

这是最容易出问题的地方。文件不适合混在字段问答里，建议**独立成一个附件收集阶段**：

1. **先列清单**：从 OA schema 里读出附件要求（如“营业执照”“项目计划书”“预算表”），一次性列给用户：“本次需要上传 3 个附件：A、B、C。你可以逐个发给我，也可以打包发。”
2. **逐个接收与确认**：用户每发一个文件，Agent 识别它对应哪个附件项（按文件名/用户说明），调 OA 上传 API 拿到 file_id，标记该项已上传，并回显“A 已上传（文件名 xxx），还剩 B、C”。
3. **支持批量与乱序**：用户一次发多个文件时，Agent 依次匹配；匹配不上的问一句“这个文件对应哪一项？”
4. **文件与字段分离**：上传只负责拿 file_id，最终提交时再把 file_id 填入对应字段值。这样即使用户中途换文件，也只需重传该项，不影响其他字段。
5. **上传失败可重试**：每个文件有独立状态，失败项单独提示重传，不阻塞其他项。

## 5. 提供“随时查看进度 / 随时改”的能力

用户在任何时刻可以说“还差什么”“把项目名改成 XX”“附件 B 我重发一下”。Agent 基于任务状态对象直接响应，而不是重新走一遍流程。这需要在系统提示里明确：**当前任务状态是唯一事实来源，每轮先读状态再决定问什么。**

## 6. 最后一步：生成提交预览，确认后调 API

所有字段 filled、所有必传附件 uploaded 后，Agent 生成一份**结构化预览**（分组展示字段值 + 附件清单），明确告诉用户“确认后我将提交到 OA”。用户确认或修改后，Agent 组装 payload 调 OA 提交 API，返回结果（成功/单号/失败原因）。

如果 OA 提交 API 对字段格式有要求（日期格式、枚举 code、文件字段传 file_id 还是 URL），在组装层做一次映射和校验，不要把这些细节暴露给对话。

## 7. 交互形态的选择

- **纯对话**适合字段不太多、用户愿意口述的场景，实现成本最低。
- 如果字段确实很多（比如 30+），建议**对话 + 一个动态确认面板**：对话负责收集和推断，面板根据任务状态实时渲染“已填/待填/附件”清单，用户可点选修改。面板只做展示和微调，输入主通道仍是对话。
- 不建议在 Agent 侧复刻一个完整 OA 表单——那等于把 OA 的负担原样搬过来，失去了 Agent 的意义。

**不能，而且不建议这么做。** 从提交 API 的请求体反推 `form_config`，最多只能拿到“字段名”和部分“数据类型”，但拿不到你设计交互最需要的几样东西：**字段分组、必填校验、下拉枚举的完整选项、附件项的语义归属**。这些信息在提交接口的 schema 里通常不存在，或者即使存在也是残缺的。

### 提交 API 能反推出什么、推不出什么

| form_config 需要的信息                         | 提交 API 能否反推 | 原因                                                        |
| :--------------------------------------------- | :---------------- | :---------------------------------------------------------- |
| 字段名 / key                                   | ✅ 可以            | 请求体里能看到                                              |
| 数据类型（string/number/array）                | ⚠️ 部分可以        | JSON 类型能看出，但“这是日期还是普通字符串”分不清           |
| **字段分组**（基本信息/项目内容/预算）         | ❌ 不能            | 提交接口不关心 UI 分组，它只收扁平或嵌套的字段值            |
| **必填规则**                                   | ❌ 通常不能        | 提交接口可能不校验，或者在服务端做隐式校验，schema 里看不到 |
| **枚举选项完整列表**                           | ❌ 不能            | 请求体只带用户选中的那个值，不会带所有可选值                |
| **附件项语义**（哪个附件对应哪一项、是否必传） | ❌ 不能            | 提交接口可能只收 file_id 数组，不区分“计划书”和“预算表”     |

参考飞书/钉钉等主流 OA 的 API 设计，正规做法是**单独提供一个“获取表单定义”的接口**来返回结构信息。例如飞书 Base 的 `+form-detail` 会返回 `questions[].title`、`questions[].type`、`questions[].required`、`select.options` 等，并明确要求“提交前按返回结构构造值，不要猜题目类型或选项”。钉钉的 OA 审批也有“获取表单 schema”的接口，返回控件的 `required`、`options` 等。这说明**表单结构信息和提交数据是两个不同层面的东西**，提交接口本来就不承载定义信息。

### 你真正该找的接口

既然你前面说过“OA 侧现在都有现成的 API 接口”，建议确认一下有没有以下这类接口：

- **获取表单 schema / 模板详情**：返回字段列表、类型、是否必填、枚举选项、附件控件等。
- **获取审批定义详情**（如果 OA 有审批流概念）：部分 OA 的审批定义接口会包含表单控件定义。

如果确实没有这类接口，退而求其次的方案是：**从 OA 前端页面或已有的表单配置里导出一份静态 `form_config.json`，手工维护**，而不是从提交 API 反推。因为从提交接口反推出来的东西，恰好缺了你设计交互最关键的“分组”和“枚举”，用起来会非常别扭——Agent 既不知道先问哪一组，也不知道下拉框该给用户哪些选项。

**一句话结论**：提交 API 是“收答案的”，不是“出题目的”。`form_config` 应该来自 OA 的表单定义接口（优先）或手工维护的配置（兜底），不要指望从提交请求体里还原出来。

## 路径一：从前端页面逆向出 form_config（最推荐）

前端写死的表单，恰恰意味着**定义信息都在前端代码/页面结构里**，这是你能拿到的最完整来源。做法：

1. **抓页面 DOM / 前端 bundle**：打开 OA 填报页，从渲染出的表单里提取每个控件的 label、类型、`required` 标记、下拉 `option` 列表、文件上传控件。
2. **看前端请求的静态配置**：很多前端表单会从某个 JS/JSON 配置渲染，或者在 bundle 里有 `formFields = [{key, label, type, required, options}]` 这类结构，直接搜出来最省事。
3. **走一遍填报流程抓提交 payload**：填一个测试单，抓提交请求体，和页面字段对照，确认每个 key 的映射关系（这是验证用，不是主要来源）。

产出一份 `form_config.json`，包含分组、字段 key、label、类型、必填、枚举、附件项。这份东西**人工核一遍**，作为 Agent 侧的权威配置。

## 路径二：如果前端也拿不到（内网、混淆、无源码）

退化为**手工维护**：

- 由业务方或实施人员对照 OA 页面，逐字段整理成 `form_config.json`。
- 在 OA 表单变更时同步更新，并**加版本号**。
- 用一次真实提交的 payload 做**校验**：`form_config` 里声明的字段集合，必须和实际 payload 的 key 集合对得上（缺了/多了就报警）。

这不是理想方案，但现实里很多企业内部 OA 集成就是这么做的。关键是**把这份配置当成受控资产**，而不是散落在提示词里。

## 路径三：用"提交 payload + 页面截图"双源对齐

如果只能拿到提交接口，那么：

- **提交 payload** 给你字段 key、数据类型、嵌套结构、文件字段形态（是 file_id 数组还是 URL）。
- **页面截图/人工走查** 给你 label、分组、必填星号、下拉选项、附件项语义。

两者**做一次映射表**，才能补齐 form_config。单靠 payload 不够，单靠页面也不够（不知道提交时的 key 长什么样）。

## 路径四：运行时兜底——提交失败回捞

`form_config` 不完美时，靠提交反馈纠偏：

- 提交 API 返回字段级校验错误时，把错误信息映射回字段，提示用户修正。
- 记录每次失败原因，反过来补全 form_config 的必填/格式规则。
- 这只作兜底，不能替代初始配置。

## 先分清哪类变化会波及 Agent

| OA 侧变化                        | 是否影响 Agent   | 影响的层次                         |
| :------------------------------- | :--------------- | :--------------------------------- |
| 新增/删除/重命名字段             | 是               | form_config 字段定义               |
| 改必填规则                       | 是               | form_config 的 required            |
| **数据字典/枚举选项增删**        | 是（但可自动化） | options                            |
| 改字段分组/页面布局              | 是               | groups（影响交互顺序，不影响提交） |
| 改字段 key / payload 结构        | 是               | payload_path 映射（最危险）        |
| 改校验规则（格式、长度、跨字段） | 是               | 校验逻辑                           |
| 纯 UI 样式、文案                 | 否               | 无影响                             |

结论：**真正需要改的只有两类——结构定义（form_config）和提交映射（payload 组装）**。交互流程、状态机、skill 里的策略原则基本不用动。所以问题不是“要不要维护”，而是**把易变的东西集中到一处、尽量自动同步、并让变更可控可发现**。

## 降低维护成本的几种做法

**1. 把 form_config 变成“唯一易变点”，Agent 代码与流程不感知字段**

Agent 的流程代码只操作抽象的 `field_key`，所有字段名、枚举、必填、映射都从 form_config 读。这样 OA 改字段时，只改配置文件，不改代码、不改 skill。这是最基础的隔离。

**2. 枚举/数据字典优先走“运行时拉取”，不要硬编码**

数据字典是最常变的部分。如果 OA 有字典接口（哪怕只是下拉选项的查询接口），Agent 在填该字段时实时拉取，而不是写进 form_config。没有接口的话，至少让 form_config 的 options 支持“引用字典 key”，由同步任务更新，而不是散落在配置里。**原则：能运行时拿的，绝不静态存。**

**3. 建立“变更检测”而不是“被动等用户报错”**

既然拿不到 schema 接口，就用**采样比对**来发现变化：

- 定期（或每次提交后）抓一次 OA 表单页面 / 一次测试提交的 payload，与现有 form_config 做 diff。
- 字段 key 集合变了、必填标记变了、枚举值变了 → 告警，人工确认后更新配置。
- 这一步可以用轻量脚本做，不必上大系统。

这样 OA 改了你**能第一时间知道**，而不是等 Agent 提交失败才暴露。

**4. 提交层做“宽容映射 + 失败回捞”**

- payload 组装用映射表，字段缺失/多余时给出明确错误，而不是静默丢数据。
- 提交 API 返回字段级错误时，回写到对应字段，提示用户修正，同时记录到“疑似规则变化”日志。
- 这层兜底能让小改动不立刻导致 Agent 不可用，给你争取修配置的时间。

**5. 版本化 + 灰度**

form_config 带 version，和 OA 表单版本对齐。OA 改版时，新配置先灰度给少量用户，验证通过再全量。出问题可快速回滚到旧配置。

## 一个务实的结论

**“OA 改，Agent 就得改”这件事无法完全消除，因为 OA 没有给你 schema 接口，Agent 侧的结构定义本质上是一份需要同步的副本。** 能做的是：

- 把需要同步的范围**收敛到一份 form_config**（而不是散在提示词、代码、工具里）；
- 能运行时拉的（字典、选项）**不静态存**；
- 用**变更检测**让同步从“被动发现”变成“主动告警”；
- 用**宽容映射 + 失败回捞**让同步延迟不至于直接导致不可用。

如果哪天 OA 愿意提供表单定义接口（哪怕只读），这套维护成本会立刻降一个数量级。在那之前，**推动 OA 侧开放一个只读的 schema/字典接口，是比在 Agent 侧做更多适配更根本的解法**——值得作为需求提给 OA 团队。
