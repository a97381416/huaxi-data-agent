## 1. 背景与范围

data-agent 当前已有 M-E1「被驳回→改→重提」闭环（declarant-workflow 技能），但申报方的**首次资料填报**（选项目→选阶段→按节点类别填报→暂存→提审）尚无能力。本设计补齐该闭环，即扩展计划中的 M-E2 资料填报组。

**范围内**：首次填报、续填草稿、暂存、提审（单节点会签）。
**范围外**：驳回后重提（M-E1 已覆盖）、多级协同审核配置、项目 CRUD（M-E3）、预警（M-E4）。

## 2. 业务系统调研结论

调研对象：`zrkj-aigov-huaxi`（后端 yudao）+ `zrkj-aigov-huaxi-ui`（前端）。

### 2.1 业务流程链路（业务端现状）

```text
申报方工作台(/doc-workbench) / 项目档案列表(/project-manage/project-archive)
   └→ 项目详情(/doc/project-archive/detail)
        ├─ 大阶段横向进度条(圆点: 已传/总数)      ← GET /doc/project/detail → majorPhases[]
        ├─ 左侧子阶段导航(缩进列表+统计)           ← GET /doc/project/phase-children
        └─ 右侧 资料备案/审核记录 Tabs
             └─「一般/特殊文件上传」→ 资料填报页(/doc/ledger/edit) ★核心
                  ├─ 区A: 项目下拉(status=1 进行中, filterable)
                  ├─ 区B: 按「文件节点」分节的表格(每行=一个文件类别条目)
                  │    列: 文件状态|文件(正文+附件≤9)|文件摘要*|是否涉密|备注|提供人|提供时间|...
                  ├─ 底部: [取消] [暂存] [提交审核]
                  │    暂存    = create/update → status=0 草稿(半成品合法)
                  │    提交审核 = 先落库 → 弹 SubmitApprovalDialog → submitForReview
                  └→ 提审弹窗: 提交说明* + 部门树选择 + 审核人多选弹框
                              + 常用审核人chips(点击即填) → POST /doc/ledger/submit-for-review
```

### 2.2 数据层级与台账状态机

```text
doc_project（项目，status=1 进行中）
 └─ doc_phase（阶段树：parent_id，根=大阶段，子=子阶段）
      └─ doc_phase_node（阶段↔文件节点绑定，required 是否必填）
           └─ doc_file_category（预设文件类别：summary 默认摘要/reference_example）
                ↑ 填报实例 ↓
doc_ledger（台账：项目×子阶段×每轮提交一条，批次号 DOC-{项目编码}-{阶段编码}-{序号}）
 └─ doc_file_entry（类别行：文件状态/文件/摘要/备注/提供人/提供时间/涉密/审核状态）
      └─ doc_file_entry_history（STAGE 暂存 / ARCHIVE 归档）
```

同一用户同项目同子阶段**草稿唯一**（`GET /doc/ledger/get-draft` 检测）。

```text
台账状态： 0 草稿 ──submitForReview──→ 1 审批中 ─┬─ 通过 → 2 已通过
                                              ├─ 驳回 → 3 已驳回 ──resubmit(M-E1)──→ 1
                                              └─ 部分通过 → 4（行级锁定，M-E1 领地）
行审核状态 audit_status： 0 草稿 / 1 待审核 / 2 已通过(锁定) / 3 已驳回
```

### 2.3 关键 API 清单（agent 工具将转发的主后端接口）

| 用途 | method url | 关键参数/返回 |
|---|---|---|
| 我的项目+阶段统计 | GET `/doc/workbench/my-projects` | pageSize=99；phases[].uploadedCount/entryTotal/missingCount |
| 项目详情(大阶段) | GET `/doc/project/detail` | projectId → majorPhases[]（含四态统计） |
| 子阶段列表 | GET `/doc/project/phase-children` | projectId, majorPhaseId |
| 阶段编码解析 | GET `/doc/ledger/resolve-phase` | phaseCode → phaseId/phaseName |
| 节点+预设类别 | GET `/doc/ledger/get-nodes` | phaseId → nodes[]{nodeId,nodeName,required,presetCategories[]{name,code,summary}} |
| 我的草稿台账 | GET `/doc/ledger/get-draft` | phaseId, projectId → ledgerId 或 null |
| 台账详情 | GET `/doc/ledger/get` | id → nodeGroups[].fileEntries[]（草稿态合并预设类别） |
| 建台账草稿 | POST `/doc/ledger/create` | {phaseId, projectId, fileEntries[], isSpecial} → ledgerId |
| 改台账草稿 | PUT `/doc/ledger/update` | 同上+id（fileEntries 全删重插） |
| **提审** | POST `/doc/ledger/submit-for-review` | {ledgerId, needNext, nextNodes[{nodeName, approvalStrategy, assigneeIds}], variables{opinion,...}} |
| 常用审核人 | GET `/doc/recommend/assignees` | {projectId, subStageId, limit:8} → 按子阶段聚合推荐 |
| 部门树 | GET `/system/dept/simple-list` | 前端直调用 |
| 部门人员 | GET `/system/user/page-for-ignore-auth` | deptId（含兼职部门），前端直调用 |
| 文件上传 | POST `/admin-api/infra/file/upload` | 前端直传（既有先例） |

提审弹窗字段映射：提交说明→`variables.opinion`；部门→选人范围；审核人→`nextNodes[].assigneeIds`（默认 nodeName=部门审核、approvalStrategy=countersign 会签）；常用审核人→recommend 接口。

### 2.4 字典枚举

| 项 | 值 |
|---|---|
| 文件状态 notApplicable（project_file_status） | **-1 待上传 / 0 已取得 / 1 空缺 / 2 不涉及 / 3 其他** |
| 台账 status / 行 audit_status | 0 草稿 / 1 审批中(待审核) / 2 已通过 / 3 已驳回 / 4 部分通过(仅代码) |
| 是否涉密 doc_file_confidential | 0 否 / 1 是 |
| 条目来源 source | 0 系统预设 / 1 用户自定义 |

### 2.5 与 agent 口径的差异（重要）

| 口径 | 来源 | 规则 |
|---|---|---|
| **本设计（D1 拍板）** | agent 侧 | 摘要**全状态必填**；已取得必须已传文件 |
| edit.vue 首次填报 | `ledger/edit.vue:933-943` | 仅校验"已取得→摘要必填"；不校验已取得必须有文件；非已取得不校验摘要 |
| detail.vue 驳回重提 | `ledger/detail.vue:1195-1225` | 非待上传(-1)一律摘要必填 |
| 主后端 | DocLedgerServiceImpl | **无上述任何校验**（仅状态/归属/草稿唯一性） |

建议：M-E2 落地后，把 D1 口径补进 `DocLedgerServiceImpl.submitForReview` 服务端硬校验，业务前端跟随统一（可另行立项，不阻塞本技能）。

## 3. 总体设计

### 3.1 架构分层（一句话）

**面板管逐类快填（状态+文件+摘要全行内完成），对话管意图与追问，卡片管全景与确认。**

### 3.2 技能定位与边界

```text
                    ┌────────────── declarant-fill (本技能) ──────────────┐
                    │                                                       │
  (无台账) ─create→ 草稿0 ──fillFileEntry(暂存,可反复)──→ 草稿0              │
                    │   │                                                   │
                    │   └─submitLedgerForReview(W2确认)→ 审批中1 ─────────────┼─→ PM审核
                    │                                                       │
                    ├─ 审批中1: 阻断填报，提示等待/看待办                       │
                    ├─ 已通过2: 阻断，只读浏览                                 │
                    └─ 已驳回3 / 部分通过4: 引导切换 declarant-workflow ────────┘
                                  （M-E1: getTaskDetail→patch→stageDraft→resubmit）
```

两技能**协议同构、技能分治**：patch 协议、确认卡协议、W1/W2 分级完全一致；触发词错开（本技能：填报/首次申报/补资料/新填/提交审核；M-E1：驳回/重提/待办）。

### 3.3 关键交互决策

1. **写路径全走工具+确认令牌**；提审表单的读数据（部门树/部门人员/常用审核人）前端直调主平台（D5）。
2. **提审交互两张卡**：`reviewConfig`（配置表单）在前、复用 `confirm` 卡（diff+影响面）在后。原因：确认令牌绑定全参数 payload SHA-256，必须先收集完配置再首轮出计划领令牌，否则二轮必然 PAYLOAD_MISMATCH；5 分钟 TTL 只覆盖"看 diff 点确认"。
3. **面板=本地草稿态→攒批通知**：行内控件（下拉/输入/上传）全是本地编辑，点「已配置完，通知助手」一条结构化消息批量注入，agent 校验→patch→fillFileEntry 暂存→返回新 fillPanel 刷新面板。与 reviewConfig 卡"表单收集→结构化注入"同构，保持单路径原则（LLM 单通道，无前端直调写接口）。

## 4. 工具层设计

### 4.1 工具清单（6 新 + 3 复用）

| 工具 | 类型 | 后端 REST | 说明 |
|---|---|---|---|
| `listMyProjects(keyword?)` | R | `/doc/workbench/my-projects` | 我的项目+各阶段完整度，projectPicker 卡数据源 |
| `listPhaseTree(projectIdOrName)` | R | `/doc/project/detail` + `phase-children`(逐大阶段) | 大阶段(四态) + 子阶段树，phaseTree 卡数据源 |
| `listFillNodes(projectIdOrName, phaseIdOrNameOrCode)` | R | `resolve-phase`+`get-nodes`+`get-draft`+`get` | **合并视图**：节点×预设类别×已填值×草稿检测，fillBoard+fillPanel 数据源 |
| `listReviewOptions(projectId, subStageId, deptId?)` | R | `/doc/recommend/assignees` + `/system/dept/simple-list`（deptId 时 `user/page-for-ignore-auth`） | reviewConfig 卡首屏数据 |
| `fillFileEntry(projectIdOrName, phaseIdOrName, patches[])` | **W1** | `get-draft` 无则 `create`，有则 `get`→merge→`update` | 批量增量暂存，自动建/续草稿 |
| `submitLedgerForReview(定位, patches?, submitRemark, nextNodes)` | **W2** | 首轮=预检+计划+令牌；二轮(ledgerId, confirmToken)=执行 `POST /doc/ledger/submit-for-review` | 两段式 |
| `cancelConfirm` / `todoWrite` / `tool_search` | 复用 | — | 与 M-E1 同一套 |

工具实现模板：W1 照抄 `StageDraftTool` + `PatchMerger`；W2 照抄 `ResubmitLedgerTool`（ConfirmTokenService + ActionPlanCache + confirmCard）。参数尾部 userId/token/tenantId/conversationId 由内核注入，LLM 不可伪造。

### 4.2 patch 协议（与 declarant-workflow 完全同构）

```json
[
  {"node":"立项文件","category":"项目建议书","field":"notApplicable","value":"0"},
  {"node":"立项文件","category":"项目建议书","field":"summary","value":"已过会，批复文号xxx"},
  {"node":"立项文件","category":"项目建议书","field":"fileUrl","value":"/admin-api/.../xx.pdf"},
  {"node":"立项文件","category":"项目建议书","field":"fileName","value":"项目建议书.pdf"},
  {"category":"规划许可证","field":"description","value":"天然缺项：未涉及规划区域"}
]
```

- **field 白名单**：`notApplicable / summary / description / fileUrl+fileName / attachmentUrl+attachmentName / provider / providerTime(yyyy-MM-dd) / isConfidential+visibleRoleIds`
- **定位**：`category` 必填；同名多行加 `node` 消歧；歧义时工具返回候选清单让用户挑
- **禁止自造 selector**："全部改成不涉及"必须先展开清单确认再逐条 patch
- ID（projectId/phaseId/ledgerId/entryId）一律字符串原样传（19 位雪花精度）

### 4.3 返回载荷：fillPanel（W1/W2 及 listFillNodes 统一携带）

```json
"fillMode": "active",
"fillPanel": {
  "phaseName": "可研批复办理",
  "draftLedgerId": "1946...",
  "docNumber": "DOC-HX-2026-018-100003-001",
  "ledgerStatus": 0,
  "stats": {"todo": 5, "done": 9},
  "nodes": [{
    "nodeId": "...", "nodeName": "批复文件", "required": true,
    "entries": [
      {"entryId":"...","category":"可研批复文件","status":0,
       "currentFile":{"fileName":"批复.pdf","uploadTime":"11-02","fromDraft":true},
       "summary":"已出正式批复","done":true},
      {"entryId":"...","category":"用地批准书","status":-1,
       "currentFile":null,"summary":null,"done":false,
       "defaultSummary":"用地批准文件复印件"}
    ]
  }]
}
```

`done` 判定：已取得→有文件+有摘要；空缺/不涉及/其他→有摘要。已通过(auditStatus=2)/被驳回(3)的行不进面板（锁定行只在 fillBoard 只读展示）。提审成功后返回 `"fillMode":"closed"` → 前端移除面板。

## 5. 技能 SOP（SKILL.md 骨架，七步）

```text
第0步 意图定位：用户带全上下文("填华西二期100001-002的资料")→跳步直达第3步；
      只说"我要填报"→从第1步走起。
第1步 选项目：listMyProjects → 项目选择卡 → 用户点名/报序号；项目唯一命中可直接确认跳过。
第2步 选阶段：listPhaseTree → 阶段树卡（大阶段进度→子阶段）。
第3步 拉清单【必须执行】：listFillNodes → fillBoard(全景卡) + FillPanel(填报面板)。
      有草稿→标注"续填草稿(批次DOC-xxx)"；台账状态≠草稿→走边界分支(§8)。
第4步 逐项收集（双通道等价）：
      a) 面板通道：用户在 FillPanel 行内操作后点「已配置完，通知助手」→
         注入 [填报配置] N 项 → 按行转 patch；
      b) 对话通道：自然语言→patch；[文件已上传]/[业务文件已上传] 绑定行照常处理。
      预检规则(§6)；"整节点不涉及"→先展开清单确认再批量patch；攒批期间不主动提交。
第5步 暂存：fillFileEntry(W1 直接执行) → 如实回报"已暂存 N 项，台账仍为草稿"。
第6步 提审(W2)：仅当用户明确说"提交审核"：
      6a 预检(§6)不通过→列出缺项引导补齐，不发起；
      6b listReviewOptions → reviewConfig卡(提交说明/部门/审核人/常用审核人)；
      6c 用户填完注入[提审配置] → submitLedgerForReview 首轮(全参数,不带token)
         → confirm卡(diff+影响面)；
      6d 用户确认 → 二轮(ledgerId+confirmToken) → 取消→cancelConfirm。
      参数变了/令牌过期 → 服务端重出计划，不用旧令牌重试。
第7步 如实回报：批次号、状态流转(草稿0→审批中1)、任务已到谁手上、未提交项留草稿。
```

## 6. 校验规则（三道闸，D1 口径）

### 6.1 规则总表

| 文件状态 | 文件 | 文件摘要 | 备注 | 提交闸行为 |
|---|---|---|---|---|
| 已取得(0) | **必传** | **必填** | 选填 | 缺文件 → 阻断，指向面板对应行 |
| 空缺(1) | 不期望上传 | **必填** | 主动追问（缺失原因+预计补齐时间） | 缺摘要 → 阻断 |
| 不涉及(2) | 不期望上传 | **必填** | 主动追问（天然缺项原因） | 缺摘要 → 阻断 |
| 其他(3) | 可选 | **必填** | 建议 | 缺摘要 → 阻断 |
| 待上传(-1) | 可选（上传即转已取得） | — | — | 预设行=本轮不提交（确认卡"未提交"区展示）；**自定义行必须给定明确状态**才能提交 |

### 6.2 三道闸

| 闸 | 位置 | 行为 |
|---|---|---|
| 闸1 对话预检 | SKILL.md 教 LLM | 按 §6.1 预检；缺项主动引导（面板行/追问） |
| 闸2 服务端 W1（软） | `fillFileEntry` | 暂存允许半成品（对齐业务暂存语义），返回 `warnings[]`（如"已取得但无文件"），agent 转达 |
| 闸3 服务端 W2（硬） | `submitLedgerForReview` 首轮 | 严格执行 §6.1，不满足拒绝出计划并返回缺项清单；同时校验草稿归属本人、状态=0、待上传预设行自动剔除、providerTime 格式 |

### 7.6 FillPanel 填报面板（核心操作台）

**设计原则**（四轮迭代收敛）：

1. **按业务结构排版**：文件节点 → 文件类别（申报方心智模型），不按"是否传了文件"归类；
2. **只在填报模式出现**：`listFillNodes` 渲染出 fillBoard 才算进入；提审成功/用户放弃/切换项目阶段 → 移除；
3. **行内三控件完成三件事**：状态下拉 + 文件按钮 + 摘要输入；
4. **服务端推导、前端纯投影**：面板内容 = 最近一次工具返回的 `fillPanel` 字段，本地编辑态攒批，通知后刷新。

#### 7.6.1 折叠条（默认态）

```text
┌──────────────────────────────────────────────────────────────────┐
│ 📋 资料填报 · 待处理 5 / 已完成 9                       [展开 ▾]    │
└──────────────────────────────────────────────────────────────────┘
```

#### 7.6.2 展开态（按节点分节 → 类别行 → 行内控件，限高滚动）

```text
┌────────────────────────────────────────────────────────────────────────┐
│ 📋 资料填报 · 可研批复办理                 [☐ 只看待处理]      [收起 ▴]  │
│────────────────────────────────────────────────────────────────────────│
│ ▼ 批复文件（必填节点）                                        ✓ 2 │
│ ──────────────────────────────────────────────────────────────────── │
│  可研批复文件                                              ✓ 已配置 │
│    状态 [已取得 ▾]   文件 批复.pdf·11-02 [替换]   摘要 已出正式批复     │
│                                                                        │
│  用地批准书                                              📝 待通知      │
│    状态 [空缺   ▾]   文件 —                摘要 [预计12月补齐____]      │
│                                                                        │
│  环评批复                                                              │
│    状态 [待上传 ▾]   文件 [选择文件]          摘要 [可稍后填________]     │
│────────────────────────────────────────────────────────────────────────│
│ ▶ 招标文件（选填节点） · 待处理 2 · 已完成 1                    [展开 ▾] │
│────────────────────────────────────────────────────────────────────────│
│                          未通知变更 2 项   [ 已配置完，通知助手 (2) ]     │
└────────────────────────────────────────────────────────────────────────┘
```

**每个类别行 = 固定三控件**，从左到右正好是填报动作顺序：

| 控件 | 形态 | 回答 |
|---|---|---|
| 状态 | **下拉**（待上传/已取得/空缺/不涉及/其他） | 这个类别什么状态？ |
| 文件 | 当前文件名 + `[选择文件]`/`[替换]` | 交什么/换什么文件？ |
| 摘要 | 单行输入（占位提示动态变化） | 为什么空缺/是什么文件？ |

行尾状态点：`·` 未动 → `📝 待通知`（有本地变更）→ `✓ 已配置`（已暂存落库）。
`[☐ 只看待处理]` 开关过滤已完成行；节点分节可折叠（应对 154 类别大清单）。

#### 7.6.3 状态下拉联动规则（本地态即时反应，通知时才落库）

```text
选「已取得」 ─→ 文件区激活并标 ⚠必传（选了不传，提审闸会拦）
               摘要占位变为 "必填"，预填类别默认摘要 defaultSummary（可改）
                ← 对齐业务端 applySummaryByStatus 联动
选「空缺」   ─→ 文件区隐藏；摘要占位 "必填：缺失原因+预计补齐时间"
选「不涉及」 ─→ 文件区隐藏；摘要占位 "必填：天然缺项原因"
选「其他」   ─→ 文件区可选；摘要占位 "必填"
选「待上传」 ─→ 整行重置为未处理（= 场景①"不填写"）
```

#### 7.6.4 三个典型场景的操作路径

| 场景 | 操作 | 结果 |
|---|---|---|
| ① 某类别不填写 | 什么都不动（保持 待上传） | 本轮不提交；提审确认卡"未提交"区列出，留草稿 |
| ② 填不涉及/空缺 | 下拉选状态 → 摘要框写原因 → 通知 | patch 状态+摘要，无需文件 |
| ③ 填已取得+传文件 | 下拉选已取得 → `[选择文件]`直传 → 摘要 → 通知 | patch 状态+fileUrl+fileName+摘要 |

**换文件路径**：已传组行内 `[替换]` → 选新文件直传 → 行显示 `新批复.pdf·刚刚(待通知📝)` → 通知时消息带 `换文件=...`；agent patch 覆盖 fileUrl+fileName，最终 diff 在提审确认卡显示 `批复.pdf → 新批复.pdf`，替换无误判。

#### 7.6.5 批量通知协议（面板唯一出口）

面板是"本地草稿态→攒批通知"模型：文件上传完成先记在行内**不立即注入消息**，点「已配置完，通知助手」一条结构化消息批量发出：

```text
[填报配置] 3 项
- 用地批准书（批复文件）：状态=空缺；摘要=用地证未批，预计12月补齐
- 环评批复（批复文件）：状态=已取得；文件=环评.pdf→/xxx.pdf；摘要=正式批复已出
- 中标通知书（招标文件）：换文件=中标v2.pdf→/yyy.pdf
```

agent 收到 → 按 §6.1 校验（缺摘要行追问，通常 0-1 轮）→ 批量 patch → `fillFileEntry`（W1 直接暂存）→ 返回新 `fillPanel` → 面板行刷新 `✓`。
**防遗漏**：通知按钮带未通知计数高亮；agent 发现面板有未通知变更时（上一轮载荷比对）主动提醒。

#### 7.6.6 生命周期状态机

```text
              listFillNodes 返回(进入填报模式)
                       │
        ┌─ 有待处理/未完成项 ──→ 折叠条 ── 展开编辑/通知循环 ─┐
 (隐藏)──┤                                              全部 done + 摘要齐
        └─ 全部完成 ──────→ "✓ 文件已齐全"短提示后隐藏        ↓
                                                                隐藏
              提审确认执行成功(fillMode:closed) / 用户"不填了" / 切换项目·阶段 ──→ 移除
```

状态变化面板自动跟随：用户对话说"环评批复其实拿到了" → patch 状态=已取得 → 暂存返回的 fillPanel 里该行变必传缺文件态并回到待处理——"改了状态忘了传文件"被结构性堵住。

## 8. 边界场景

| # | 场景 | 处理 |
|---|---|---|
| 1 | 已有草稿 | `get-draft` 命中 → fillBoard/面板标"续填草稿(批次DOC-xxx)"，patch 合并进现有草稿 |
| 2 | 审批中/已通过台账 | 阻断填报，引导看进度/待办；已通过可只读浏览 |
| 3 | 已驳回/部分通过 | 引导切 declarant-workflow（重提闭环），避免双入口写冲突 |
| 4 | 特殊文件(isSpecial) | 提审卡提示协同审核；v1 仅单节点部门会签（D2），多级配置引导去业务页面 |
| 5 | 涉密文件 | patch 支持 isConfidential+visibleRoleIds；确认卡 diff 强制显示涉密标记；文件名脱敏口径与业务端一致 |
| 6 | 新增自定义类别 | patch 的 category 不在预设清单 → agent 先问"是否新增自定义类别行？"确认后 source=1 落库 |
| 7 | "整节点不涉及" | 先展开该节点全部类别清单确认，再批量 patch（禁止自造 selector） |
| 8 | ID 精度 | projectId/phaseId/ledgerId/entryId 一律字符串 |
| 9 | 令牌过期/参数变更 | 服务端重出计划，禁用旧令牌重试（7 态消费枚举） |
| 10 | 上传后状态联动 | 空缺/待上传行上传文件 → 询问"是否改为已取得？"（对齐业务端自动置已取得+回填默认摘要） |
| 11 | 面板未通知变更 | 通知按钮计数高亮；agent 主动提醒"面板还有 N 项变更未通知" |
| 12 | 双通道并发 | 对话 patch 与面板通知同轮到达 → 合并为一次 fillFileEntry 攒批执行 |
