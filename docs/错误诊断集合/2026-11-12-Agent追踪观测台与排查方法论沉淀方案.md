## 一、背景

本次 TodoWrite 死循环排查完全依赖手工 SQL/Python 直查 `agentx_trace`，方法论只存在于排查人脑中。现状盘点：

| 已有资产 | 位置 | 缺口 |
|---|---|---|
| `agentx_trace`（每轮 input/output/think/tokens/耗时/成败） | PG 库 | 数据全，但无人读界面 |
| `TraceQueryService`（overview/roundDetail/firstAppear 三工具） | `dataagent/eval/trace/` | **面向 Agent 自诊断**（M8），不是给人用的 |

| 排查方法论 | 无 | 本次是第一次系统化排查，应固化 |

## 三、层 1：诊断 Playbook（`docs/错误诊断集合/troubleshooting-playbook.md`）

### 3.1 排查模板（六步法）

1. **定位**：按话术关键词 / 时间窗 / 用户锁定 session。SQL 模板：
   ```sql
   SELECT id, session_id, conversation_id, round, success, length(input_data),
          length(output_data), prompt_tokens, completion_tokens, created_at
   FROM agentx_trace WHERE input_data LIKE '%关键话术%' ORDER BY id;
   ```
2. **定形态**：逐轮解析 `output_data` 统计工具调用分布（同名占比、有无业务工具）、`length(input_data)` 增长曲线（每轮 +500 字符的匀速增长 = 循环特征）、压缩点（input 骤降）；
3. **查背离**：think（意图）与 output（实际调用）是否背离——背离 = 模型想调的工具不可得，是结构问题的铁证；
4. **查结构**：本次请求实际可用的工具清单（常驻 + deferredSession 已发现）vs 历史消息中出现过的工具名——"发现态断裂"检查；
5. **查反馈**：高频工具的返回话术是否构成无失败信号的正反馈（如"请继续执行当前的任务"）；
6. **定终态归因**：`agentx_conversation.status` + `agentx_pause_state`（区分 maxRounds 兜底 / 用户打断 / 异常），归因到四层之一：模型层 / 提示词层 / 内核层 / 工具层。

### 3.2 案例库

每次事故按模板追加案例条目（现象 → 数据证据 → 根因 → 修复 → 验证）。**第一篇即本次 TodoWrite 案例**（见附录 A，可直接入册）。

## 四、层 2：后端诊断 API

新增三个类（与 Agent 自诊断的 `TraceQueryService` 分开，人读版）：

| 类 | 职责 |
|---|---|
| `TraceDiagnoseController` | REST 端点，挂现有 admin 鉴权体系 |
| `TraceDiagnoseService` | 查询编排：会话列表、会话详情（轮次时间线 + 指标）、轮次原文 |
| `TraceHeuristics` | 启发式红旗检查（纯函数），**与 LoopGuard 共用阈值常量**（同 module 或常量类引用，改阈值一处生效） |

### 端点设计

| 端点 | 返回 |
|---|---|
| `GET /admin/trace/sessions?suspicious=true&date=&conversationId=` | 会话列表 + 自动检测标记：🔴 循环嫌疑（同名工具占比 ≥ LoopGuard warn 阈值）、🟡 高消耗（轮次/累计 token 超阈）、🔴 失败聚集（连续失败轮） |
| `GET /admin/trace/sessions/{sessionId}` | 会话详情：轮次时间线（round、工具名、参数/结果摘要、tokens、耗时、压缩点标注）+ **红旗面板**（跑 TraceHeuristics 全套检查，输出人读结论） |
| `GET /admin/trace/sessions/{sessionId}/rounds/{n}` | 该轮 input/output/think 全文 |

### TraceHeuristics 检查项（即 Playbook 六步法的代码化）

1. 工具调用分布与同名占比（循环嫌疑，含"纯单工具轮"计数——与 LoopGuard 同口径）；
2. input 增长曲线异常（匀速线性增长 + 无业务工具 = 复读）；
3. think 与实际调用的背离检测（think 中提及的工具名 ∉ 实际调用名，且该工具名 ∈ 延迟注册表 →"发现态断裂"红旗）；
4. 高频工具返回话术复读检测（同一返回文本出现次数）；
5. 失败轮聚集、token 消耗超阈。

> 检查 3 是本次事故的专属信号：round 2/59 的 think 都点名 listMyDrafts 而从未调用成功——自动化后可直接亮红旗"疑似延迟工具发现态断裂"。

## 五、层 3：前端「追踪观测台」

新路由 `/trace`（`frontend/src/router/index.js` 挂现有 manage 布局）+ `TraceObservatoryView.vue`（对齐 `ModelManageView`/`EvalReportView` 的写法与组件库）：

- **左栏**：会话列表（时间倒序、异常徽章筛选、按 conversationId 搜索）；
- **右栏会话详情**：
  - 轮次时间线：一轮一节点、按工具类型着色，红旗点（背离点/压缩点/熔断点）特殊标注；
  - token/耗时迷你图（展示增长曲线形态）；
  - 红旗诊断面板（后端 TraceHeuristics 结果直渲染）；
  - 轮次点开：input/output/think 折叠原文，**懒加载**（input 动辄 140K+ 字符，不能整页渲染）；
- **顶部**：Playbook 文档链接 + 异常统计摘要。

## 附录 A：案例条目样例（本次事故，可直接作为 Playbook 第一篇）

### [2026-11-12] TodoWrite 死循环——延迟工具发现态断裂 + 弱模型复读

- **现象**：会话 `dodo_conv_f20d3687-…` resume 后连续 78 轮只调 TodoWrite，烧 ~270 万 prompt token，用户手动打断。
- **数据证据**：75×TodoWrite / 4×context_reload / 0×业务工具 / 0×tool_search；round 2 与 59 的 think 点名 listMyDrafts 但发射 TodoWrite（think-call 背离）；每轮 input +530 字符匀速增长。
- **根因**：resume 后 `deferredSession` 清空但历史保留延迟工具调用记录，提示词禁止重复 tool_search → 业务工具全程不可得；常驻工具仅 2 个；TodoWrite 无条件成功 + "请继续"话术正反馈；内核无循环检测。
- **归因**：内核层（发现态隔离设计）+ 工具层（无失败信号）+ 模型层（弱模型模式坍缩）。
- **修复**：见《TodoWrite 死循环修复方案》Fix A（LoopGuard 熔断）+ Fix B（历史延迟工具重登记）+ Fix C（话术中性化）+ Fix D（max-rounds 40）。
- **验证**：回归 replay 本会话快照，断言 resume 后 listMyDrafts 可直接调用、连续 TodoWrite 在第 7 轮被熔断收口。
