# 排查报告：「分析下我的项目」耗时 2 分多

> 日期：2026-11-13
> 现象：shenbao1/123456 登录后提问「分析下我的项目」，端到端耗时 2 分钟以上（历史成功记录 92s~200s，另有 8 次 interrupted 为用户等不及主动停止）。
> 排查方式：agentx_trace / agentx_session / agentx_conversation 三表量化 + 浏览器实测复现 + 内核代码走读。
> 结论先行：**~99% 时间花在 MiniMax LLM 推理上（ReAct 循环 13~26 轮），工具执行、数据库、前后端合计不到 1.5 秒**。三大耗时因子 = 轮次太多 × 思考太重 × 上下文越滚越大。

---

## 一、排查结论（一句话）

耗时不是 SQL 慢、不是落库慢、不是前端慢，而是 **MiniMax M3.1-Flash 在 ReAct 循环里被调用了 13~26 次**，每次都是全量上下文的流式推理，其中"思考"占 50~60%。

## 二、证据链

### 1. 数据库 trace 量化（agentx_trace 逐轮实时落库）

| 轮 | 动作 | LLM耗时 | 其中思考 | prompt tokens |
|---|---|---|---|---|

| 2 | tool_search 发现工具 | 11.5s | 8.2s | 24,758 |
| 3 | TodoWrite 写计划 | 13.5s | 5.4s | 32,996 |

| 5 | validateSql | 14.4s | 8.1s | 39,834 |

会话总耗时 200.46s − LLM 199.8s = **0.6s 是全部工具执行 + 落库**。

关键口径：trace 的 `duration_ms` 只统计 LLM 流式调用耗时（`AgentLoopExecutor.traceRound` 在工具执行**之前**调用，RoundState 从创建到流结束），`think_duration_ms` 是首轮/末轮 reasoning chunk 间隔。所以 trace 加总≈LLM 纯推理时间，与 `agentx_conversation.completed_at - created_at` 对账吻合。

### 2. 浏览器实测复现（shenbao1，新建会话同题提问）

- 实测 **174.3s、26 轮**，LLM 172.9s（**99.2%**），思考 87s，**累计 prompt tokens 149 万**（每轮全量重发上下文）。
- prompt 单轮从 15.7k 一路涨到 84k，**压缩阈值（100 条消息 / 90k token）始终没触发**。
- 这轮还跑偏了：「分析下我的项目」最终产出单个项目（南三高速）的档案五层下钻报告——SOP 的穿透式下钻把轮次滚到 26，前端显示「已工作 · 2 分 54 秒」。
- 前两分钟用户界面只有思考流 + 工具卡片，报告正文最后 26s 才开始流式出现。

### 3. 历史数据旁证（agentx_conversation）

同题多次执行 92s / 136s / 163s / 190s / 200s 不等 + 8 次 interrupted。耗时波动主因是 **MiniMax 推理速度不稳定**：同形态轮次有的 2s、有的 10s+（单轮最高 34.5s，其中 31.4s 是思考）。

## 三、瓶颈定位（按代码链路）

链路：`POST /agent/stream`（AgentController）→ `DodoAgent.stream()` → `AgentLoopExecutor`（mini-agentx-core ReAct 主循环）→ MiniMax M3.1-Flash（application-local.yml，api.minimax.chat）

1. **轮次是乘数**：每轮 = 一次完整 LLM 流式调用（`AgentLoopExecutor.scheduleRound`）。data-analysis 技能 SOP（`skills/data-analysis/SKILL.md`）天然多轮：Skill 加载 1 轮 + tool_search 1 轮 + TodoWrite 2~3 轮 + 每条查询 validateSql/executeSql 各 1 轮 + describeTables/lookupGlossary/currentTime/calculate 各 1 轮 + 最终报告 1 轮。
2. **思考占 50~60%**：`data-agent.agent.thinking-mode: REASONING_CONTENT`（application.yml:68），MiniMax M3.1-Flash 每轮深度思考，工具轮尤其重（trace 中单轮思考最高 31.4s 只为发一个 executeSql）。
3. **上下文滚雪球**：首轮系统提示词 16k tokens（system-prompt.md 10.6KB + 常驻工具 schema + 技能清单 + 用户上下文），第 2 轮注入 15.7KB 技能正文后涨到 24k，此后每轮全量重发并持续增长。
4. **纯浪费轮**（设计导致，逐项核对过代码）：
   - `validateSql` → `executeSql` 成对走：但 `ExecuteSqlTool.java:78` 本来就"强制校验兜底（validateSql 通过后这里再验一次，双保险）"——validateSql 那一轮是白花的；
   - `currentTime` 整轮只为读服务器时钟（system-prompt.md:49"时间概念必先 currentTime"强制要求），而 `UserContextBuilder` 本可免费注入当前时间；
   - `calculate` 轮思考 30s 算一个除法；
   - `tool_search` 延迟发现：SQL 六工具每次必用，每次必先搜一轮。
5. **已排除的嫌疑**（有数据背书）：
   - PG 查询毫秒级（executeSql 各轮工具执行合计 <1s）；
   - `agentx_session` 循环期间零写入（终态一次落库，`persistTerminal`），trace 每轮单条 INSERT 开销可忽略；
   - 登录/token 校验、前端渲染、SSE 传输均无异常。

## 四、优化方案建议（按预期收益排序，未动代码）

### P0（预估合计省 60%+，200s → 60~80s）

| # | 方案 | 预期收益 |
|---|---|---|
| 1 | **SOP 改为直接 executeSql**（executeSql 已内置同款校验），或 executeSql 加"已校验"入参 | 每条查询省 1 轮，单次省 4~8 轮 ≈ 30~50s |
| 2 | **思考治理**：验证 MiniMax API 是否支持关闭/降级思考（如 reasoning_effort / extra_body）；至少对工具调用轮禁思考 | 思考 87~116s 压到 20~30s |
| 3 | **轮次预算**：对话场景 maxRounds 50 → 12~15；「分析下我的项目」类全景题给固定模板（2~4 条汇总 SQL），五层下钻仅明确追问时启用 | 防跑偏+防失控，26 轮可拦在 12 |

### P1（再省 15~25%）

4. **SQL 六工具转常驻**（省 tool_search 轮）+ **data-analysis 技能按意图自动注入 system prompt**（省 Skill 轮），代价是首轮 prompt +2~3k tokens，远小于省下两轮；
5. **UserContextBuilder 注入当前时间**（省 currentTime 轮）；42 条术语表评估常驻 vs 按需（省 lookupGlossary 轮）；
6. **压缩阈值下调**到 ~30-40k tokens，让长会话中途真正触发 L1/L2 offload；describeTables 输出瘦身（示例值/注释截断）。

### P2（体验与稳定性）

7. **模型分层路由**：工具轮用快模型，最终报告才用主模型（本轮 23~25 轮单轮 16~34s 全耗在思考上）；
8. MiniMax 推理速度波动大（同请求 92s vs 200s），评估备用 endpoint/模型兜底；
9. 交互层：报告开始前的 ~120s 用户只能看思考流和工具卡片，可加阶段进度（"已完成：表结构✓ 盘点查询✓ 备案率计算中…"）。

## 五、复现与排查方法备忘

- 查库工具：`tools/PgQuery.java`（JDBC 单文件，连接 192.168.2.61:5432/zrkj-huaxi）；
- 逐轮 trace：`SELECT round, duration_ms, think_duration_ms, prompt_tokens, completion_tokens, LEFT(output_data,100) FROM agentx_trace WHERE conversation_id='...' ORDER BY round`；
