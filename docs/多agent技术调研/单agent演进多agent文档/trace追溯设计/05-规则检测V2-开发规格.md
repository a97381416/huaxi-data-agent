# 规则检测 V2 开发规格（含 AI 诊断增强与批量重诊断）

> 定位：本文档是 V2 的**正式开发规格**，依据 04 文档（GPT 规则评审）+ 03 方案（V1 落地规范）+ V1 代码现状编写。
> 每条规则明确：现状问题 / 输入字段 / 检测算法 / 触发与排除条件 / 风险等级 / params 配置 / 测试用例。
> 开发照本文档实现，不再出现「规则名写了答案不一致、实际只检查数字是否出现」的口径漂移。

---

## 1. 背景与现状基线

### 1.1 V1 已交付（03 方案，2026-11-19/20 上线）

- 11 条规则引擎：REACT-001~004 / TOOL-001~005 / ANSWER-001~002，代码 SPI（`DetectRule`）判定 + `agentx_monitor_detect_rule` 配置表（enabled / params jsonb）。
- 三入口检测：closeSession 异步派发（`DetectDispatcher` 单线程 + 有界队列 200）、`DetectSweepJob` 每 5 分钟兜底（终态未检测限 50 条）、手动单问重检 `POST /monitor/sessions/{id}/detect`。
- 风险落库 `agentx_monitor_risk`（幂等 replace），session 回填 detect_status / risk_total / risk_high / first_risk / detector_version（当前 v1）。
- 前端：规则管理页（RuleManageView）、详情页风险卡 + ⚠ 角标、列表风险筛选。
- AI 诊断（`MonitorDiagnoseService`）：独立诊断 Agent（temperature=0、enableTrace=false）+ 4 个只读 trace 查询工具，提问级（全链路）/窗口级两种入口，风险清单注入提示词，报告落 `agentx_monitor_report`。
- 36 个规则单测（`DetectRulesTest`）+ SeedData 验收数据构造器。

### 1.2 V1 遗留问题（04 文档评审结论）

8 条存量规则检测逻辑有缺陷：TOOL-001 只扫前 300 字符且文档工具豁免、TOOL-002 全局共用 30s 阈值、TOOL-003 统一要求 JSON、TOOL-004 关键词匹配误报（`WHERE remark='DELETE'`）、TOOL-005 逻辑不完整、ANSWER-001 无恢复感知、ANSWER-002「数字未出现≠不一致」、REACT-002 无恢复感知。缺 4 条规则：TOOL-006（参数异常）/ TOOL-007（API 业务失败）/ REACT-005（无有效进展）/ SKILL-001（Skill 加载失败）。

### 1.3 关键探查结论（影响 V2 设计）

- **技能加载就是工具调用**：工具名 `Skill`，加载失败返回「未找到技能…可用技能: …」文本（`SkillsTool.java` SkillsFunction.apply）。SKILL-001 按工具结果检测即可，**零采集改造**（04 文档担心的 trace 无 skill 落点问题不存在）。
- **工具入参可查**：payload `output_data` 已存 `{"tool_calls":[{name,arguments}]}`，TOOL-006 检测输入参数有数据基础。
- **Observation 有截断**：检测器从下一轮 input 还原工具结果时 `substring(content,1,2000)`（`AnomalyDetectService` payload 访问器），全文兜底扫描前必须放宽。
- **trace 只有轮级耗时**：无工具级耗时（03 方案已确认），TOOL-002 按工具阈值只能以轮耗时对单工具轮生效。

## 4. 规则规格（15 条）

规则注册顺序不变：REACT(5) → TOOL(7) → ANSWER(2)（ANSWER-001 依赖前置命中，必须最后）。
`DetectRuleRegistry.VERSION` 升为 `v2`。

severity 三档与展示口径（全局统一，V2-D9）：

| severity | 展示 | 含义 |
|---|---|---|
| high | 异常（红） | 明确故障/安全风险 |
| medium | 待人工确认（橙） | 大概率有问题，需人复核 |
| low | 风险提示（黄） | 轻微风险/观察项 |

### 4.1 REACT-001 执行循环过多 · medium（阈值调整）

- **输入**：session 行 rounds；trace 行（轮类型、tool_names）。
- **算法**：决策轮数 = trace 行数；工具调用次数 = tool 轮的调用总数（一轮多工具计多次）。决策轮数 > maxRounds 触发。
- **触发**：决策轮数 > maxRounds（默认 15 → **10**，观察级）。
- **排除**：无。
- **证据增强**：detail 同时给出「决策轮 X / 工具调用 Y 次」两个数。
- **params**：`maxRounds: 10`。
- **用例**：正——12 个决策轮 → 命中（detail 含两计数）；反——8 轮其中含多工具轮共 12 次调用 → 不命中（调用次数不单独触发）。

### 4.2 REACT-002 连续工具执行失败 · high（恢复感知）

- **输入**：trace 行 success/error_message（按轮序）。
- **算法**：找连续失败段（相邻 ≥ failStreak 轮）；对每个失败段检查**其后**是否存在成功轮。
- **触发**：存在连续失败 ≥ 2 轮，**且之后到结束再无任何成功轮**（未恢复）。
- **排除**：后续换工具/改参后成功（恢复）→ 不命中；空结果属业务正常返回（success=true），不算失败。
- **params**：`failStreak: 2`。
- **用例**：正——R2/R3 失败、R4 起到结束全失败 → 命中；反①——R2/R3 失败、R4 改参成功 → 不命中（V1 会命中，V2 修正）；反②——单轮失败后即恢复 → 不命中。
- **联动**：不命中时 ANSWER-001 仍可经 TOOL-001 判失败（两条独立）。

### 4.3 REACT-003 相同工具重复调用 · medium（等级 high→medium，加进展条件）

- **输入**：payload tool_calls（name + arguments），Observation 文本。
- **算法**：调用指纹 = `tool_name + sha256(规范化参数)`（V1 已有 argsHash）；结果指纹 = Observation 规范化（去空白、截断 500）哈希。
- **触发**：同一调用指纹**连续** ≥ repeatCalls 次（默认 3），**且这些调用的结果指纹完全相同**（无有效进展）。
- **排除**：同指纹但结果变化（分页推进/数据变化）；改参重试（指纹不同）；非连续重复。
- **params**：`repeatCalls: 3`。
- **用例**：正——同 SQL 同参 3 次、3 次结果一致 → 命中；反①——同 SQL 3 次但 LIMIT/OFFSET 推进 → 不命中；反②——同参但结果逐次不同 → 不命中（V2 修正）。

### 4.4 REACT-004 最终回答缺失 · medium（保持）

- V1 逻辑保持：completed 且 answer 为空且无成功 text 轮 → 命中。running/interrupted/error 状态不判（error 态由别的路径解释）。
- **用例**：正——completed + answer 空 → 命中；反——answer 非空或 Observation 文本不算 answer → 不命中。

### 4.5 REACT-005 多轮执行无有效进展 · medium（**新增**）

- **输入**：轮序 tool_calls（调用指纹）、Observation 文本（结果指纹）。
- **算法**：滑动窗口检查连续 noProgressRounds 轮（默认 3）：
  1. 结果指纹全部相同（含全空），**且**期间调用指纹在变（不同参数或不同工具）——排除后归 REACT-003；
  2. 或 Observation 连续为空结果特征（`rows:[]` / `count:0` / 空文本），且调用在变。
- **触发**：满足 1 或 2。
- **排除**：调用指纹完全相同（REACT-003 管）；期间任一轮结果指纹不同；窗口内最后恢复了（有非空有效结果）则窗口在该轮截断。
- **params**：`noProgressRounds: 3`。
- **用例**：正①——SQL→API→SQL 轮换、三次结果文本一致 → 命中；正②——三轮空 rows、参数各不同 → 命中；反——前两轮空第三轮有数据 → 不命中；反——三轮同参同结果 → 不命中（REACT-003 命中，本规则去重）。

### 4.6 TOOL-001 工具调用失败 · high（结构化优先，V2-D2）

- **输入**：Observation 全文（放宽截断后）。
- **算法**（两级）：
  1. **结构化状态**：Observation 可解析为 JSON 对象时检查——
     `status ∈ {error, failed, failure}`、`success === false`、`error_code` 非空且非 0、`exception` 非空、`timeout === true`，任一成立 → 命中（证据记字段名与值）；
  2. **关键词兜底**：无可识别结构化状态字段时，**全文**扫描失败特征词（词表沿用 + 可配置）。
- **排除**：结构化 `success=true` 或 `status ∈ {ok, success, completed}` → 不进关键词兜底（正常文本含 "error" 词不误报）。
- **变更点**：① 删除 300 字符扫描窗（全文）；② `docToolNames` 默认改空（参数保留兼容）；③ payload 访问器截断 2000 → `obsTruncateChars`（默认 8000）。
- **params**：`failKeywords`（沿用现词表）、`docToolNames: []`、`obsTruncateChars: 8000`。
- **用例**：正①——`{"status":"error","error":"Unknown column"}` → 命中；正②——错误信息出现在第 3000 字符处 → 命中（V1 漏）；反①——`{"success":true,"data":[…]}` → 不命中；反②——文档工具正常返回含「error handling」且 success=true → 不命中（V1 因文档豁免/窗口外表现不稳定）。

### 4.7 TOOL-002 工具调用耗时异常 · low（改名 + 按工具阈值）

- **改名**：「轮耗时超长」→「工具调用耗时异常」。
- **输入**：trace 行 duration_ms、tool_names。
- **算法**：单工具轮 → 查 `perToolMs[toolName]`，未配置用 `defaultMs`；**多工具轮 → 用 defaultMs**（轮耗时无法归因单工具，宽松避免误报）。超阈值 → 命中。
- **params**：`defaultMs: 30000`、`perToolMs: {"execute_sql":5000,"Skill":3000,"search_documents":5000,"外部HTTP类工具":10000}`（上线按实际工具清单与性能基线校准）。
- **用例**：正——execute_sql 单工具轮 8s → 命中（8s > 5s）；反①——未知工具轮 20s → 不命中（< defaultMs 30s）；反②——多工具轮 8s 含 execute_sql → 不命中（用 30s 判）。

### 4.8 TOOL-003 工具返回格式异常 · low→**medium**（按工具期望输出类型）

- **输入**：Observation 文本、工具名。
- **算法**：查 `expectedOutput[toolName]`（缺省 `TEXT_OR_JSON`）：
  - `JSON`：先查堆栈特征，再强制 JSON 解析，解析失败 → 命中；
  - `TEXT_OR_JSON` / `TEXT`：只查堆栈特征（`at 包名.类.方法(文件:行号)` 模式、`Exception:` 起始行）。
- **排除**：合法 JSON（即使业务码失败——那是 TOOL-007 管）；Markdown/纯文本且无堆栈特征。
- **params**：`expectedOutput: {"execute_sql":"JSON","Skill":"TEXT","search_documents":"TEXT_OR_JSON"}`。
- **用例**：正①——execute_sql 返回 `{rows:[` 截断 JSON → 命中；正②——任意工具返回 `java.sql.SQLException: …\n\tat …` → 命中；反——search_documents 返回 Markdown → 不命中；反——execute_sql 返回合法 JSON 数组 → 不命中。

### 4.9 TOOL-004 SQL 非法操作 · high（词法分析，V2-D7）

- **输入**：SQL 类工具调用的 sql 参数文本。
- **算法**：
  1. 剥离行注释 `--…`、块注释 `/*…*/`、字符串字面量 `'…'`（替换为 `''` 占位）；
  2. 若以 `WITH` 开头，跳过全部 CTE 定义（括号配平）定位主语句；
  3. 取首个关键字，∉ `{SELECT, WITH, EXPLAIN, ANALYZE, SHOW, TABLE}`（只读白名单）→ 命中。
- **排除**：写操作白名单用户（`writeWhitelist`，按 user_id）。
- **params**：`sqlToolKeywords`（识别 SQL 工具，沿用）、`writeWhitelist: []`。
- **用例**：正①——`DELETE FROM project` → 命中；正②——`/* x */ DROP TABLE t` → 命中；反①——`SELECT * FROM project WHERE remark='DELETE'` → 不命中（V1 误报）；反②——`WITH cte AS (SELECT …) SELECT …` → 不命中。

### 4.10 TOOL-005 统计查询空结果风险提示 · low（改名 + 逻辑重构）

- **改名**：「SQL 空结果提示」→「统计查询空结果风险提示」。
- **输入**：session.question、成功 SQL 轮的 Observation、session.answer。
- **算法**（四个条件同时满足才命中）：
  1. 用户问题含统计类词（`statKeywords`：多少/数量/几个/count/统计/总数/合计）；
  2. 存在 success=true 的 SQL 工具轮（未命中 TOOL-001）；
  3. 该轮结果为空（`rows:[]` / `count:0` / 空文本特征）；
  4. 最终回答给出**确定性统计结论**（数字 + 结论模式，如「共 X 个」「X 个项目」），且无「未查到/无数据/无法获取」声明。
- **排除**：回答「数据库中暂无符合条件的数据」类 → 不命中；非统计类问题 → 不命中。
- **变更点**：默认启用 false → **true**（逻辑闭合后有价值）。
- **params**：`statKeywords`（如上）、`emptyPatterns`。
- **用例**：正——问「今年多少项目已验收」+ SQL 成功 0 行 + 答「今年共 3 个已验收」→ 命中；反①——同场景答「暂无符合条件的数据」→ 不命中；反②——问「项目列表」+ 空 + 答「没有找到」→ 不命中（非统计类）。

### 4.11 TOOL-006 工具调用参数异常 · high（**新增**，查输入）

- **输入**：payload `output_data.tool_calls[].arguments`（调用前置检查，与 TOOL-003 的查输出互补）。
- **算法**：
  1. `requiredArgs` 配置内的工具：必填参数缺失 → 命中；
  2. 通用检查（全部工具）：参数值为 null / 空串 / 空对象且必填 → 命中；
  3. SQL 参数残缺启发：去注释空白后以 `SELECT`/`FROM`/`WHERE`/`AND`/`,` 结尾、或缺 `FROM` 的 SELECT → 命中。
- **排除**：可选参数缺失；未知工具只做通用检查。
- **params**：`requiredArgs: {"execute_sql":["sql"],"Skill":["name"]}`（上线按工具清单补全）。
- **用例**：正①——`{"sql":null}` → 命中；正②——`{"sql":"SELECT * FROM"}` → 命中；反——`{"sql":"SELECT 1"}` → 不命中。

### 4.12 TOOL-007 API 业务执行失败 · high（**新增**）

- **输入**：`apiTools` 配置内工具的 Observation JSON。
- **算法**：解析 Observation → 取 `codeField` 值，∉ `successCodes` → 命中（detail 带 `messageField` 内容）。
- **排除**：非 `apiTools` 配置的工具不检查；Observation 非 JSON → 交给 TOOL-003。
- **params**：`apiTools: {"业务API工具名": {"codeField":"code","successCodes":[0,200],"messageField":"message","dataField":"data"}}`（上线按实际 API 工具约定配置）。
- **用例**：正——`{"code":10001,"message":"没有权限","data":null}` → 命中；反——`{"code":0,"data":[…]}` → 不命中。
- **依赖**：需与业务平台 API 工具对齐业务码约定后填配置，规则代码不感知具体码值。

### 4.13 SKILL-001 Skill 加载失败 · medium（**新增**，V2-D6）

- **输入**：工具名 `Skill` 的调用 Observation。
- **算法**：Observation 匹配失败特征模式——含「未找到技能」/「可用技能」列表提示 → 命中（detail 带传入的 name 与可用清单摘要）。
- **排除**：正常返回「技能工作目录: …」+ SKILL.md 正文 → 不命中；不检测「应该调 Skill 而没调」（04 文档明确不查）。
- **params**：`skillToolName: "Skill"`、`failPatterns: ["未找到技能","可用技能"]`。
- **用例**：正——`Skill(name="data-analys")` 拼错 → 返回未找到 → 命中；反——`Skill(name="data-analysis")` 正常加载 → 不命中。

### 4.14 ANSWER-001 工具失败后仍给出确定性结论 · high（恢复感知，V2-D4）

- **输入**：失败轮位置（TOOL-001/REACT-002 命中或 success=false 轮）、失败后轮序、session.answer。
- **算法**：
  1. 存在工具失败（依赖 `ctx.hasHit("TOOL-001","REACT-002")` 或独立扫 success=false，口径与 V1 一致）；
  2. **最后一个失败轮之后不存在成功的数据来源轮**（success=true 的 SQL/API 工具轮且结果非空）——存在则数据可能来自恢复后的调用，不命中；
  3. 最终回答含确定性数字结论（数字 + 结论模式）；
  4. 回答未声明获取失败/无数据。
- **触发**：1+2+3+4 同时成立。
- **排除**：失败后有成功数据轮（即使数字对不上——那是 ANSWER-002 管）；回答已声明失败（宁可漏报不误报，03 纪律；「虽失败但按之前数据给出 X」这类边界归 AI 诊断复核）。
- **用例**：正①——R2 SQL 失败、后续无成功轮、答「今年共完成 86 个」→ 命中；反①——R2 失败、R3 改参成功取到 86、答 86 → 不命中（V2 修正，V1 误报）；反②——答「抱歉，暂时无法查询」→ 不命中。

### 4.15 ANSWER-002 工具结果与最终答案数值不一致 · medium（真数值比对，V2-D3）

- **改名**：「答案与工具结果数值不一致」→「工具结果与最终答案数值不一致」。
- **输入**：成功统计类工具结果的单一数字字段（`statFields`：count/total/sum/cnt/num/数量/总数/合计）、session.answer。
- **算法**（首版单数字场景）：
  1. 取**最后一次**成功统计结果中的单一数字字段值 T（多个数字字段/多行聚合 → 本版跳过不判）；
  2. 提取回答中的阿拉伯数字集 A（含千分位 `1,234` 归一）；
  3. 判定：T ∈ A → 不命中；T ∉ A 且 A 中存在以「统计结论模式」出现的其他数字（共 X 个 / X 项 / X 条…）→ **命中**（detail 给 T vs 冲突数）；T ∉ A 且回答无数值结论（定性）→ 不命中。
- **排除**：定性回答；多数字复杂场景（明确跳过）；T 出现在回答中。
- **params**：`statFields`（如上）、`conclusionPatterns: ["共\\s*([0-9,]+)\\s*(个|项|条|次|条)", …]`。
- **用例**：正①——count=86、答「今年完成了 68 个」→ 命中；反①——count=86、答「共 86 个」→ 不命中；反②——count=86、答「整体完成情况良好」→ 不命中（V1 误报主场景）；反③——count=86、答「约 80 多个」→ 不命中（约数不构成确定性冲突，首版保守）。

### 4.16 ANSWER-003（占位，下一版）

工具失败后最终回答未说明数据获取失败且无数据来源。首版不做——与 ANSWER-001 判定面重叠度高，待 ANSWER-001 恢复感知上线观察误报后再定边界。

## 6. 批量重诊断设计（V2-D10）

### 6.1 API

```
POST /monitor/detect/rerun
{
  "conversationIds": ["..."],          // 三选一或组合
  "detectorVersionLt": "v2",           // 圈定旧版本检测过的
  "from": "2026-11-01T00:00:00",       // created_at 范围
  "to":   "2026-11-20T00:00:00",
  "limit": 200                          // 单次上限，默认 200、最大 1000
}
→ { "accepted": 187, "skipped": 13 }    // skipped=非终态/不存在
```

### 6.2 执行模型

- 圈定 session_id 列表 → 校验终态 → 按 50/批切片，逐批投递到 **DetectDispatcher 现有单线程队列**（与实时检测天然串行，不并发挤压；队列满丢弃部分由 SweepJob 兜底下一轮接续——sweep 只补 `detect_status<>'done'`，故 rerun 前先把这些行置 `detect_status='pending'`，形成闭环）。
- `detect(sessionId)` 复用现有幂等 replace：DELETE→INSERT 风险 + 回填 detector_version=v2。
- **只读红线**：全程只读 `agentx_monitor_trace` + `agentx_trace_payload`，绝不重放 Agent/SQL/API。
- 进度：首版不建进度表——列表页按 `detector_version` 筛选观察 + 完成日志汇总；内存计数器暴露 `GET /monitor/detect/rerun/status`（受理/完成/失败计数，可选任务）。

### 6.3 前端入口

- TraceListView：多选会话 → 「批量重诊断」按钮 → 确认框（提示只读回放）。
- RuleManageView：修改规则保存后提示「是否对近 7 天会话重刷」（预填 `detectorVersionLt=v2` + from=now-7d）。
