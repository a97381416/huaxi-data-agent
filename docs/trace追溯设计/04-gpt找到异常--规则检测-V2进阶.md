## **1. 工具类规则**

### **TOOL-001：工具调用失败**

保留

高风险

当前配置：

- 失败特征词：error、exception、timeout、failed、失败、超时、cancelled
- 关键词扫描窗口：300 字符
- 文档类工具名称：tool_search、listTables、lookupGlossary

这条规则的目的是：

检查 Tool 执行结果中是否存在失败信息。

例如：

```
{
  "tool": "execute_sql",
  "status": "error",
  "error": "Unknown column 'project_status'"
}
```

应该触发异常。

**我认为这条规则必须保留，但需要修改检测方式。**

目前存在三个问题：

1. 只扫描前 300 个字符，错误信息如果在后面就可能漏掉。
2. 只匹配错误关键词，正常返回的文本也可能包含 error、failed 等词。
3. 文档类工具名称被单独排除，但实际上文档检索工具也可能调用失败。

建议调整为：

优先检查结构化状态字段：

- status
- success
- error_code
- exception
- timeout

如果没有结构化状态，再通过错误关键词进行兜底判断。

另外，不建议仅仅因为工具名称是 `search` 或 `lookup` 就跳过失败检测。

### **TOOL-002：轮耗时超长**

保留

低风险

当前阈值：30000ms。

意思是单轮工具调用超过 30 秒就产生提示。

这条规则没有问题，但我建议把它改成：

**工具调用耗时异常**

因为不同工具的合理耗时差别很大：

| 工具类型      | 建议初始阈值 |
| ------------- | ------------ |
| 普通业务 API  | 5 秒         |
| SQL 查询      | 5 秒         |
| Skill 加载    | 3 秒         |
| 外部 HTTP API | 10 秒        |

这些只是初始参考值，需要根据你实际接口的性能基线调整。

最好支持按工具名称分别配置阈值，而不是所有 Tool 共用 30 秒。

### **TOOL-003：工具返回格式异常**

保留

低风险

当前规则主要检测：

- 工具返回异常堆栈。
- 返回了异常文本。
- 返回 JSON 但解析失败。

这个规则的方向是正确的。

但我建议明确一个概念：

**不是所有工具都必须返回 JSON。**

例如：

- SQL 工具可能返回结构化行数据。
- 文档工具可能返回 Markdown。
- API 工具可能返回 JSON。
- 某些工具可能返回纯文本。

所以应该根据工具的输出类型检查，而不是统一要求 JSON。

建议配置：

```
tool_name: execute_sql
expected_output_type: JSON

tool_name: search_documents
expected_output_type: TEXT_OR_JSON

tool_name: lookupGlossary
expected_output_type: JSON
```

这样才有准确的检测依据。

### **TOOL-004：SQL 非法操作**

保留

高风险

当前配置：

- SQL 工具特征词：sql
- 禁用操作词：INSERT、UPDATE、DELETE、DROP、TRUNCATE、ALTER、GRANT
- 写操作白名单用户：空

这条规则非常有必要。

因为你的 SQL Tool 直接执行 SQL，如果 Agent 错误生成了写操作，可能影响业务数据库。

但是这里有个重要问题：

**不能只靠字符串匹配来保证 SQL 安全。**

例如：

```
SELECT *
FROM project
WHERE remark = 'DELETE';
```

这里出现 DELETE，并不代表执行了删除操作。

另外，CTE、注释、大小写、存储过程等情况，也可能影响简单关键词检测。

我的建议：

1. 继续保留这条 Trace 检测规则。
2. 在 SQL 执行工具本身增加只读数据库账号。
3. 数据库层面限制写操作权限。
4. 使用 SQL 解析器识别真实 SQL 语句类型，而不是仅依赖关键词。

这条规则应该属于安全防护，而不仅仅是健康诊断。

### **TOOL-005：SQL 空结果提示**

修改后保留

低风险

当前规则：

统计类问题命中关键词（多少、数量、count、统计），但是 SQL 返回空结果时提示。

这个规则值得保留，但必须明确：

**SQL 查询返回 0 条数据，不代表 SQL 执行失败。**

例如：

用户问：

> 今年有多少个项目已经验收？

数据库确实没有符合条件的数据。

返回：

```
{
  "rows": [],
  "count": 0
}
```

这可能完全正常。

我建议把规则改名为：

```
TOOL-005：统计查询空结果风险提示
```

检测条件调整为：

- 用户问题属于统计类。
- SQL 执行成功。
- 返回结果为空，或者结果结构中没有预期的统计字段。
- Agent 最终回答给出了确定性的统计结论。

其中前面几项可以识别风险，最后一项才是更有价值的异常信号。

建议不要直接判定为高风险，只产生低风险提示。

## **2. 最终回答类规则**

这两条我认为需要重点修改。

### **ANSWER-001：失败后仍给出确定性结论**

保留

高风险

当前规则：

存在工具失败，但最终回答仍然给出确定性数字结论，且没有声明获取失败。

这个规则非常有价值。

举个例子：

工具执行：

```
{
  "status": "failed",
  "error": "数据库连接失败"
}
```

最终回答：

```
今年一共完成了 86 个项目。
```

显然存在问题。

但你目前使用正则匹配数字和否认/失败词语的方式，存在误判风险。

例如：

> 虽然查询失败，但根据之前的数据，今年完成了 86 个项目。

这句话包含失败词，但仍然给出了确定性结论。

建议改为检查：

1. 是否存在工具失败。
2. 失败之后是否又有成功的数据来源。
3. 最终回答是否包含确定性结论。
4. 是否明确说明数据无法获取，或者标明数据来源。

特别注意：工具失败后，Agent 可能通过另一个工具成功获取了数据。因此不能只要发生过工具失败，就直接认为最终答案不可信。

### **ANSWER-002：答案与工具结果数值不一致**

必须修改

中风险

这是我认为目前最需要修正的一条。

你当前配置：

```
统计数字字段名：
count,total,sum,cnt,num,数量,总数,合计
```

规则描述：

统计型工具结果含单一数字字段，但该数字未出现在最终回答中。

这里存在一个逻辑问题：

**数字没有出现在答案中，不等于答案与工具结果不一致。**

例如：

工具返回：

```
{
  "count": 86
}
```

最终回答：

```
今年共完成了86个项目。
```

应该正常。

但如果最终回答是：

```
今年共完成了68个项目。
```

才是真正的不一致。

所以我建议你把这条规则改为：

```
ANSWER-002：工具结果与最终答案数值不一致
```

检测逻辑：

1. 获取成功执行的 SQL/API 结果。
2. 提取结果中的统计数字字段。
3. 提取最终回答中的相关数字。
4. 比较数字是否一致。
5. 如果不一致，产生风险提示。

第一版只支持简单的单数字统计场景。

例如：

```
工具返回：count = 86
最终回答：今年完成了86个项目
检测结果：正常
工具返回：count = 86
最终回答：今年完成了68个项目
检测结果：异常
```

不要一开始就尝试处理复杂的多数字、多指标、百分比、单位换算等情况。

保留

当前规则：

相邻两轮以及以上执行失败。

例如：

```

第2轮：SQL 失败

```

这个规则很有价值。

另外，如果某次失败是可预期的业务返回，例如查询不到数据，也不能简单视为工具执行失败。

保留，但修改

连续三次调用完全相同的工具和参数，值得关注。

但要注意：

- 相同 SQL 重试可能是合理行为。
- 相同 API 不同分页参数是合理行为。
- 相同查询多次调用也可能是正常的验证过程。

建议根据：

```
tool_name + 规范化后的 tool_input
```

生成调用指纹，再进行比较。

建议将规则改为：

**相同工具及相同参数重复调用，且没有有效执行进展。**

### **REACT-004：最终回答缺失**

保留

这条规则很简单，但很有用。

# **四、我认为你现在还需要调整一个架构设计**

你提到目前的触发方式是：

> 完成提问后，通过异步线程进行诊断。

我认为这个设计非常合适，暂时不用改变。

但建议把你的诊断系统分成两个层次。

## **Agent Trace 健康诊断架构**

**第一层：规则检测引擎**

自动执行

每次 Agent 完成提问后，异步读取 Trace 数据，执行所有启用的规则。

输出：

- 命中的规则
- 风险节点
- 检测证据
- 风险等级

**第二层：AI 辅助诊断**

后续实现

当规则检测发现风险时，再让 AI 结合完整 Trace 分析。

输出：

- 最可能的问题原因
- 关联节点
- 排查建议
- 需要人工确认的事项

这里有一个关键点：

规则引擎负责判断有没有命中明确的异常条件，AI 负责解释这些异常可能意味着什么。

不要让 AI 直接决定一切是否正常。

## **那么手动诊断要不要做？**

我建议做，但不是现在的第一优先级。

你可以把它设计成两种入口：

| 入口         | 使用场景                                      |
| ------------ | --------------------------------------------- |
| 自动诊断     | 每次用户提问完成后，后台自动执行              |
| 手动重新诊断 | 开发人员修改规则后，对历史 Trace 重新执行检测 |

手动重新诊断特别有价值。

例如：

你今天新增了 `ANSWER-002`，想知道过去 100 条 Trace 中有没有答案数值不一致的问题。

就可以选择历史 Trace，重新执行最新规则。

注意，重新诊断应使用原始 Trace 数据和指定的规则版本，不应该重新调用 Agent 或重新执行 SQL/API 工具，否则可能改变原始业务状态。

另外，建议每次诊断记录规则版本，这样你才能知道某条异常是由哪个版本的规则发现的。
