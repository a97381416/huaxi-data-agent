# **一、先明确你的 Agent 执行链路**

我理解你的架构大概是这样的：

**用户提问**

User Query



**主 Agent（ReAct Agent）**

核心

理解问题、决定调用什么 Skill / Tool、观察执行结果、决定下一步行动

**Skills**

业务知识、操作规范、领域指导

**Tools**

业务 API、SQL 执行等

**ReAct 执行循环**

思考/决策 → Action → Observation → 再次决策



**最终回答**

Final Answer

注意：这里的 Skills 和 Tools 不是一回事。

- Skill：告诉 Agent 遇到某类任务应该如何处理。
- Tool：提供 Agent 真正可以执行的能力。
- ReAct：负责根据当前问题和工具执行结果，决定下一步做什么。

这三者需要分别检查。

# **二、针对你的架构，我建议设计 4 大类检测规则**

这是我认为你目前最值得实现的部分。

## **第一类：ReAct 执行链路检测**

这是你的核心。

ReAct Agent 有一个特点：它可能多次调用工具，直到认为任务完成。

例如：

```
用户提问  ↓ Agent 决策  ↓ 调用 SQL 工具  ↓ 获得 SQL 执行结果  ↓ Agent 再次决策  ↓ 调用业务 API  ↓ 获得 API 返回结果  ↓ Agent 最终回答
```

我们要检测的是整个执行过程是否合理。

| 规则 ID   | 检测内容               | 检测条件                       |
| --------- | ---------------------- | ------------------------------ |
| REACT-001 | 执行循环过多           | ReAct 循环次数超过阈值         |
| REACT-002 | 工具调用失败后继续执行 | Tool 失败，但 Agent 未正确处理 |
| REACT-003 | 工具重复调用           | 相同工具、相同参数反复调用     |
| REACT-004 | 无效循环               | 多次执行后没有产生有效进展     |
| REACT-005 | 执行提前终止           | Agent 未完成任务就结束         |
| REACT-006 | 最终回答缺失           | 整条 Trace 没有 Final Answer   |

举个例子：

**某次 ReAct 执行记录**

1. 

   Agent 决策：查询项目数量

2. 

   调用 SQL Tool：查询项目数量

3. 

   SQL Tool 返回：执行失败

4. 

   Agent 决策：再次调用 SQL Tool

5. 

   SQL Tool 返回：执行失败

6. 

   Agent 决策：再次调用 SQL Tool

疑似异常

检测结果：相同工具连续失败并重复调用，可能存在无效循环。

这里要注意：重试本身不一定是异常。比如第一次 SQL 语法错误，Agent 修改 SQL 后第二次成功，就属于合理恢复。

## **第二类：Skills 使用检测**

你有一堆 Skills，这部分也值得检查。

例如：

用户问：

> 如何查询项目的验收情况？

你的系统应该使用项目管理相关 Skill。

但 Agent 实际上没有使用任何 Skill，直接调用了 SQL 工具。

这是否错误？不一定，但值得检查。

建议规则：

| 规则 ID   | 检测内容          | 检测条件                                   |
| --------- | ----------------- | ------------------------------------------ |
| SKILL-001 | 应用 Skill 未加载 | 按业务规则应使用 Skill，但没有加载         |
| SKILL-002 | Skill 加载失败    | Skill 文件不存在或加载异常                 |
| SKILL-003 | Skill 内容为空    | 加载结果为空                               |
| SKILL-004 | Skill 使用异常    | 加载了 Skill，但后续执行明显违反其明确约束 |

其中 SKILL-001 需要你建立一个简单的业务映射关系，例如：

| 问题类型     | 预期 Skill          |
| ------------ | ------------------- |
| 项目管理问题 | project_skill       |
| 合同审查问题 | contract_skill      |
| 数据统计问题 | data_analysis_skill |

注意，不是每次对话都必须调用 Skill。只有明确规定需要使用的场景才进行检测。

## **第三类：Tools 工具调用检测**

这一类应该是你第一版重点投入的地方。

因为你的 Tool 有两种主要能力：

- 业务平台 API
- SQL 执行

它们的异常检测方式不完全相同。

**A. 业务 API 检测**

| 规则 ID | 检测内容         | 检测条件                    |
| ------- | ---------------- | --------------------------- |
| API-001 | API 调用失败     | HTTP 状态码异常或业务错误码 |
| API-002 | API 调用超时     | 超过配置的耗时阈值          |
| API-003 | API 返回为空     | 必须有数据但实际没有        |
| API-004 | API 返回格式异常 | JSON 结构不符合预期         |
| API-005 | API 重复调用     | 相同参数短时间重复请求      |
| API-006 | API 业务失败     | HTTP 200，但业务返回失败    |

特别注意 API-006。

例如：

```
{
  "code": 5001,
  "message": "项目不存在",
  "data": null
}
```



HTTP 可能是 200，但业务实际上失败了。

**B. SQL 执行检测**

| 规则 ID | 检测内容         | 检测条件                   |
| ------- | ---------------- | -------------------------- |
| SQL-001 | SQL 执行失败     | SQL 执行异常               |
| SQL-002 | SQL 执行超时     | 超过配置阈值               |
| SQL-003 | SQL 返回空结果   | 结果集为空                 |
| SQL-004 | SQL 返回数据过多 | 超过预设行数               |
| SQL-005 | SQL 重复执行     | 相同 SQL 重复执行          |
| SQL-006 | SQL 非法操作     | 出现不允许的写入或删除操作 |

这里我特别强调一点：

**SQL 返回 0 条数据不代表异常。**

例如用户确实查询不到符合条件的项目，这就是正常结果。

因此 SQL-003 应该是风险提示，而不是直接判定执行失败。

## **第四类：最终回答检测**

这是整个链路的最后一道检查。

我们要判断 Agent 是否正确利用了前面工具返回的结果。

例如：

**用户问题**

今年完成了多少个项目？

**SQL 工具返回**

执行成功

```
{"count": 86}
```



**Agent 最终回答**

结果不一致

今年完成了 128 个项目。

这就属于非常明确的异常。

建议先做这几条：

| 规则 ID    | 检测内容                   | 检测条件                               |
| ---------- | -------------------------- | -------------------------------------- |
| ANSWER-001 | 最终回答缺失               | 没有生成最终回答                       |
| ANSWER-002 | 工具结果与答案不一致       | 答案中的确定性数值与工具结果不一致     |
| ANSWER-003 | 工具失败后仍给出确定性结论 | 工具执行失败，却没有说明数据获取失败   |
| ANSWER-004 | 无工具依据回答             | 需要业务数据的问题没有相关工具结果支撑 |

ANSWER-002 可以先从 SQL 返回单一统计数字这种容易验证的场景做起，不要一开始就试图判断所有自然语言答案是否正确。

# **三、我帮你确定第一版开发范围**

上面一共涉及很多规则，但你现在是入门级 Agent，我建议第一版只做下面 12 条。

## **Agent Trace V1 异常检测规则**

建议首批实现

**ReAct 执行检测**

- REACT-001：执行循环过多
- REACT-002：工具失败后未正确处理
- REACT-003：相同工具重复调用
- REACT-004：最终回答缺失

**Skills 检测**

- SKILL-001：预期 Skill 未加载
- SKILL-002：Skill 加载失败

**Tools 检测**

- TOOL-001：工具调用失败
- TOOL-002：工具调用超时
- TOOL-003：工具返回格式异常
- TOOL-004：SQL 非法操作

**最终答案检测**

- ANSWER-001：工具失败后仍给出确定性结论
- ANSWER-002：最终答案与工具结果明显不一致

这些规则中，执行状态、超时、格式、SQL 操作等可以先用代码实现；Skills 预期使用、工具失败后的处理、答案一致性则需要结合业务配置或语义判断。

# **四、你的 Trace 界面应该如何配合？**

我不建议你再单独做一个很复杂的诊断页面。

在现有 Trace 详情页中，增加一个功能区域即可：

**自动检测**

例如：

**Trace 自动检测**

2 个风险

检测规则 12 条

本次命中 2 条

**SQL Tool**

高风险

TOOL-001 · 工具调用失败

**主 Agent**

中风险

REACT-003 · 相同工具重复调用

相同 SQL 工具和参数连续调用 3 次。

点击风险项，直接定位到对应 Trace 节点，查看 INPUT、OUTPUT、执行日志。

这样，你的现有界面就形成了：

**自动发现风险 → 定位节点 → 查看执行证据 → 人工判断原因。**

# **五、现在还有一件事比设计规则更重要**

我需要了解你现在的 Trace 到底记录了哪些数据。

因为规则能不能实现，取决于你是否采集了相应字段。

例如，要判断工具是否重复调用，就必须记录 tool_name 和 tool_input；要判断耗时，就必须记录开始时间和结束时间。

我建议你先不要写代码，也不要马上开发这 12 条规则。

**先做一次 Trace 数据结构盘点。**

| 数据       | 需要记录的内容                           |
| ---------- | ---------------------------------------- |
| 基础信息   | trace_id、session_id、开始时间、结束时间 |
| Agent 信息 | Agent 名称、模型名称                     |

其中模型内部的隐式思考过程不需要作为完整思维链保存，记录结构化的决策结果、Action、Observation 和必要的诊断摘要就够了。
