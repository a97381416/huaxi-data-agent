### TOOL-005（统计查询空结果风险提示）

它的触发条件太苛刻：用户问统计类问题 + SQL 成功但返回空 + 最终回答给出了确定性数字 + 且没有“未查到”声明。四个条件同时满足的概率很低。更关键的是，**这个场景的本质问题不是“空结果”，而是“回答与数据矛盾”**——如果 Agent 在没有数据的情况下编造了统计数字，那应该由 ANSWER-002（真数值比对）在回答层兜底；如果 Agent 老实说了“无数据”，那运维人员也不需要被提醒。TOOL-005 夹在中间，定位尴尬。

### REACT-004（最终回答缺失）

这条规则检测的是 `completed` 状态但 answer 为空。在 V1 时代这确实有意义——Agent 跑完了却没输出，是明确的故障。但在 V2 的上下文中，**如果 Agent 真的完成了任务却没有回答，大概率是前端渲染或协议层的问题，而不是 Agent 逻辑问题**。运维人员看到“回答缺失”时，能做的排查动作很有限（查日志、看 trace 尾部），而这条规则本身不提供更多线索。

## 二、关于“针对单条规则异常进行 AI 诊断”的可行性

你设想的操作——把规则异常填入诊断输入框再诊断——**在业界是有对应实践的，但入口形态和你描述的有差异**。

### 业界怎么做

阿里云 STAROps 的智能助手支持从告警直接发起诊断：用户在云监控侧边栏看到告警后，可以 `@` 引用该告警，系统自动注入告警上下文，然后进行多轮对话式根因分析。AWS CloudWatch investigations 也是从告警或指标异常直接启动，AI 自动扫描相关遥测数据并给出根因假设。这些产品的共同点是：**诊断的触发点就是异常本身，用户不需要手动复制异常信息到另一个输入框**。

更接近你设想的“单规则诊断”的，是 Opik 的 Diagnostics 功能：它自动从 trace 中聚合相似问题、识别根因并推荐修复，用户看到的是一个“问题列表”，点击某个问题即可深入。这本质上就是你说的“针对单条规则异常进行诊断”，但入口是**问题列表中的一键诊断**，而不是手动填输入框。

### 运维人员是否需要这个能力

需要，但**取决于异常的类型**。

对于 **TOOL-004（SQL 非法操作）** 或 **TOOL-007（API 业务失败）** 这类规则，异常本身已经指明了问题域（SQL 写法错误、API 返回了非成功码），运维人员大概率不需要 AI 诊断——直接看错误信息就能判断。AI 诊断在这里的增量价值是**解释为什么 Agent 会生成这样的调用**，以及**建议如何调整工具配置或提示词**。

对于 **REACT-002（连续失败未恢复）** 或 **REACT-005（无有效进展）** 这类规则，异常本身是一个“模式”，而不是一个明确的错误。运维人员看到“Agent 连续三轮没有进展”时，需要知道的是：是工具本身坏了？是参数一直在错？是数据源没数据？**这正是 AI 诊断能提供增量价值的地方**——它可以把多轮 trace 放在一起分析，给出“Agent 陷入了参数错误的循环”或“目标数据表为空导致所有查询返回空”这类根因判断。

### 建议的入口设计

你现在的 AI 诊断入口是“提问级全链路诊断”，适合**从一个用户问题出发，看整条链路哪里出了问题**。针对单条规则异常的诊断，更适合做成**风险卡片上的一个操作按钮**：

text

```
[风险卡片] TOOL-004 · SQL 非法操作 · high
  风险详情：DELETE FROM project（第 3 轮）
  [查看 Trace]  [AI 诊断此风险]
```



点击“AI 诊断此风险”后，诊断 Agent 的输入不是用户手动填的文字，而是**自动注入的上下文**：规则名称、命中证据（具体的 SQL 语句、所在的轮次、trace 片段）、该会话的摘要信息。诊断 Agent 的提示词可以围绕这个规则做针对性设计，比如 TOOL-004 的诊断提示词可以聚焦于“分析 Agent 为什么生成了写操作 SQL，是用户请求触发的，还是模型幻觉，还是工具描述误导”。

这样做的优势是：

1. **降低操作成本**：运维人员不需要理解诊断输入框该填什么，风险卡片就是入口。
2. **诊断质量更高**：规则命中的结构化证据（哪个工具、哪一轮、什么参数）作为诊断的锚点，比手动描述更准确。
3. **与现有全链路诊断互补**：全链路诊断回答“这个提问整体上出了什么问题”，单规则诊断回答“这条规则为什么触发、该怎么处理”。

### 一个需要警惕的问题

单规则诊断的**成本纪律**。你在文档里明确写了“AI 诊断每次是真实 LLM ReAct 执行”，如果每条规则异常都能一键诊断，在高风险时段可能产生大量并发诊断请求。建议：

- 单规则诊断**不自动触发**，仅由人工点击发起（与现有全链路诊断的定位一致）。
- 在风险卡片上展示“是否已有针对该会话的 AI 诊断报告”，如果有，引导用户先看已有报告，避免重复诊断。
- 对于同一会话的同一规则，可以缓存诊断结果（规则命中证据不变的情况下），二次点击直接展示缓存。

**总结**：单规则异常诊断是有价值的，尤其对于 REACT 类“模式型异常”。建议做成风险卡片上的显式操作入口，自动注入规则证据作为诊断上下文，而不是让用户手动复制粘贴。这与 STAROps 从告警直接发起诊断的思路一致，也符合你文档里“人工触发 + 成本纪律”的约束。

**应该区分，且最好不要用同一个模型。** 这不是一个可有可无的偏好问题，而是一个有明确工程依据的设计决策。核心原因在于：诊断 Agent 的角色是“审查和判断”运行 Agent 的行为，如果两者使用同一模型，会引入系统性的**自我偏好偏差（self-preference bias）**，导致诊断结论对运行 Agent 的缺陷“视而不见”或“手下留情”。

### 为什么不能用同一个模型

业界在 LLM-as-a-Judge（用模型做评判）的实践中已经反复验证：模型倾向于给自己或同家族模型的输出打更高分。Panickssery 等人的研究发现，LLM 能够识别自己的生成内容，并且这种自我识别能力与自我偏好强度正相关。在工程规范层面，已有项目明确将“评判模型必须不同于执行模型”写为强制规则，原因正是自偏好偏差被评估为高风险项。一个用于代码评估的开源项目也在架构决策中写明：评判模型必须结构性地区别于答案模型，否则模型自身的盲点会被“洗白”为合格。

放到你的场景里：运行 Agent 的模型在生成工具调用和最终回答时，如果有某种系统性弱点（比如倾向于跳过参数校验、或者在 SQL 失败后反复重试同一写法而不改参），用同一个模型去诊断它，诊断 Agent 大概率也会以同样的逻辑认为“这没什么问题”或“这是合理行为”。诊断就失去了意义。

### 怎么区分：两个务实方案

**方案 A：跨模型家族（推荐优先考虑）**

诊断 Agent 使用与运行 Agent **不同厂商或不同训练谱系**的模型。比如运行 Agent 用 Qwen 系列，诊断 Agent 用 DeepSeek 或 Claude 系列。跨家族是消除自偏好最直接的手段，业界实践中的共识也是“从不同模型家族选择评判者”。

代价是需要维护两套模型接入和可能的成本差异。但考虑到你的 AI 诊断是**人工触发、非高频**的（文档里的成本纪律），这个增量成本是可控的。

**方案 B：同家族但不同能力档位**

如果运维上实在不便引入第二家模型供应商，至少让诊断 Agent 使用**比运行 Agent 更强或不同的模型档位**。比如运行 Agent 用较小/较快的模型，诊断 Agent 用同一家族中更大/推理能力更强的模型。这不能完全消除家族层面的偏差，但能部分缓解。有实践表明，当诊断任务涉及多步推理和跨轮证据关联时，评判者至少需要与被评判者能力相当或更强。不过需要注意：同家族的不同档位仍然共享部分训练数据和偏好，偏差只是被削弱而非消除。

### 一个值得参考的业界信号

阿里云 STAROps 在运维诊断场景中已经在探索**专用决策模型**与通用大模型的分工。他们的实践表明，不同模型在运维判断的不同环节（如任务分派、进展判断、根因校验）表现差异显著，把特定判断交给专门的模型可以提升整体诊断质量。这从侧面说明：诊断链路中的模型选择是一个需要主动设计的变量，而不是“随便找一个能用的就行”。

### 对你当前架构的具体建议

在你的 V2 架构中，`MonitorDiagnoseService` 是一个独立的诊断 Agent，它已经有自己的提示词和工具集。**把它使用的模型配置从运行 Agent 的模型配置中独立出来**，是最小改动、最大收益的一步。

具体做法：

1. 在配置中新增 `diagnoseModel` 字段，与运行 Agent 的 `agentModel` 分离。
2. 默认值选择一个与运行 Agent **不同家族**的模型。如果运行 Agent 用 Qwen，诊断 Agent 可以配 DeepSeek 或 GLM 系列。

所以固定模板是可行的，但模板要解决四个**跨异常类型的共性问题**，这两份报告都没做好：

**① 轮次对照表必须是固定表格，不是散文。**
每份报告的轮次概览都写成段落，这是最大的模板化失败。表格字段固定为：`轮次 | 工具调用参数 | 观察结果 | 规则命中 | 复核结论 | 数据来源（原始/反查）`。最后一列“数据来源”是这份报告暴露出来的需求——R1 参数是反查的，必须标出来。

**② 规则命中复核矩阵必须是固定表格，且要有“期望命中”列。**
两份报告都缺“期望 vs 实际”的对照。开发修规则引擎 bug 时，最需要的就是这张矩阵——它能直接当验收标准。字段固定为：`规则@轮次 | 实际命中 | 期望命中 | 依据 | 处理方`。上一份报告的证据错配、这份报告的“合法失败是否该命中 TOOL-001”，都能在这张表里给出明确口径。

**③ “可信度声明”必须作为模板的第一个固定槽位。**
两份报告的脏数据情况不同（一份是证据错配，一份是参数反查），但都需要在开头声明“本结论不依赖哪些脏数据、哪些证据是反查/推断的”。这个槽位不能省，内容按会话实际情况填。

**④ “建议”必须带“落点”字段，不能只有方向。**
模板应该强制要求每条建议写清：`建议内容 | 落点（类/入口/配置项） | 处理方 | 优先级`。两份报告的建议都停在“提示词层面”“框架层面”这种粒度，对开发来说不够。固定模板的价值恰恰在于逼着诊断 Agent 把“提示词层面”细化成“在 system prompt 的 XX 段注入当前日期”。

------

## 四、一个需要你决策的点：模板要不要区分“异常类型”

固定骨架能覆盖 80%，但有两类异常的**归因证据链结构**差异较大，值得在骨架里做“按异常类型选填”：

- **模型生成类异常**（空参数、臆造列名、错误 SQL）：归因链核心是“排除法”——排除工具、排除提示词、排除框架，落到模型。两份报告都是这个套路，可以固定。
- **规则引擎/采集类异常**（证据错配、参数丢失、schema 未下发）：归因链核心是“数据完整性验证”，不是排除法。这类异常的报告，模板里“轮次对照表”的“数据来源”列和“可信度声明”槽位会承载更多信息。

我的建议是：**主模板固定七段（可信度声明 / 结论 / 轮次对照表 / 归因推理链 / 规则命中复核矩阵 / 分处理方待办 / 建议+落点 / 复现信息），其中“归因推理链”按“模型生成类 vs 规则采集类”提供两种填充指引**。这样既固定，又不丢类型特异性。

------

**总结**：这份报告本身质量不错，尤其“合法失败”定性和“反查补全参数”是开发会认的亮点。但作为模板样本，它和上一份共同暴露了四个模板化缺口：**轮次概览该表格化、规则命中该有“期望 vs 实际”矩阵、可信度声明该前置、建议该带落点**。固定模板可行，固定骨架 + 按异常类型填充归因链 + 强制“落点”字段，是让诊断报告从“开发愿意读”变成“开发能直接开单”的关键。另外，这两份报告都回避了一个规则引擎必须回答的口径问题——**“合法失败”到底该不该命中 high 级 TOOL-001**——这个问题不回答，模板做得再规整，规则命中复核矩阵的“期望”列也填不出来。

## 【3. 归因推理链】（排除法结构，模型生成类异常适用）

1. **排除工具缺陷**：R1 报错信息含明确错误列名与 SQL 语义错误类型（`column "quarter" does not exist`），属结构清晰的**合法失败回传**，工具无过错。

3. **排除失败后编造/级联误判**：`{数值是否一致、是否对失败数据拼接}`
4. **残余不确定性**：`{决定置信度的因素，如 schema 未下发}`
5. **根因落点**：`{模型在 X 轮生成 Y，属生成疏漏/能力缺陷}`

### 类型 B：规则采集类（证据错配 / 参数丢失 / 采集缺失）

采用**数据完整性验证链**：

1. **证据落盘完整性**：`{规则命中的证据串是否属于该轮 observation}`
2. **轮次绑定正确性**：`{证据串首现轮 vs 命中轮是否一致}`
3. **反查还原可靠性**：`{缺失参数从何处反查、是否有截断风险}`
4. **根因落点**：`{引擎绑定逻辑缺陷 / 采集接口缺失 / 索引未覆盖}`
5. **影响范围声明**：`{本缺陷是否影响其他会话的规则证据可信度}`

### 类型 C：用户反馈语义类（答非所问 / 口径错配 / 编造数值）

采用**语义匹配链**（逐环标注匹配/错配）：

1. **用户问题 → 指标语义**：`{用户问「X」，属哪类指标（金额/计数/比率）}`
2. **指标语义 → 模型 SQL**：`{模型选用何种聚合/字段，匹配或错配点}`
3. **SQL → 工具返回**：`{工具返回是否正常（工具侧无异常时显式标注）}`
4. **工具返回 → 最终回答**：`{回答数值是否有来源，无来源则定性为编造}`
5. **根因落点**：`{语义映射错配点，如「金额聚合被替换为计数」}`
6. **规则盲区标注**：`{本会话规则未命中，但存在语义层问题}`
