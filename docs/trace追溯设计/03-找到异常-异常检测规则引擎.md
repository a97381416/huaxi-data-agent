> 状态标记规则：每完成一个任务，把对应 `- [ ]` 改为 `- [x]`，并在任务后追加 `（完成于 YYYY-MM-DD）`。
> 依据：`02-gpt如何找到异常-自动巡检-诊断报告.md`（诊断思路）+ `监控中心自有表方案.md`（数据底座，Step 1/2 已完成 T1-T9）。
> 定位：第 3 步「找到异常」= 自动判断**哪个节点（哪一轮）出了问题**，而不只是展示 `success=0` 的显性失败。

## 0. 现状与差距

| 能力 | 现状（Step1/2 已交付） | 差距 |
|---|---|---|
| 显性失败 | fail_rounds 红条、first_error 免点开直出、详情默认定位失败轮、总览失败 TOP10 | 已覆盖 |
| 隐性异常 | 无 | ReAct 无效循环、相同工具重复调用、SQL 非法操作、工具失败后仍给确定性结论、答案与工具结果不一致——这些轮次 `success=1` 但链路已坏，**当前完全靠人工逐轮点开看** |

```
自动发现风险 → 定位节点 → 查看执行证据(INPUT/OUTPUT/THINK) → 人工判断原因 → AI 诊断(Step5)
```

## 2. Trace 数据结构盘点（02 文档第五节要求的动作，结论）

| 规则所需数据 | 现有落点 | 结论 |
|---|---|---|
| 轮基础信息（轮数/状态/错误/耗时/token） | `agentx_monitor_trace`：round / success / error_message / duration_ms / think_duration_ms / tokens | ✅ |
| 本轮调用的工具名 | `agentx_monitor_trace.tool_names[]` | ✅ |
| 工具调用入参（SQL 语句等） | `agentx_trace_payload.output_data` = `{"tool_calls":[{id,name,arguments}]}`（AgentLoopExecutor.toolCallsJson） | ✅ |

| 最终回答 | `agentx_monitor_session.answer / answer_trace_id` | ✅ |
| 用户问题 | `agentx_monitor_session.question` | ✅ |
| Skill 加载/使用 | ❌ 无任何落点（装配期注入，不进 trace） | SKILL 类规则不可实现 → 阶段二 |
| 工具单独执行耗时 | ❌ 无（一轮 = LLM 决策 + 工具调用整体，只有轮耗时） | TOOL 超时规则用**轮耗时**近似 |

## 3. V1 规则清单（10 条，ID 沿用 02 文档）

判定口径精确到可实现程度；severity：high=链路已坏/结论不可信，medium=高度可疑，low=提示。

### 3.1 ReAct 执行链路（4 条）

| 规则 ID | 内容 | severity | 判定口径（伪代码） | 数据 |
|---|---|---|---|---|
| REACT-001 | 执行循环过多 | medium | `session.rounds > N`（默认 15，可配） | 瘦表 |
| REACT-002 | 连续失败轮 | high | 存在相邻两轮 `success=0`（i、i+1 都失败） | 瘦表 |
| REACT-003 | 相同工具相同参数重复调用 | high | 连续 ≥N 轮（默认 3）的 tool_calls `(name + arguments归一化hash)` 完全相同。**参数有变（如改写 SQL 重试）不算命中** | payload（output_data） |
| REACT-004 | 最终回答缺失 | medium | `status=completed` 且（answer 为空 或 无成功 text 轮） | session + 瘦表 |

### 3.2 Tools 工具调用（5 条）

| 规则 ID | 内容 | severity | 判定口径 | 数据 |
|---|---|---|---|---|
| TOOL-001 | 工具调用失败 | high | ① 失败轮 `error_message` 含工具名；或 ② 第 i 轮决策调用工具，第 i+1 轮 input 中对应 tool 消息文本命中失败特征词表（error/exception/timeout/failed/失败/超时/cancelled，可配）——因为内核里工具异常会作为观察继续循环，轮本身 success=1 | payload（次轮 input 的 tool 消息） |
| TOOL-002 | 轮耗时超长 | low | `duration_ms > T`（默认 30_000，可配）。提示级：非错误但拖慢链路（工具级耗时的近似替代） | 瘦表 |
| TOOL-003 | 工具返回格式异常 | low | tool 消息内容非 JSON 且含堆栈特征（`at xx.xx(`、`Exception`、`Traceback`），或 JSON 解析失败但非纯文本表格 | payload |
| TOOL-004 | SQL 非法操作 | high | exec_sql 类工具（工具名含 `sql`，可配清单）的 arguments 中 SQL 语句含 `INSERT/UPDATE/DELETE/DROP/TRUNCATE/ALTER/GRANT`（不区分大小写）且会话不在只读白名单 | payload（arguments） |
| TOOL-005 | SQL 空结果提示 | low（**默认关闭**） | 统计类问题（question 含 多少/数量/count/统计）且末个 SQL 工具观察 `rows=[]` 且 answer 声称有数据。02 文档明确「0 条不等于异常」，仅作风险提示 | payload + session |

### 3.3 最终回答（2 条）

| 规则 ID | 内容 | severity | 判定口径 | 数据 |
|---|---|---|---|---|
| ANSWER-001 | 工具失败后仍给出确定性结论 | high | 本问命中过 TOOL-001/REACT-002（有工具失败）且 answer 含数字 + 确定性表述（共/总/为/是 N），且未声明数据获取失败（不含 无法/失败/未能） | 规则间依赖 + session |
| ANSWER-002 | 答案与工具结果数值不一致 | medium | 限定 02 文档建议的最小场景：**末个统计型工具结果 JSON 含单一数字字段**（count/total/sum/数量 等 key，值为纯数字），该数字 ∉ answer 中出现的数字集合 | payload + session |

> 阶段二再考虑：SKILL-001/002（先补采集：`agentx_monitor_trace` 加 `skill_names` 列或内核 trace 事件带 skill 标记）、REACT-005 无效循环（多轮无 token/文本进展）、API-00x（业务 API 与 SQL 工具同用 TOOL 条件细分）。

## 4. 架构与写入路径

```
closeSession（终态回填后，MonitorTraceCollector 内）
  └─ DetectDispatcher.submit(sessionId)          ← 单线程池 + 有界队列，自吞异常
       └─ AnomalyDetectService.detect(sessionId)
            ① 读 monitor_session 行 + monitor_trace 瘦行（一次 SQL，按 round 排序）
            ② 惰性取 payload：
               - toolCalls(round)：output_data 的 tool_calls（name+arguments）
               - toolObservation(round)：次轮 input 中 role=tool 消息——SQL 侧
                 jsonb 截取前 2000 字符，不整拉 input 大字段
            ③ rules: List<DetectRule> 逐条 eval(ctx)（规则独立开关+阈值）
            ④ RiskStore.replace(sessionId, hits, version)
               事务内：DELETE 该 session 旧风险 → INSERT 命中行（幂等）
                      → 回填 session.detect_status/risk_total/risk_high/first_risk
兜底：DetectSweepJob 每 5 分钟扫 status∈终态 AND detect_status<>'done' 限量 50 条补检测
手动：POST /monitor/sessions/{id}/detect（详情页「重新检测」按钮）
```

**规则 SPI**（monitor 包内，无外部依赖）：

```java
public interface DetectRule {
    String id();                          // "REACT-003"
    String title();                       // "相同工具重复调用"
    boolean enabled(DetectConfig cfg);
    List<RiskHit> eval(DetectContext ctx);// ctx 含 session行/轮次瘦行/惰性payload视图
}
```

### 4.1 新表 `agentx_monitor_risk`（一次命中一行）

```sql
CREATE TABLE IF NOT EXISTS agentx_monitor_risk (
  id              bigint PRIMARY KEY,
  conversation_id varchar(100) NOT NULL,
  session_id      varchar(100) NOT NULL,
  rule_id         varchar(20)  NOT NULL,   -- REACT-003 / TOOL-001 / ANSWER-001 …
  severity        varchar(10)  NOT NULL,   -- high / medium / low
  round           int,                     -- 主定位轮（提问内 round，深链用）
  trace_id        bigint,                  -- 主定位轮 trace 行 id
  rounds_hit      varchar(100),            -- 跨轮规则涉及轮清单，如 "5,6,7"
  title           varchar(200) NOT NULL,   -- 规则名
  detail          text,                    -- 证据摘要（一句人话，列表直出）
  evidence        jsonb,                   -- 结构化证据：args哈希/观察摘录/比对数字
  created_at      timestamp DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX IF NOT EXISTS idx_amr_session ON agentx_monitor_risk (session_id);
CREATE INDEX IF NOT EXISTS idx_amr_conv    ON agentx_monitor_risk (conversation_id, created_at DESC);
CREATE INDEX IF NOT EXISTS idx_amr_rule    ON agentx_monitor_risk (rule_id, severity);
```

### 4.2 `agentx_monitor_session` 加列（列表直出 + 兜底扫描）

```sql
ALTER TABLE agentx_monitor_session ADD COLUMN IF NOT EXISTS
  detect_status     varchar(20),            -- pending / done / failed（终态未检测=待兜底）
  risk_total        int  DEFAULT 0,
  risk_high         int  DEFAULT 0,
  first_risk        text,                   -- 首个 high 风险一句话（同 first_error 交互）
  detector_version  varchar(10);            -- 引擎版本，规则升级可按此重刷
CREATE INDEX IF NOT EXISTS idx_ams_undetected ON agentx_monitor_session (created_at)
  WHERE detect_status IS NULL OR detect_status <> 'done';
```

> 列表查询口径：`risk_total`/`risk_high` 为 0 且 detect_status='done' 才是「无风险」；running 行不计。

### 4.3 规则参数：配置表（web 管理）+ yaml 兜底（D7）

**配置表**（阈值/开关，web 端可改，读库优先——每问检测前读一次，频率极低不缓存）：

```sql
CREATE TABLE IF NOT EXISTS agentx_monitor_detect_rule (
  rule_id     varchar(20) PRIMARY KEY,   -- REACT-003 / TOOL-001 …
  enabled     boolean NOT NULL DEFAULT true,
  params      jsonb NOT NULL DEFAULT '{}',  -- 各规则阈值：{"maxRounds":15} / {"repeatCalls":3} …
  updated_by  varchar(100),
  updated_at  timestamp DEFAULT CURRENT_TIMESTAMP
);
```

- 首次启动代码 seed 全量规则行（默认阈值）；表缺行/解析失败回退代码默认值，永不让检测因配置缺失挂掉；
- `DetectConfig` 读取顺序：**配置表行 → 代码默认值**；`enabled=false` 的规则跳过 eval；
- 修改只影响**后续检测**，历史命中不自动重算——需要时单问「重新检测」即可（批量重刷留阶段二，detector_version 已留好）。

**yaml 只留总开关**（进程级熔断，出问题时可不进检测链路）：

```yaml
data-agent:
  monitor:
    detect:
      enabled: true    # 总开关；单条规则开关在配置表
```

## 5. API

| 接口 | 说明 |
|---|---|
| `GET /monitor/sessions/{sessionId}/risks` | 风险列表（详情页自动检测卡数据源；按 severity desc, round asc） |
| `POST /monitor/sessions/{sessionId}/detect` | 手动重检（同步执行返回结果，<1s 量级；兜底调度失效的人工出口） |
| `GET /monitor/sessions`（改造） | SessionPageItem 增 `riskTotal/riskHigh/firstRisk`；筛选参数 `riskOnly=true`、`severity=high` |
| `GET /monitor/conversations/{id}`（改造） | 详情 VO 的 sessions 段各带 `riskTotal/riskHigh`（问题详情页随 Q 切换时计数即取，风险明细再按需调 risks 接口） |
| `GET /monitor/detect/rules` | 规则注册表（ID/名称/级别/当前阈值/开关/默认阈值）——「规则 N 条」弹层数据源 |
| `PUT /monitor/detect/rules/{ruleId}` | 改单条规则 `enabled` / `params`（adminOnly），落配置表即时生效；返回合并后配置供回显 |

检测区域四种状态（状态头始终占一行；**收缩态只留这一行**，点 ▾/▸ 或状态头切换展开）：

```

无风险： ✓ 自动检测  未发现风险 · 规则 10 条 · 14:33                    [重新检测]  → 无卡可展
未检测： ○ 自动检测  未检测（历史数据）                                 [立即检测]
检测中： ○ 自动检测  检测中… 引擎 v1
```

交互约定：
1. 检测区域绑定**当前提问**（currentSessionId），数据源 `GET /sessions/{id}/risks`，切换 Q 时懒加载缓存；
2. 风险卡「定位 ▸」= 复用现有深链 `?sessionId=&round=` 定位（round 取主定位轮），点击滚动到该轮并高亮（同 AI 诊断证据深链）；
3. `rounds_hit="5,6,7"` 渲染为卡内轮次胶囊 `[R5][R6][R7]`，逐个可点定位；
4. 链路区域仅两处轻量改动：时间轴节点命中任一规则加 ⚠ 角标（tooltip 列规则名，失败轮保持 ❌ 前缀）；筛选加第四档「⚠」（命中轮置顶）；
5. 「重新检测」→ `POST /detect` 后刷新检测区域与时间轴角标（检测中状态头显示 spinner）；
6. 状态头「规则 10 条」点开**规则弹层**：每条规则一行（ID/名称/级别/说明 + 开关 + 阈值编辑），改动 `PUT /detect/rules/{ruleId}` 即时生效——即 D7 的轻量管理入口，不做独立管理页。
