# 监控中心自有表方案（conversation / session / trace 重建）

> 状态标记规则：每完成一个任务，把对应 `- [ ]` 改为 `- [x]`，并在任务后追加 `（完成于 YYYY-MM-DD）`。
> 本方案为增量改造，不改系统会话三表的任何写入逻辑。

---

## 0. 背景与问题

### 0.1 场景复盘

用户在同一会话窗口内连续两次提问：

1. 首问：「统计一下各项目状态的项目数量分布」→ trace 正常落库；
2. 追问：「系统中总投资金额是多少？」→ **监控中心查不到该问题，也看不到它的 trace 与最终答案**。

### 0.2 根因（2026-11-19 代码审查结论）

| # | 问题 | 位置 |
|---|---|---|
| 1 | **trace 静默丢失**：唯一索引 `uk_trace_conv_round (conversation_id, round)` 与"一次提问一个 session、round 从 1 重新计数"的数据模型冲突——追问的 round=1 与首问 round=1 必然撞键，整事务回滚且仅 warn 日志，多轮会话第 2 问起 trace/payload 全丢 | `TraceManager.java:106`、`sql/trace-monitor/V01__trace_thin_and_payload.sql:34` |
| 2 | **监控只认首问**：列表 question 只取窗口内最早一条，模糊搜索也只匹配 first_question——追问在任何页面都检索不到 | `MonitorQueryService.java:154-158、134` |
| 3 | **最终答案不在监控数据模型里**：要看某问的最终答案只能人工点开末个文本轮的 OUTPUT，提问层级无 answer 字段 | `MonitorQueryService.java:222`、`TraceDetailView.vue` |

### 0.3 验收标准（五步排查闭环）

| 步骤 | 标准 |
|---|---|
| 1 找到问题 | 能否快速找到用户的这次提问（任意一问可检索），并直接看到当时的最终答案 |
| 2 还原过程 | 能否看到 Agent 完整的执行过程（该问的全部轮次 + 明细） |
| 3 找到异常 | 能否判断是哪个节点（哪一轮）出了问题 |
| 4 分析原因 | 能否通过节点的输入输出（INPUT/OUTPUT/THINK）判断错误原因 |
| 5 得出结论 | AI 诊断能否明确告诉开发人员应该修改哪里 |

## 1. 已决策事项（2026-11-19 评审确认）

| # | 决策点 | 结论 |
|---|---|---|
| D1 | 系统三张表 | `agentx_conversation` / `agentx_session` / `agentx_trace` **完全不动**（聊天回放、评测断言等其他逻辑继续依赖，旧写入链路原样保留） |
| D2 | 监控中心自有表 | 新建三张：`agentx_monitor_conversation`（窗口）+ `agentx_monitor_session`（提问）+ `agentx_monitor_trace`（轮次） |

| D4 | 历史数据 | **不回刷**。监控中心自切换上线日起生效，切换前的旧数据仍在旧表中可查（走旧口径或直接不查，另行决定） |

| D6 | 读模式 | 监控中心（人工排查 + AI 诊断 + 指标/报表）**只读新表**；firstAppear 仍只读系统表 `agentx_session` 的消息链（只读不违例） |

## 2. 总体架构

```
                      ┌─ 旧轨（不动）──────────────────────────────┐
AgentLoopExecutor ────┤ TraceManager(旧) → agentx_trace / payload   │
  每轮调用/开题/终态    │                    agentx_conversation(旧) │
        │             └────────────────────────────────────────────┘
        └─ 新轨（本方案）
          TraceCollector SPI（内核抽接口，组合装配）
          MonitorTraceCollector(新, data-agent-server monitor 包)
            ├─ openSession  → agentx_monitor_session(一问一行) + agentx_monitor_conversation(首问建行)
            ├─ trace(每轮)  → agentx_monitor_trace(一轮一行) + agentx_trace_payload(大字段,复用)
            └─ closeSession → 回填 answer/聚合列 + UPSERT 窗口聚合

读侧（只读新表）      MonitorQueryService（列表/详情/总览/搜索）
                     TraceQueryService（AI 诊断 overview/roundDetail/searchQuestions）
                     MetricAggregateJob / ReportScheduleService（指标/报表）
读侧（只读系统表）    firstAppear（消息链真相）、SessionService 聊天回放、KernelDemoController 评测断言
```

链路模型（全链 ID 冗余，上下钻取不 JOIN）：

```
窗口 conversation 1→ N 提问 session 1→ N 轮次 trace 1→ 1 明细 payload
（一个对话窗口）        （一次用户提问）      （一轮 LLM 调用）   （input/output/think）
```

## 3. 表设计

### 3.1 语义对照

系统表 `agentx_conversation` 实际是"一次提问一行"（`UNIQUE(session_id)`）；监控三张表按监控视角重新分层：

| 新表 | 语义 | 解决什么 |
|---|---|---|
| `agentx_monitor_conversation` | 一个对话窗口一行（聚合快照） | 列表页纯单表分页，查询期零聚合 |
| `agentx_monitor_session` | **一次提问一行**（可检索） | 第 1 步：找到问题 + 看到最终答案 |
| `agentx_monitor_trace` | 一轮 LLM 调用一行 | 第 2/3/4 步：执行链路与异常定位 |

### 3.2 DDL（迁移脚本 `V0x__monitor_own_tables.sql`，幂等）

```sql
-- ① 窗口表：列表页主表，聚合列终态递增
CREATE TABLE IF NOT EXISTS agentx_monitor_conversation (
  id                bigint PRIMARY KEY,
  conversation_id   varchar(100) NOT NULL UNIQUE,
  user_id           varchar(100),
  title             varchar(120),              -- 首问截断（列表展示）
  question_count    int  DEFAULT 0,
  total_rounds      int  DEFAULT 0,
  fail_rounds       int  DEFAULT 0,
  prompt_tokens     bigint DEFAULT 0,
  completion_tokens bigint DEFAULT 0,
  status            varchar(20),               -- 聚合态 running/error/interrupted/completed
  started_at        timestamp,
  last_active_at    timestamp,
  created_at        timestamp DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX IF NOT EXISTS idx_amc_user   ON agentx_monitor_conversation (user_id, last_active_at DESC);
CREATE INDEX IF NOT EXISTS idx_amc_active ON agentx_monitor_conversation (last_active_at DESC);

-- ② 提问表：一次提问一行（检索入口）
CREATE TABLE IF NOT EXISTS agentx_monitor_session (
  id              bigint PRIMARY KEY,
  conversation_id varchar(100) NOT NULL,
  session_id      varchar(100) NOT NULL UNIQUE,  -- 内核本次提问的 sessionId（与 agentx_conversation 1:1）
  seq             int NOT NULL,                   -- 窗口内第几问（前端展示 Q1/Q2）
  user_id         varchar(100),
  question        text NOT NULL,
  status          varchar(20) DEFAULT 'running', -- running/completed/error/interrupted
  answer          text,                           -- 终态回填最终回答
  answer_chars    int,                            -- 列表懒加载门控
  answer_trace_id bigint,                         -- 终答所在轮，点击直达其 OUTPUT
  rounds          int,
  fail_rounds     int,
  prompt_tokens   bigint,
  completion_tokens bigint,
  duration_ms     bigint,
  first_error     text,                           -- 首个失败轮错误（第 3 步直出）
  created_at      timestamp DEFAULT CURRENT_TIMESTAMP,
  completed_at    timestamp
);
CREATE UNIQUE INDEX IF NOT EXISTS uk_ams_session ON agentx_monitor_session (session_id);
CREATE INDEX IF NOT EXISTS idx_ams_conv    ON agentx_monitor_session (conversation_id, seq);
CREATE INDEX IF NOT EXISTS idx_ams_created ON agentx_monitor_session (created_at);
CREATE INDEX IF NOT EXISTS idx_ams_running ON agentx_monitor_session (created_at) WHERE status = 'running';
-- 阶段二再启用（业务 SQL 不用改）：
-- CREATE EXTENSION IF NOT EXISTS pg_trgm;
-- CREATE INDEX IF NOT EXISTS idx_ams_q_trgm ON agentx_monitor_session USING gin (question gin_trgm_ops);

-- ③ 轮次表：一轮 LLM 调用一行
CREATE TABLE IF NOT EXISTS agentx_monitor_trace (
  id              bigint PRIMARY KEY,             -- 雪花；同时写 agentx_trace_payload.trace_id（新旧 id 同为雪花，共存不冲突）
  conversation_id varchar(100) NOT NULL,          -- 冗余：窗口级查询不 JOIN
  session_id      varchar(100) NOT NULL,
  round           int NOT NULL,                   -- 提问内计数，从 1
  round_type      varchar(10),                    -- tool/text/error
  tool_names      text[],
  input_chars     int,
  prompt_tokens   bigint,
  completion_tokens bigint,
  duration_ms     bigint,
  think_duration_ms bigint,
  success         int DEFAULT 1,
  error_message   text,
  created_at      timestamp DEFAULT CURRENT_TIMESTAMP
);
-- ★ 核心教训：唯一键必须是"一次提问内一轮"（session_id + round），
--   绝不是 conversation_id + round（多轮会话第 2 问起必撞键 → trace 静默丢失）
CREATE UNIQUE INDEX IF NOT EXISTS uk_amt_session_round ON agentx_monitor_trace (session_id, round);
CREATE INDEX IF NOT EXISTS idx_amt_conv    ON agentx_monitor_trace (conversation_id, created_at);
CREATE INDEX IF NOT EXISTS idx_amt_created ON agentx_monitor_trace (created_at);
CREATE INDEX IF NOT EXISTS idx_amt_failed  ON agentx_monitor_trace (session_id) WHERE success = 0;
```

要点：

- 三张表全部**窄行、无大字段**；input/output/think 继续按 trace_id 写 `agentx_trace_payload`（复用不动）；
- `agentx_monitor_trace.id` 沿用雪花 ID，与旧表 id 空间天然不冲突，payload 新旧共存；
- `seq` 为窗口内序号，写入时 `MAX(seq)+1`（同一窗口前端串行提问，冲突概率极低；如需严格并发安全改用子查询 UPSERT）。

## 4. 写入路径

### 4.1 内核 SPI（唯一的内核改动）

mini-agentx-core 把 `TraceManager.trace(...)` 抽成接口，并补两个生命周期钩子：

```java
public interface TraceCollector {
    /** 提问开始（挂点：AgentLoopExecutor 初始化、initConversation 同点位） */
    void openSession(String sessionId, String conversationId, String userId, String question);
    /** 每轮 LLM 调用（挂点：现 traceRound，签名与 TraceManager.trace 一致） */
    void trace(String sessionId, String conversationId, int round, ...);
    /** 终态（挂点：persistTerminal 之后） */
    void closeSession(String sessionId, String conversationId, String status, String finalAnswer);
}
```

- `AgentLoopExecutor` 字段类型 `TraceManager` → `TraceCollector`（`AgentLoopExecutor.java:91` 及构造器）；
- 旧 `TraceManager implements TraceCollector`（行为零变化，openSession/closeSession 空实现）；
- DodoAgent 装配处改为组合 collector：`CompositeTraceCollector([旧 TraceManager, 新 MonitorTraceCollector])`。

### 4.2 MonitorTraceCollector（新，data-agent-server monitor 包）

写入时序：

| 时机 | 动作 |
|---|---|
| 提问开始（openSession） | ① 首问：INSERT `monitor_conversation`（title=question 截断）；② INSERT `monitor_session`（seq=MAX+1，status=running） |
| 每轮（trace） | 同事务双 INSERT：`monitor_trace`（瘦行）+ `agentx_trace_payload`（大字段）。REQUIRES_NEW 独立事务，**失败仅 warn + 写入失败计数进 `agentx_monitor_metric`**，不阻断主流程、不影响旧轨 |
| 终态（closeSession） | UPDATE `monitor_session`：answer / answer_chars / answer_trace_id（末个成功 text 轮的 trace id）/ rounds / fail_rounds / tokens / duration_ms / first_error / status / completed_at；UPSERT `monitor_conversation` 聚合列递增 |

### 4.3 最终答案口径

`closeSession` 的 finalAnswer 由 `extractAnswer`（现 `SessionService.java:249` 的"实质性回答"判定：≥100 字符或含 markdown 结构，倒序取第一个）**下沉为公共工具**，聊天回放与监控中心使用同一口径，避免两边答案不一致。

## 5. 读路径改造（消费方切换清单）

| 消费方 | 现状 | 改造 |
|---|---|---|
| `MonitorQueryService` 列表 | conversation 分组聚合 + trace 聚合 JOIN + first_question 子查询（三层嵌套 SQL） | 改查 `monitor_conversation` / `monitor_session` 单表分页；**问题模糊搜索改为匹配窗口内任一提问**（`monitor_session.question LIKE`） |
| `MonitorQueryService` 详情 | 只显示首问 question，轮次扁平混合多问（R 序号重复） | 返回该窗口全部提问（question/answer/seq/status）+ 按 `session_id+round` 分组的轮次；前端时间轴按提问分组渲染（Q1·R1…Rn / Q2·R1…Rm） |
| `MonitorQueryService` 总览/卡死 | 扫 conversation + trace 聚合 | 扫 `monitor_conversation` / `monitor_session`（running partial index，扫描量极小） |
| `TraceQueryService.overview`（AI 诊断） | conversation + trace | `monitor_session`（每问一行，含 answer 摘要）+ `monitor_trace` 轮次异常 |
| `TraceQueryService.roundDetail` | trace join payload，按 session_id+round | 逻辑不变，表名替换 |
| `TraceQueryService.firstAppear` | 扫 agentx_session original_messages | **不动**（消息链是真相，只读系统表） |
| `MetricAggregateJob` | 扫 agentx_trace 计数/聚合 | 扫 `monitor_trace`（字段同名，SQL 基本原样） |
| `ReportScheduleService` | 扫 agentx_trace 失败聚合 | 扫 `monitor_trace` |
| `SessionService`（聊天回放）、`KernelDemoController`（评测断言）、`ActionAuditLogger` | 读旧表 | **不动**（旧表照写，零影响） |

### 五步验收对照

| 步骤 | 落点 |
|---|---|
| 1 找到问题 | 列表/命令面板按问题文本检索（每问一行）→ 行内 question + answer 预览 + answer_trace_id 直达终答轮 |
| 2 还原过程 | 详情按提问分组时间轴；轮次明细 INPUT/OUTPUT/THINK 懒加载（契约不变） |
| 3 找到异常 | fail_rounds>0 红条 + first_error 免点开直出；失败 partial index；详情默认定位失败轮 |
| 4 分析原因 | 单轮 INPUT/OUTPUT/THINK 原文（renderInputData 契约不变） |
| 5 得出结论 | AI 诊断 overview 第一屏即"问了什么 / 最终答了什么 / 哪轮失败 / 错误是什么" |

## 6. AI 诊断增强

1. **数据源切换**：overview / roundDetail 切新表（见 §5）。
2. **新增第四工具 `searchQuestions(keyword)`**：模糊检索 `monitor_session.question`，返回 conversation_id + session_id + question + answer 摘要 + status——解决"用户只记得问题原文、不知道任何 ID"的入口问题，补全第 1 步闭环。
3. **术语统一**：工具描述里明确"一次提问（session）= monitor_session 一行；一轮 = monitor_trace 一行"，消除旧数据模型里会话/轮次的混淆。

## 7. 性能设计

| 维度 | 措施 |
|---|---|
| 写入 | 每轮 2 条窄 INSERT + 每问 1 INSERT + 终态 1 UPDATE + 1 UPSERT；窄索引；REQUIRES_NEW 小事务；相对现状只多一组同构写入，量级不变 |
| 读取 | 列表/总览/报表全部读**物化聚合列**，无运行时聚合；旧的三层嵌套聚合 SQL 直接消失 |
| 大字段 | payload 隔离 + 懒加载门控（answer_chars / input_chars 预览，>100KB 确认加载，沿用现有交互） |
| 检索 | question 模糊初期 LIKE（行数=提问量，可控）；数据量上来后启用 pg_trgm GIN，一条索引、业务 SQL 不改 |
| 失败可观测 | 监控表写入失败计数进 `agentx_monitor_metric`，总览给"trace 写入失败数" KPI——杜绝再次静默丢数据而无人知晓 |
| 深分页 | 当前 LIMIT/OFFSET 可接受；后续如有需要升级 keyset（created_at, id）游标 |

## 10. 风险与备忘

| # | 项 | 说明 |
|---|---|---|
| 1 | 旧表唯一索引仍在丢数据 | 本方案新表已规避，但旧轨（评测断言、聊天思考耗时对齐等读旧表的逻辑）在多轮会话下依旧缺第 2 问起的 trace——T10 建议尽快单独执行（一条 DROP+CREATE，不动逻辑） |
| 2 | 双写一致性 | 监控表允许极少量丢失（不阻断主流程），由失败计数 KPI 兜底发现；不影响系统表 |
| 3 | seq 并发 | 同一窗口并发提问理论少见（前端串行）；如出现，`MAX(seq)+1` 可能重号——改子查询 UPSERT 即可 |
